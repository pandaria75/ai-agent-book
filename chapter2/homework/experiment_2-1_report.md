## 2. 实验目的

1. 在本地网络中部署并访问 Ollama 大语言模型服务。
2. 理解 Agent 的工具调用闭环：模型选择工具、生成参数、Python 执行工具、将结果回灌模型并生成最终回答。
3. 观察流式响应中的思考片段、工具调用和最终文本。
4. 测量小模型服务的首 token 延迟、生成吞吐、KV Cache 效果及不同并发度下的吞吐变化。
5. 扩展一个自定义工具，验证工具注册机制。

## 4. 实现过程

### 4.1 Agent 与工具调用流程

`ToolCallingAgent` 在 Ollama 后端下创建 `OllamaNativeAgent`。工具以 OpenAI 兼容的 JSON Schema 注册在 `ToolRegistry` 中。一次请求的处理流程为：

```text
用户问题
  -> Ollama 模型生成 tool call
  -> ToolRegistry 分派并执行 Python 函数
  -> 工具结果作为 tool message 返回模型
  -> 模型生成自然语言答案
```

工具调用阶段支持 `ThreadPoolExecutor` 并行执行相互独立的多个工具。例如，“温哥华现在几点、天气如何”的请求可同时调用 `get_current_time` 与 `get_current_temperature`。

### 4.2 已启用工具与自定义扩展

实验中已注册的工具如下：

| 工具 | 用途 |
| --- | --- |
| `get_current_temperature` | 通过 Open-Meteo 查询指定地点的天气和温度 |
| `get_current_time` | 查询 IANA 时区的当前日期和时间 |
| `convert_currency` | 使用示例汇率进行货币换算 |
| `code_interpreter` | 执行 Python 代码 |
| `generate_uuid` | 本实验新增，生成 UUID v4 唯一标识符 |

自定义工具 `generate_uuid` 通过 `uuid.uuid4()` 生成标识符，Schema 不需要任何参数。实际提问“帮我生成一个 UUID”时，模型正确选择并调用了 `generate_uuid`，返回 UUID `3279b0ef-ebf1-46d4-8dcf-0f7431518a25`，证明自定义工具已被模型识别、调用和回传。

### 5.3 服务性能基准

对远程 Ollama 服务运行全部场景，原始数据保存于 `local_llm_serving/results.json`。结果如下。

| 场景 | 指标 | 结果 |
| --- | --- | --- |
| throughput | 重复次数 | 5 |
| throughput | 平均 TTFT | 0.337 s |
| throughput | 平均解码吞吐 | 57.5 tok/s |
| throughput | 平均输出长度 | 256 tok |
| kv-cache | 共享前缀长度 | 约 1024 tok |
| kv-cache | 命中平均 TTFT | 1.618 s |
| kv-cache | 未命中平均 TTFT | 2.070 s |
| kv-cache | 命中相对加速 | 1.28x |

批处理结果：

| 并发度 | 聚合吞吐 | 单请求吞吐 | 平均 TTFT | 墙钟时间 |
| ---: | ---: | ---: | ---: | ---: |
| 1 | 59.4 tok/s | 59.4 tok/s | 0.096 s | 4.31 s |
| 2 | 97.5 tok/s | 48.7 tok/s | 0.090 s | 5.25 s |
| 4 | 98.7 tok/s | 24.7 tok/s | 2.657 s | 10.28 s |
| 8 | 98.6 tok/s | 12.3 tok/s | 7.846 s | 20.78 s |

结论如下：

1. 单流生成速度约为 57.5 tok/s，远程局域网调用仍可获得较短的热启动首 token 延迟。
2. 前缀完全一致时，KV Cache 命中使 TTFT 从 2.070 s 降至 1.618 s，说明保持系统提示词稳定有利于降低预填充计算成本。
3. 并发从 1 增至 2 时，聚合吞吐由 59.4 tok/s 提升到 97.5 tok/s；继续提高到 4 和 8 时，聚合吞吐基本饱和在约 98.6 tok/s，而单请求吞吐和 TTFT 明显恶化。这体现了连续批处理的典型权衡：提高整体吞吐会牺牲单请求延迟。

## 6. 问题与分析

在“查询巴黎天气并把 20 摄氏度转换为华氏度”的流式对比测试中，模型调用 `code_interpreter` 时生成了类似 `20°C in Fahrenheit = 20 * 1.8000` 的非法 Python 代码，因包含 `°` 字符和自然语言而触发 `SyntaxError`。最终回答仍错误地给出 `20°C = 40°F`，正确值应为 `68°F`。

这一现象说明：

1. 工具调用成功不等于任务答案一定正确；需要同时校验工具参数、工具返回值与模型最终表述。
2. `qwen3:0.6b` 作为小模型能够完成常见的工具选择和参数填充，但在多步骤推理、单位换算和可执行代码生成上存在可靠性限制。
3. 对数值任务，应提供专用且受限的计算工具，或在工具侧增加参数验证与结果校验，不宜完全依赖模型生成自由形式 Python 代码。
4. 该截图中的天气单位也说明最终自然语言答案可能误读工具返回字段，因此生产场景应使用结构化结果模板或增加结果一致性检查。

## 7. 实验结论

本实验完成了远程 Ollama 服务接入、标准工具调用、流式中间状态展示、并发工具执行、性能基准测试和自定义 UUID 工具扩展。实验验证了小型本地模型在明确工具 Schema 和 Agent 循环支持下可以完成天气、时间等实时信息任务；同时，KV Cache 与批处理结果说明上下文稳定性和并发策略会直接影响服务性能。

实验也表明，模型最终回答仍需经过可靠性评估，特别是涉及数值、单位换算或代码生成时，不能仅因工具调用发生就认定结果正确。后续可通过专用计算工具、输入输出校验和更大模型进一步提升准确性。

# 实验 2-2：注意力机制可视化

## 1. 实验目的

本实验使用 `attention_visualization` 项目观察 Qwen3 模型在处理文本时的自注意力分布，理解以下概念：

1. 注意力矩阵中行（Query）和列（Key）分别对应正在关注与被关注的 token。
2. 自回归语言模型的因果掩码使 token 只能关注自身和先前 token。
3. 序列首 token 可能形成 Attention Sink，即吸收大量注意力权重的稳定位置。
4. Agent 的提示词、工具定义、推理文本和最终回答都会成为同一条 token 轨迹的一部分。

## 2. 实验环境与方法

实验在 Windows 环境中运行。模型为 `Qwen/Qwen3-0.6B`，通过 Hugging Face Transformers 在本地加载；注意力可视化使用 `attention_cli.py`，其默认设置为最后一层（`layer=-1`）并对全部 attention heads 求平均。

本次完成的基础可视化使用默认提示词：

```text
北京 的 天气 怎么样
```

CLI 会使用模型 Chat Template，因此热力图同时包含 `<|im_start|>`、`system`、`user`、`assistant` 等结构 token。除此之外，交互式 Agent 在 `frontend/public/trajectories/` 中写入了 2026-09-19 20:34 至 20:37 的 7 条新轨迹，覆盖 Knowledge、Math、Creative、Reasoning、Code 和 ReAct 类别。

## 3. 注意力热力图结果

**图 5：北京天气提示词的最后一层平均注意力热力图。**

![[attention_heatmap.png|北京天气提示词的最后一层平均注意力热力图]]

图中横轴是被关注的 Key 位置，纵轴是当前 Query 位置。图标题记录了本次实测结果：首 token 的 attention sink 平均占比为 **76.1%**，单行最大值为 **100.0%**。

从图中可以观察到：

1. 矩阵右上区域为空白，只有主对角线及其左下方存在注意力值，符合因果掩码规则。也就是说，当前 token 不会关注未来 token。
2. 第一列长期呈现高亮颜色，说明大量 Query token 将注意力分配给序列起始的 `<|im_start|>` token。这是 Attention Sink 现象的直接证据。
3. 除首 token 外，主对角线附近也存在较明显的注意力，说明 token 会关注邻近上下文和自身位置。
4. 输入并非只含“北京”的自然语言 token，还包含 Chat Template 的系统消息及角色边界。这说明真实模型的注意力对象是完整 token 序列，而不是仅用户可见的问题文本。

## 4. 轨迹观察

本次运行保存的轨迹清单记录了 5 条基础问答和 2 条 ReAct 轨迹。基础轨迹覆盖事实知识、算术、创作、逻辑推理和代码生成；每条轨迹均保存 token 序列与注意力矩阵，供前端热力图组件查看。

复利计算 ReAct 轨迹包含 2 次模型调用和 5 个推理步骤：模型先在 `<think>` 区分析复利公式，随后调用 `code_interpreter`，工具成功计算出终值 `$30,112.88` 和利息 `$25,112.88`，最后再根据工具观察生成答案。这说明注意力可视化不只适用于单轮自然语言输入，也能保留包含系统提示词、工具 Schema、思考、工具调用和工具结果的较长 Agent 上下文。

该轨迹也发现一个回答质量问题：模型最后将 30 年的“总回报”表述为约 `25.11%`，但其计算出的利息为 `$25,112.88`，相对 `$5,000` 本金约为 `502.26%`。因此，注意力轨迹可用于观察模型的上下文与推理过程，但不能替代对最终数值答案的校验。

## 5. 完成范围说明

本次已完成并可由个人产物验证的内容是：本地 Qwen3 模型加载、北京天气提示词的真实注意力热力图导出、Attention Sink 测量，以及多类别和 ReAct 轨迹保存。

项目中另有 `run_attention_experiment.py` 的严格验收流程，可额外导出第 0、中间和最后层的无损注意力矩阵、推理区与最终答案区的分区统计、两张对比热力图及 `evidence.json`。当前作业未将仓库预存的 `runs/exp2-2-*` 结果当作本人的实验数据，因此本报告不引用其中的数值或图片。

## 6. 实验结论

实验直观验证了因果注意力的下三角结构和 Attention Sink 现象：在本次北京提示词运行中，首 token 平均吸收了 76.1% 的注意力。该结果说明模型注意力并非均匀分布，而会同时受位置、Chat Template 结构和局部上下文影响。

注意力机制也是 KV Cache 的基础。每个历史 token 的 Key 和 Value 会在生成过程中被后续 token 重复读取；当上下文前缀保持不变时，这些中间结果可以复用。当系统提示词、工具定义或角色边界发生变化时，变更位置之后的 Key/Value 缓存便不能继续复用。这也是 Agent 系统中应保持稳定前缀、把动态信息追加在上下文末尾的原因。

# Context、Memory 与 RAG 的理解

## 1. 上下文窗口及上下文组织方式

上下文窗口是模型在一次推理中可见的 token 容量上限。对 Agent 而言，上下文并不只是用户当前的问题，而是由系统提示词、工具定义、用户消息、历史 assistant 消息、工具调用及其结果共同构成的消息列表。本实验中，天气或时间查询会先由模型生成 tool call，框架执行工具后再将 tool result 追加到消息历史，模型据此生成最终回答；这正是上下文随着 ReAct 循环逐步增长的过程。

上下文应按“稳定前缀 + 动态轨迹”组织：系统提示词和工具 Schema 尽量固定在前部，便于 KV Cache 复用；用户新消息、工具结果、当前时间和任务状态等动态信息只追加在末尾，避免修改已缓存前缀。实验测得完全一致的前缀可将 TTFT 从 2.070 s 降至 1.618 s，说明上下文组织不仅影响模型是否看得到关键信息，也直接影响延迟和成本。上下文接近窗口上限时，不能简单滑动删除历史，否则可能遗失工具结果并导致重复调用；更合适的方式是保留关键决策、约束和来源，对旧内容进行摘要或按需检索。

## 2. 短期上下文与长期记忆的区别

短期上下文服务于当前会话和当前任务，包含本轮问题、近期轨迹和工具观察；它随每次 API 请求重新发送，受上下文窗口限制，并在会话结束后不一定继续保留。实验中的模型之所以能根据时间工具的返回值回答问题，是因为该结果仍在当前短期上下文中。

长期记忆则跨会话持久保存，通常记录用户偏好、身份信息、历史事件和稳定事实，例如“用户偏好靠窗座位”。它不应直接保存所有原始对话，而应经过选择、抽象、结构化、冲突处理和来源核验。短期上下文像当前任务的工作台，强调实时性和完整交互轨迹；长期记忆像可维护的用户档案，强调持久性、可检索性和可更新性。长期记忆被检索出来后，仍需要作为一部分注入短期上下文，模型才能在当前推理中使用它。

## 3. RAG 在 Agent 中承担的作用

RAG（检索增强生成）负责把模型参数之外的知识或历史记忆按需取回，并注入当前上下文。其基本流程是“分块和索引 -> 检索相关内容 -> 将结果作为上下文 -> LLM 生成或继续决策”。它使 Agent 可以访问最新的、私有的、可追溯的知识，而不需要把全部文档永久塞入 Prompt 或重新训练模型。

在 Agent 中，RAG 既可以检索共享知识库中的政策、技术文档，也可以检索某个用户的长期记忆。对于复杂问题，检索还可作为工具由 Agent 多轮调用：先检索、观察信息是否充分、再调整查询并补充检索。RAG 的结果只是外部参考数据，不是高优先级指令；检索内容应标注来源，并且不能仅凭其中的文本触发删除、转账等高风险操作。三者的关系是：Memory 或知识库负责长期存储，RAG 负责在需要时找到相关内容，Context 负责承载这些内容并让模型在当前回合中使用。
