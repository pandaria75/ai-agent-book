# 上手智能体

如果你用 Cursor 写过代码，看着它搜索代码库、编辑多个文件并反复重跑测试直到通过，那么你其实已经在使用智能体了。同样，如果你用 Deep Research 通过反复搜索和阅读来调研一个主题，让 Manus 控制浏览器完成在线任务，让豆包手机助手订票或发消息，或者派 Pine AI 去协商降低电信账单——这些也都属于智能体的应用。

这些产品形态各异，但它们有一个共同特征：不再是被动的"你问它答"的对话。它们会自行规划执行步骤，调用每个任务所需的工具，并根据结果动态调整策略。智能体正在成为人机交互的新方式。

本章从实际案例出发，逐步回归智能体的核心组成：读者将亲身体验现代智能体能做什么，理解其背后的架构，并学习构建智能体系统的设计模式与最佳实践。

> **阅读提示**：本章是全书的概念地图：对核心公式、运行循环、工程框架和智能体设计模式的一次简要导览。它建立了后续各章通用的术语体系和参照基准。第一次阅读时不要试图记住每个概念，先把整体图景建立起来。后面每一章都会展开本章介绍的某一个方面，当你需要重新定位方向时，随时可以回到本章。

## 现代智能体 = LLM + 上下文 + 工具

最简形式下，现代智能体由三个组件构成：**智能体 = LLM（大语言模型）+ 上下文 + 工具**。这里的加号表示工程组件的组合，并非强化学习中的正式定义；更重要的是，这个公式只描述智能体边界之内的内容，**不包括智能体与之交互的环境**。每个术语都需要广义理解，同时保持清晰的边界：

- **LLM 是智能体的推理引擎**：它不仅是一组模型参数，更是智能体的决策核心，负责理解意图、推理、规划和判断。LLM 的能力来自**预训练**阶段获得的世界知识和语言能力，加上**后训练**阶段编码的决策策略（监督微调、强化学习等技术详见第 8 章）。
- **上下文是智能体的信息工作集**：不只是喂给模型的文本，而是智能体在每个决策点上可获取的信息工作集——环境、用户记忆、领域知识、自身状态以及任务进度。正如一个人做决策时需要审时度势、回忆相关经验、查阅参考资料，智能体的上下文窗口包含的就是它在那一刻可以使用的信息。
- **工具是智能体的行动接口**：不只是几个可调用的 API 函数，而是智能体与外界交互的全部方式——从预定义的工具调用到按需加载的技能（Skills），从即时生成代码来创造新能力到将工作委派给子智能体，从主动触达用户到响应外部事件。

换一种更直观的说法：**智能体 = 推理引擎 + 工作上下文 + 行动接口**。模型负责推理和决策，上下文提供决策所依赖的信息工作集，工具提供决策影响外部世界的接口。

从经典的强化学习与控制论视角来看，智能体与环境是闭环交互的两端，而非彼此的组成部分。环境返回观测，智能体利用其上下文选择下一个行动，该行动改变环境状态，进而产生下一个观测。

![图 1-1：智能体与环境的交互循环，以及智能体内部的"模型—驾驭层"结构](images/fig1-1.svg)

图 1-1 展示了两个抽象层次。外层是**智能体与环境的交互**：环境包括文件系统、数据库、网页、用户、其他智能体，以及物理或模拟世界。内层是**智能体内部的"模型—驾驭层"结构**：模型负责策略决策；驾驭层是智能体边界内的运行时与治理层，负责构建上下文、暴露工具接口、维护循环与状态，并执行权限控制、校验和纠正。驾驭层可以创建、隔离或代理一个环境，但自身不包含该环境的状态或转移规则。

因此，工程公式可以进一步展开为：LLM 即模型，而上下文 + 工具构成最小驾驭层；生产系统还会在这个边界内部加入约束、校验和纠正机制。本章后续内容将沿用这个边界划分。

这三个组件可以与强化学习（RL；详见第 8 章）中的策略和交互接口相对应，但并非一一映射。上下文代表智能体内部的观测和历史，并非完整的观测空间；工具定义了智能体可用的观测和行动接口，而它们作用的对象仍然存在于环境中。

| 直觉类比 | 智能体组件 | 强化学习概念 | 角色 |
|---------------|----------------|------------------|---------------------------------------------|
| **推理引擎** | LLM | **策略** | 决定"接下来做什么"的决策逻辑——根据当前信息，从所有可选方案中选出最合适的行动 |
| **工作上下文** | 上下文构建 | **观测与历史** | 将环境观测和已有历史组织为当前决策所需的信息 |
| **行动接口** | 工具接口 | **观测/行动接口** | 定义智能体可以读取哪些观测、可以发出哪些行动，以及这些接口的格式 |

### 观测空间与行动空间：模型与世界的接口

**观测空间和行动空间共同构成 LLM 与其外部环境之间的接口**。观测空间将环境中的信息转化为模型可处理的上下文；行动空间将模型的决策转化为对外部世界的具体操作。不在观测空间内的信息，对模型而言实际上不存在；不在行动空间内的操作，即便模型清楚地知道应该做什么，也只能以文字推荐的方式表达。

因此，**一旦底层模型固定，提升智能体性能的首要系统工程手段，往往是重新定义或扩展其观测空间和行动空间**。用本书的术语来说，就是扩展上下文和工具。许多看似需要"更聪明的模型"才能解决的问题，其实是接口问题：把任务相关的数据带入上下文，或把所需操作暴露为工具，之前无法解决的任务可能就此迎刃而解。

**Manus：合并原本割裂的空间。** 在 Manus 出现之前，生产级智能体基本沿三条截然不同的赛道发展：深度研究（Deep Research）、编码（Coding）和计算机操控（Computer Use）。Manus 是第一个将三者融于一体的广泛影响力的生产级智能体。它的虚拟浏览器扩展了观测空间，而文件系统、代码执行和命令执行则扩展了行动空间。Manus 并非仅仅通过更换更强的模型就成为了通用智能体——它取三类智能体观测空间和行动空间的并集，使一个智能体得以跨越此前的产品边界。

**OpenClaw：将接口延伸到用户的数字生活。** OpenClaw 再次将两个空间向外推展。它通过用户已有的消息通道（WhatsApp、Telegram、Slack、Discord、iMessage 等）接收任务并返回结果，使用户几乎可以从任何地方触达智能体。其本地网关（Gateway）既可接入 Google Drive、Notion 等云端应用，也可接入本地文件系统。因此，散落在各个账户和设备上的文件，在用户明确授权后，可以进入同一个智能体的观测空间，并被其工具操作。相较于以云端沙箱为中心的 Manus 原始形态——文件通常需要上传或单独配置连接器——本地优先的 OpenClaw 覆盖了更广的数据边界。Manus 后来也推出了自己的 Google Drive 连接器和访问本地文件的桌面功能，这恰恰印证了这一观点：产品的演进往往就体现为观测空间和行动空间的不断扩展[^ch1-agent-products]。

[^ch1-agent-products]: Manus 官方资料称其原始 Sandbox 是一台隔离的云端虚拟机。在推出 Google Drive 连接器时，Manus 明确回顾了此前在 Drive、桌面和 Manus 之间手动下载上传文件的碎片化工作流。2026 年 3 月推出"My Computer"时，它指出重要工作内容保存在本地而非云端是云沙箱的根本局限。OpenClaw 官方 README 描述了一个运行在用户自有设备上、本地优先、始终在线的个人助理，并列出了二十多个消息通道；其工具和插件系统可以添加云端集成和本地能力。参见 https://manus.im/blog/manus-sandbox、https://manus.im/blog/manus-google-drive-connector、https://manus.im/blog/manus-my-computer-desktop、https://github.com/openclaw/openclaw 和 https://docs.openclaw.ai/tools

理解每个组件的作用以及它们如何协同，是构建高效智能体系统的基础。我们将从三者中最具体的一个——工具，即行动接口——开始，再逐步深入 LLM 和上下文。首先，来看不同类型智能体在这三个维度上的对比：

| 智能体产品 | 工作上下文 | 行动接口 | 策略 |
|-----------------|------------------------|--------------------------|-----------------------------|
| **编码智能体（如 Cursor）** | 需求文档、代码库、终端环境 | 开放式（内部推理、代码搜索、文件读写、命令执行等） | 增量开发：理解需求 → 搜索相关代码 → 编辑代码 → 测试验证 → 调试修复 |
| **搜索智能体（如 Deep Research）** | 网络资源、学术数据库、本地文件 | 开放式（内部推理、搜索查询、网页阅读、摘要生成） | 迭代深入：根据已有信息调整搜索方向，逐步综合出完整报告 |
| **计算机操控智能体（如 Browser Use）** | 电脑屏幕、浏览器页面、文件系统 | 开放式（内部推理、点击、输入、滚动、截图、代码执行等） | 视觉感知 + 操作：观察屏幕 → 识别目标元素 → 执行动作 → 验证结果 |
| **手机助理智能体（如豆包）** | 手机屏幕、已安装应用 | 开放式（内部推理、点击、滑动、输入、打开应用等） | 意图理解 + 应用操控：理解用户需求 → 定位目标应用 → 执行动作 → 确认完成 |
| **个人任务智能体（如 Pine AI）** | 用户账户信息、历史账单、服务商知识库 | 开放式（内部推理、拨打电话、发送邮件、填写表单、与用户确认） | 多步骤任务执行：收集信息 → 制定谈判策略 → 联系服务商 → 谈判 → 汇报结果 |

这些系统共享三个特征：**开放式的行动空间**——不是从固定的按钮集中选择，而是生成任意自然语言和代码；**内部推理**——先规划再行动；**持续交互**——根据环境反馈调整策略。这些能力恰恰来源于推理引擎、工作上下文和行动接口三者的协同——即 LLM、上下文和工具。

### 工具：智能体的行动接口

工具是智能体通向外部世界的桥梁。它们将智能体从被动的观察者转变为主动的系统，能够搜索、写文件、运行代码、调用 API、发送消息或操控界面。没有工具，智能体仅限于文本生成；有了工具，它便能对外部系统施加影响。

为了系统地讨论工具，我们可以按照智能体与世界交互的方向将它们分为五类。目前每类举几个例子来建立整体认识即可；后续章节会深入探讨。

**感知工具** 让智能体获取信息：搜索引擎提供实时网络数据，文件系统读取本地文档，API 和数据库连接外部服务与企业核心数据。

**执行工具** 让智能体作用于外部系统：代码执行、文件操作、系统命令和外部 API 调用，将决策转化为具体行动。

**协作工具** 让智能体与其他智能体分担工作：将专业任务委派给子智能体、在关键决策点请求人工确认，或在多智能体系统中协调行动。

**事件触发工具** 的调用方式与前三大类有根本不同：智能体不会主动调用它们，它们作为外部输入到达，触发智能体开始工作。一封新邮件到来、定时时间到达，或者另一个系统触发了 Webhook 回调——事件激活智能体并启动推理与行动。智能体从不自行调用这些工具，但它们仍是智能体与外部世界交互的通道，因此我们将其纳入广义的工具体系。

**用户通信工具** 是智能体与用户沟通的渠道。执行工具改变外部世界，而通信工具传递信息——通过短信、语音通话、邮件等，传递智能体的进展汇报或主动的进度询问。

第 4 章将涵盖这五类工具的完整分类和设计原则。工具设计的质量直接决定了智能体能可靠地完成什么：接口定义模糊，模型就会误用它；错误处理不当，一次工具失败就可能让智能体卡住；权限范围过宽，一次智能体错误就可能造成不可逆的后果。随着 MCP（模型上下文协议，Model Context Protocol）标准的普及，集成工具正在变得越来越容易。

**工具调用**（也称函数调用，Function Calling）是现代 LLM 智能体的核心能力：它使模型能够以结构化的方式调用外部工具，将 LLM 从纯文本生成器转变为能够通过外部接口采取行动的智能系统。本书全程使用"工具调用"这一术语。

工具调用分为四个步骤：首先，上下文告知模型有哪些可用工具（名称、用途、参数）；然后，模型自行决定是否调用工具、调用哪个工具、传什么参数；接着，工具运行完毕后，其结果被追加到上下文中；最后，模型根据结果决定下一步行动。这个循环就是后文将要介绍的推理-行动（ReAct）模式的基础。

以天气查询为例，API 层面四个步骤的简化表示如下：

```text
Step 1: Declare tools                  Step 2: Model decides to call
tools: [{                             assistant: {
  name: "get_weather",                  tool_calls: [{
  parameters: {                           function: "get_weather",
    city: "string"                        arguments: {city: "Beijing"}
  }                                      }]
}]                                    }

Step 3: Result appended to context    Step 4: Model responds based on result
tool: {                               assistant: {
  tool_call_id: "call_1",               content: "Today in Beijing: 28°C, sunny."
  content: '{"temp":28,"sky":"clear"}' }
}                                     }
```

开发者只需定义工具并执行调用；是否调用、调用哪个工具、传什么参数，都由模型自己决定。第 2 章将详细分析这一 API 结构。

为智能体设计工具时，应从任务所需的最窄能力开始，随着任务复杂度的提升再逐步扩展。如果任务只需要基本算术，一个参数定义清晰的计算器就够了；当任务发展到读取电子表格、清洗缺失值、计算统计量并绘制图表时，一个受限的 Python 代码解释器比不断膨胀的专用工具集更容易组合和探索。但通用性也会增加错误风险并扩大攻击面：代码必须在隔离沙箱中运行，默认禁用网络访问，不允许访问授权工作目录之外的文件，并对执行时间、CPU、内存和输出大小加以限制。

同理，单次日志工具适合记录一次执行；对于持续数小时甚至数天的长时间任务，一个受控的虚拟工作目录可以保存计划、中间结果、执行日志和最终产物，使智能体能够在多次运行之间恢复状态。这个目录同样需要限制可读写的路径、存储容量和文件类型，并防止路径穿越，而非将整个宿主文件系统暴露给智能体。

通用工具并不总是优于专用工具。高风险操作或受严格业务约束的操作——如支付、数据删除、发送邮件和生产部署——仍应作为专用工具暴露，具备明确的参数、受限的权限和端到端的可审计性，并在必要时加入预览和人工确认。因此，工具设计的核心原则是：**用通用的基础能力进行组合与探索；用专用工具约束高风险操作并严格执行业务规则**。

### LLM：智能体的推理引擎

大语言模型（LLM）是智能体的决策核心。给定一个用户请求，它首先要推断真实意图（用户说的往往不是他们真正想要的），然后将模糊或复杂的任务拆解为可执行的步骤。在整个执行过程中，它不断做出决策：下一步做什么、是否调用工具、调用哪个工具、传什么参数。这种"理解—规划—执行"的能力来自预训练阶段积累的知识，也是工作流和自主智能体共同依赖的基础。

LLM 智能体的一个独特能力是**内部推理**——在行动之前，智能体可以先对任务进行规划和推理。这不会改变外部环境，却能显著提升后续行动的质量。这种能力源于预训练（在海量互联网文本上的初始训练，模型从中习得语言模式和世界知识）：模型调用编码在人类知识中的推理模式，包括数学规律、因果关系和问题分解策略。因此，与传统的强化学习智能体不同，今天的 LLM 智能体并非通过盲目试错进行探索，而是在结构化的知识体系上进行推理。

#### 模型即智能体：当模型本身成为产品

# 智能体入门 [第 2/5 部分]

"模型即智能体"范式是智能体开发的最新方向。先进模型通过后训练（尤其是强化学习）将工具调用内化为原生能力：何时调用工具、调用哪个工具、使用什么参数——全部由模型自行决定，无需人工编排。这并不意味着框架层不再重要。恰恰相反：模型越强大，周围的驾驭层就越关键。Harness 一词最初指的是套在马身上的缰绳和挽具——不是为了限制马奔跑的能力，而是为了恰当地引导这股力量。在智能体语境中，模型是强大但难以预测的马，而驾驭层则是将其能力引导为可靠任务执行的工程基础设施。它包括上下文管理、工具接口、安全约束以及验证与纠正机制（见本章最后一节）。

模型拥有的决策权越大，错误决策的影响就越大——这就要求更细粒度的约束、验证和纠正来保证其可靠性。模型提供商的真正优势不在于"让框架更薄"，而在于能够协同优化模型及其周围的驾驭层，并持续迭代。

但随之而来一个更深层的问题：如果模型不断变强，今天的驾驭层最终是否会被模型吸收？在《苦涩的教训》中，Rich Sutton 回顾了贯穿七十年 AI 研究的一种反复出现的模式[^ch1-1]：研究者一再将自己对某个领域的理解编码进系统，获得短期收益，但最终败给了能随算力和数据规模扩展的通用方法——搜索和学习。从这个视角来看，驾驭层中的约束、验证和纠正，有多少是模型注定要内化的"人类先验"？**本书认为模型将越来越多地吸收这些能力，但我们也应务实看待这一过程发生的速度。** 在方向上，我们毫不怀疑模型会持续吸收驾驭层的一部分——工具调用和长程规划曾经依赖外部编排，如今已是模型的原生能力。然而在实践中，这种吸收远比直觉所预期的缓慢：训练以月为单位推进，没有哪个模型能在单次训练中内化真实企业的所有约束和偏好。模型当前的能力边界，正是驾驭层创造价值的地方。因此，驾驭层工程不是对苦涩教训的抵抗，而是将其落实在工程时间尺度上：凡是模型尚不能可靠完成的事情，驾驭层先行覆盖；每当模型内化了又一层能力，驾驭层便卸下那一层，转而支撑下一个能力前沿。

[^ch1-1]: Sutton, Rich. "The Bitter Lesson", 2019. http://www.incompleteideas.net/IncIdeas/BitterLesson.html

#### 智能体学习机制：从上下文自适应到持久化更新

前面的讨论指出，模型可以通过强化学习将工具使用策略内化为原生能力。但智能体的行为变化并不只发生在训练期间。根据更新发生的位置以及持续时间，这些变化可以理解为三条互补的路径（图 1-2）：任务内的上下文自适应、跨任务的外部工件更新、以及训练循环中的参数更新。

![图 1-2：智能体能力更新的三个层次](images/fig1-2.svg)

**上下文自适应**发生在当前任务内。一旦示例、状态和检索结果进入上下文，模型可以立即调整其行为，但这不会改变下一个会话的持久状态。其优势是速度快、成本低；其局限则来自上下文窗口和信息组织方式。第 2 章将详细阐述这种自适应形式的工作原理。

为了使变化跨任务持久化，系统可以更新**外部工件**：事实和经验可以组织成知识文档，可用语言表达的策略可以写入提示词或 Skill，确定性流程和约束可以编码在程序和驾驭层中。这些工件可审计、可修订，但智能体在执行时仍必须通过上下文或工具接口来访问它们。第 3 至 5 章为知识和程序奠定基础，第 9 章则讨论如何从经过评估的运行轨迹中生成此类更新。

当目标是一种高维能力——例如医学影像理解、自然语言风格，或隐式决策策略——外部规则无法完全表达时，就必须通过后训练更新**模型参数**。参数更新的部署成本更高，但可以产生自然且广泛泛化的效果；第 8 章将系统介绍其方法。因此，这三条路径并非互斥的类别，而是运行在不同时间尺度上的协同机制：上下文支持即时自适应，外部工件支持受控积累，参数则内化难以显式表达的能力。

### 上下文：智能体的工作集

上下文是智能体在每个决策点可用的信息工作集。正如一个人做决策时需要桌上有合适的材料——任务指令、参考手册、之前的往来邮件、最新数据——智能体的上下文窗口就是它可以使用的信息。从 API 的角度来看（详见第 2 章），每次 LLM 调用的上下文由五个部分组成：

- **系统提示词**：与用户在对话中输入的提示词不同，系统提示词由开发者编写，在整个对话过程中保持固定。它是智能体的"职位描述"——定义其身份、权限和行为准则。对系统提示词进行精心的提示工程，正是我们塑造智能体运行行为的方式。系统提示词还承载着跨会话持久化的**用户记忆**（个性化信息，如偏好、过往行为和背景设置；见第 3 章），以及动态注入的环境状态。
- **工具定义**：声明智能体可用工具的名称、功能描述和参数格式。没有工具定义，智能体无法识别或调用任何工具——不过它也不会一言不发——一项消融实验（实验 1-1）将展示它会转而做什么。工具定义与系统提示词共同构成在整个对话中保持不变的**静态前缀**。（这是基础模式；自 2026 年起，生产框架也可以在上下文末尾按需加载完整的工具 schema 而不破坏前缀——见第 2 章的工具定义一节和第 4 章。）
- **用户消息**：来自用户的输入。用户消息还可以包含通过 RAG（检索增强生成，详见第 3 章）动态检索的**外部知识**——涵盖超出训练数据截止日期的信息或私有领域知识。
- **助手消息**：模型之前生成的响应，最多可包含三个部分——`reasoning`（内部思维链，保持连贯性和决策可解释性）、`content`（对用户的回答）和 `tool_calls`（智能体采取行动的方式）。在一次具体的响应中，这三个部分不一定同时出现：例如，当智能体决定调用工具时，通常只有 `reasoning` + `tool_calls`；当给出最终答案时，通常只有 `reasoning` + `content`。
- **工具结果**：智能体框架执行工具后返回的输出。这些结果是智能体下一步推理的直接依据——也是让它能从结果中学习而非重复犯错的原因。

前两项（系统提示词 + 工具定义）构成静态前缀；后三项（用户消息 + 助手消息 + 工具结果）构成随每次交互不断增长的动态消息历史。这五个部分共同组成每次 LLM 推理的上下文。

每个组件都真的不可或缺吗？最直接的检验方式是**消融实验**——逐一排除原因的诊断方法：去掉组件 A，看看系统是否还能工作，然后去掉组件 B，依此类推，直到每个组件的贡献都清晰明了。实验 1-1 正是将这种方法应用于上述五个组件。

> **实验 1-1 ★★：上下文的关键作用**
>
> 我们通过系统的**消融实验**探究了每个上下文组件如何塑造智能体行为。上述五个组件中，测试了四个——系统提示词作为智能体的基础身份定义，被豁免：没有它，智能体完全没有角色意识，测试将毫无意义。如图 1-3 所示，实验设置了五个对照组：一个保留所有组件的完整基线组，以及四个各缺少一个组件的组，以观察每个组件对智能体性能的影响。
>
> ![图 1-3：实验 1-1——上下文消融实验设计](images/fig1-3.svg)
>
> 实验结果揭示了每个上下文组件的作用——以及它们的重要性并不相同。**工具定义**（静态前缀的一部分）是智能体行动能力的基础；没有它们，智能体无法调用任何工具。但失去行动能力并不意味着沉默：模型仍然会返回格式整洁、措辞自信的回答，其中的数字来自参数化记忆而非观察所得，排版方式与真正从工具输出推导出的答案如出一辙。它是直接拒绝还是当场编造，主要取决于模型自身的幻觉率和诚实程度；提示词中诸如"不要自行估算比率"这样的约束可以降低编造概率，但无法杜绝。**工具结果**是闭环控制的关键；没有它们，智能体就是在"盲跑"，不断重试直至耗尽迭代预算。**推理过程**（助手消息中的推理部分）记录了*为什么*要执行某个步骤，而工具结果记录了*发生了什么*；当后者可以重构出前者时，将其从历史中移除几乎不产生任何损失。**消息历史**（之前轮次的用户消息、助手消息和工具结果）防止冗余操作，避免重复同样的错误。
>
> 实验的核心洞见：**上下文决定了智能体能"看到"什么，而智能体只能基于它看到的东西做决策。** 但各个组件并非等价；衡量标准是其承载的信息能否从别处重构——"每个组件都不可或缺"这类说法必须经过测量而非假设，而且模型迭代速度很快，同样的消融在更新的模型上很可能得出不同结论。还有一点在工程实践中更为重要：**"产出了答案"不等于"完成了任务"。** 当缺失某个上下文组件时，典型的失败不是错误退出，而是一个看起来无懈可击的答案。

### 推理-行动循环

掌握了这三个组件，一个自然的问题随之而来：它们如何协同工作？推理-行动循环是将 LLM、上下文和工具连接成一个系统的核心机制。我们来逐步剖析它。

智能体执行任务的核心模式称为**推理-行动**（Reasoning + Acting）。这个名字只提到了推理和行动，但实际的循环有三个阶段：模型首先**推理**接下来该做什么，然后调用工具进行**行动**，接着**观察**工具结果并推理下一步。这个"推理 → 行动 → 观察 → 推理 → 行动 → 观察"的循环不断重复，直到任务完成。

考虑一个具体例子——跨多种货币汇总收入——来理解智能体的**轨迹**：智能体工作过程中累积的消息历史，由用户消息、助手消息（含其推理和工具调用）以及工具结果组成。在每次 LLM 调用中，模型接收到的完整上下文是**静态前缀**（系统提示词 + 工具定义）加上**轨迹**（动态消息历史）（图 1-4）。这揭示了一个关键事实：**智能体上下文 = 静态前缀 + 轨迹**。具体而言，静态前缀是上述五个组件中的前两个（系统提示词 + 工具定义）；轨迹是后三个（用户消息 + 助手消息 + 工具结果，随每次交互增长）。LLM 从这个完整上下文中生成下一个响应，然后将其追加到轨迹中以供后续调用使用。

![图 1-4：智能体轨迹——多币种汇总任务的推理-行动循环](images/fig1-4.svg)

先看一个最小化的循环实现。它展示了**各组件如何协同工作**：模型只负责决定下一步，驾驭层负责组装上下文并验证和执行工具，环境负责产生实际的状态变更和观察结果。本书其余部分同样使用 Python 风格的伪代码；伪代码不可运行，也不对应任何特定的 SDK。可执行的具体代码在本书的配套仓库中。

```python
trajectory = [user_request]

repeat:
    context = stable_prefix + trajectory
    decision = Model(context)
    trajectory.append(decision)

    if decision has no tool call:
        return decision.answer

    for call in decision.tool_calls:       # independent calls may run in parallel
        validated_call = Harness.validate(call)
        observation = Environment.execute(validated_call)
        trajectory.append(observation)
```

以下是轨迹的结构，以伪代码表示：

```text
trajectory = [
  {role: "user", content: "Based on the company's quarterly revenue: Q1 2.5M USD, Q2 2.1M EUR, Q3 1.8M GBP, Q4 380M JPY, calculate the company's total annual revenue and average quarterly revenue"},
  
  # First iteration - LLM receives the above trajectory and generates a response
  {role: "assistant",
   reasoning: "Need to convert all currencies to USD...",
   content: "",  # No direct reply to the user
   tool_calls: [
     {name: "convert_currency", args: {amount: 2100000, from: "EUR", to: "USD"}},
     {name: "convert_currency", args: {amount: 1800000, from: "GBP", to: "USD"}},
     {name: "convert_currency", args: {amount: 380000000, from: "JPY", to: "USD"}}
   ]},
  
  # Agent framework executes tools, adds results to trajectory
  {role: "tool", content: "EUR->USD: 2282608.7"},
  {role: "tool", content: "GBP->USD: 2278481.01"},
  {role: "tool", content: "JPY->USD: 2541806.02"},
  
  # Second iteration - LLM receives the complete trajectory, including tool results
  {role: "assistant",
   reasoning: "Conversion results obtained, now need to aggregate and calculate...",
   content: "",
   tool_calls: [
     {name: "code_interpreter", args: {code: "total = 2500000 + 2282608.7 + ..."}}
   ]},
  
  {role: "tool", content: "Total: $9,602,895.73, Average: $2,400,723.93..."},
  
  # Third iteration - LLM receives the complete trajectory and generates the final answer
  {role: "assistant",
   reasoning: "All calculations complete, summarizing results...",
   content: "FINAL ANSWER: Total revenue $9,602,895.73..."}
]
```

请注意，系统提示词和工具定义并未出现在轨迹中——它们作为静态前缀，在每次 LLM 调用前自动拼接在轨迹之前。

在我们的实验中，这个循环清晰可见。第一轮，智能体分析任务并并行调用了三个货币转换工具；第二轮，它将转换结果交给代码解释器进行计算量更大的运算；第三轮，在确认所有计算完成后，它产出了最终答案。一个复杂的多步任务在 3 次迭代和 4 次工具调用中完成。

在这种最基础的设计中，LLM 看到的上下文是不断追加的。每次 LLM 调用都收到完整的轨迹，因此模型知道自己处于任务的哪个阶段、之前尝试过什么、结果如何。正如人们在解决问题时不断回顾和总结，智能体通过轨迹保持对任务的全局视野。而且由于轨迹是结构化的——用户消息、助手消息（推理 + 工具调用）和工具结果被清晰地分离——系统具有高度的可解释性和可调试性。

了解了智能体的运行循环后，我们接下来看两个实验，观察不同模型如何驱动这个循环。

> **实验 1-2 ★：Kimi K3 的原生智能体能力**
>
> 本实验展示了 **Kimi K3** 的原生智能体能力，它是"模型即智能体"范式的一个范例。Kimi K3 是一个混合专家（MoE）模型，参数量约为 2.8 万亿。MoE 可以看作一个专家团队：对于每类问题，系统只激活最适合的少数专家，而非整个模型，从而在保留能力的同时不承担完整的效率开销。Kimi K3 拥有 100 万词元的上下文窗口、原生视觉理解能力以及始终开启的"思考模式"。通过强化学习，它将工具调用的**决策策略**内化为原生能力：何时调用工具、调用哪个工具、传入什么参数，全部由模型自身决定，使其能够自主执行诸如网络搜索等任务。严格来说，被内化的是*何时以及如何调用*的决策；工具本身（如 `web_search` 和 `code_runner`）仍然作为 API 级别的内置工具在服务端执行。Kimi 通过一个名为 Formula 的服务端脚本引擎来运行这些官方工具。
>
> 关键观察在于：模型自主决定何时搜索、搜索什么，展现出真正的自主性；随着搜索结果返回，它会调整策略并判断信息是否充分。有一个常见的误解需要澄清：**强化学习赋予模型的是决策策略**，而非工具本身。它教会模型何时调用工具、选择哪个工具、传入什么参数、收到结果后是否继续，以及如何将数十甚至数百次调用串联成连贯的推理；这些*是否使用以及如何使用*的判断才被写入模型的权重。**工具及其执行由智能体框架或 API 内置提供**：`web_search` 和 `code_runner` 的实现、代码沙箱、以及发出调用和返回结果的基础设施全部位于模型之外。强化学习优化的是决策策略；它不会把搜索引擎或代码沙箱嵌入模型的权重中。因此，编排循环并未消失；它从客户端移到了服务端，而决策权则移入了模型内部[^ch1-2]。
>
> [^ch1-2]: 感谢读者 asdlem 通过 GitHub Issue #30 指出并澄清了这一区别：强化学习内化的是工具调用的决策策略，而非工具执行机制。参见 https://github.com/bojieli/ai-agent-book/issues/30
>
> Kimi K3 在智能体任务中的显著优势在于**长链工具调用的稳定性**——它能够维持 200 至 300 次连续工具调用，并始终保持连贯的推理，远超大多数模型在几十次调用后就开始退化的水平。K3 针对长周期编程和智能体工作负载进行了优化，发布了两个变体：K3 Max（用于对话和智能体任务）和 K3 Swarm Max（用于大规模并行处理）。作为一个开源模型，它在软件工程和智能体基准测试中与顶级闭源系统相匹衡——这证明了强化学习能够赋予模型原生的智能体能力。
>
> **实验 1-3 ★：GPT-5.6 的原生深度研究能力**
>
> 第二个实验使用 **OpenAI GPT-5.6** 来展示一个先进的模型如何借助 API 级别内置工具，在服务端为深度研究（Deep Research）闭合"搜索—阅读—分析"编排循环。GPT-5.6 有一个便利的特性是**自由格式工具调用（Freeform Tool Calling）**。传统上，模型调用工具时必须将每个参数序列化为严格的 JSON（一种结构化数据格式），就像按照僵硬的格式规则填写表格。自由格式工具调用（在 API 中通过 `type: "custom"` 的工具声明）允许模型直接向工具发送原始文本（如一段 Python 代码、一条 SQL 查询），完全避免了 JSON 转义。需要强调的是，这是 API 参数格式的演进，而非模型架构上的创新——客户端的工具调用循环（检测 `tool_calls` → 执行 → 返回结果）保持不变；只有参数从 JSON 字符串变为原始文本。
>
> GPT-5.6 配合 Responses API 的**网页搜索和代码解释器**内置工具，实现了深度研究的核心机制：模型可以自主搜索网络获取实时信息，并编写代码进行深入分析，实现"搜索 → 阅读 → 分析 → 再次搜索"的迭代研究过程。例如，面对"东盟十国首都之间的最短距离是多少？"这样的问题，GPT-5.6 会自动搜索每个首都的地理坐标，然后编写 Python 代码计算所有首都两两之间的大圆距离，最终找出距离最近的一对。类似地，在"搜索比特币过去一个月的走势并进行技术分析"这样的任务中，它可以从多个金融数据源获取实时价格数据，利用专业技术分析库计算移动平均线、RSI、MACD 等技术指标，生成可视化图表，并给出交易建议。
>
> 更重要的是，GPT-5.6 在模型层面内化了 **OpenAI Deep Research** 产品的设计理念，引入了**意图澄清流程**。面对研究请求，GPT-5.6 不会立即开始执行；它会先通过一系列问题澄清用户的真实意图。对于"搜索比特币过去一个月的走势并进行技术分析"，它会先问："您偏好哪个数据源？您希望分析哪些技术指标？"这种交互式澄清使 GPT-5.6 能够产出更精准、更符合用户实际需求的研究报告。
>
> GPT-5.6 是"模型即智能体"的成熟范例——网页搜索、代码解释器等 Responses API 内置工具在服务端闭环执行；编排循环从客户端移至 API 服务器，简化了客户端实现。模型仍然输出标准的工具调用；只是客户端不再需要自行构建"搜索—阅读—分析"编排框架。最值得注意的是其意图澄清机制：模型不是立即执行任务，而是先确认用户真正需要什么，再制定研究策略。"用户说了什么"与"用户实际想要什么"之间的鸿沟在执行开始之前就被弥合了。
>
> 需要说明的是，本实验不绑定于任何特定厂商。没有 OpenAI 额度的读者可以用提供等效托管工具的服务商复现。例如，阿里云百炼的 qwen3.7-plus Responses API 同样包含内置的 `web_search` 和 `code_interpreter`；Kimi K3 由 Formula 管理的搜索和 `code_runner` 提供同类能力。

## 驾驭层工程：围绕模型构建可靠系统

至此，你已经理解了智能体的核心工作方式：大语言模型运行推理-行动循环，由上下文引导，使用工具完成任务。上面的实验表明基本机制是可行的——同时也暴露了它有多么脆弱。模型可能产生幻觉（捏造不存在的工具或参数）、选错工具，或无法从错误中恢复。一个可运行的演示与一个可靠的产品之间存在相当大的差距，而这些脆弱性正是驾驭层工程所要解决的问题。本章前半部分回答了智能体是什么；后半部分回答的是智能体如何在生产环境中可靠运行。

前文确立了核心公式：**智能体 = 大语言模型 + 上下文 + 工具**。它描述了智能体的**内部构成**：推理引擎、工作上下文和动作接口。驾驭层工程为同一系统提供了第二个、**实现层面**的视角：将大语言模型视为一个核心组件（模型），将围绕它构建的所有支撑代码统称为驾驭层。两个视角并非对立，而是从不同抽象层次描述同一个系统。我们改用更通用的"模型"一词，是因为驾驭层工程的原理适用于任何能够推理和调用工具的模型，而非某一特定类型。驾驭层的核心是原公式中的"上下文 + 工具"，再加上三层保障：**约束**（智能体可以和不可以做什么）、**验证**（它是否正确完成了任务）、**纠正**（当它做错时如何恢复）。

展开为等式，完整的生产级构成为：

> **智能体 = 模型 + 驾驭层**
>
> **驾驭层 = 上下文管理 + 工具接口 + 约束 + 验证 + 纠正**
>
> **智能体 ↔ 环境**

最小的演示只需要一个模型和一个能够构建上下文、暴露工具的驾驭层；生产系统则必须在同一边界内增加约束、验证和纠正。例如，一个退款智能体可以将政策放入上下文，用权限和金额规则约束调用，对照数据库状态验证结果，并在超时后重试或回退。驾驭层工程研究的正是这些运行时和治理代码——位于模型之外，但在智能体边界之内。

更精确地说，驾驭层并非模型之外的所有东西：它是**位于智能体边界内、模型之外**的运行时和治理层。它介导模型与环境的交互，但不包括环境本身。工具定义、调用适配器、沙箱权限和重置机制属于驾驭层；沙箱内发生变化的文件和进程、外部数据库、网页、用户以及物理世界属于环境。部署位置不改变这一概念边界。驾驭层的核心是上下文管理和工具接口，围绕它们构建了三类工程保障：

| 组件 | 职责与设计原则 | 实际示例 | 参见章节 |
|---|---|---|---|
| **上下文管理** | 提供相关信息。**信息充分性：**在每一步给智能体足够的信息以做出明智决策。 | 系统提示词、知识库、智能体状态栏、Sidecar 旁路查询 | 第 2、3 章 |
| **工具接口** | 定义模型如何行动。**清晰的接口：**使用直观的工具名称，提供参数示例，说明每个工具的限制。 | MCP 工具、代码解释器、搜索工具 | 第 4 章 |
| **约束** | 定义智能体被允许做什么。**安全默认值：**能力默认关闭，直到显式启用，类似于移动应用权限。 | Claude Code 默认要求用户授权后才执行工具。 | 第 4 章 |
| **验证** | 检查工具执行是否产生了正确结果。**输入隔离：**基于结构化数据进行安全检查，例如工具返回的字段，而非模型生成的文本——后者可能被攻击者通过提示注入影响。 | Lint 检查、类型检查、工具结果校验 | 第 5、6 章 |
| **纠正** | 从错误中恢复或回滚失败的操作。在向用户呈现失败之前先尝试恢复——例如，重试失败的工具调用，而不是展示不完整的结果。 | 自动重试、恢复生成、多次失败后升级给人工处理（熔断机制） | 第 2、5 章 |

基本的模型控制循环如下方伪代码所示：

```python
observation = Environment.observe()
trajectory = [observation]
while true:
	actions = Model(Harness.build_context(trajectory))
	if len(actions) == 0:
		break
	allowed_actions = Harness.constrain(actions)
	observation = Environment.apply(allowed_actions)
	if not Harness.verify(Environment):
		observation = Harness.correct(Environment)
	trajectory.append(allowed_actions, observation)
```

该框架刻意省略了实现细节。完整的 API 消息循环见第 2 章；工具和自动验证分别在第 4 章和第 5 章中介绍。

上下文和工具让智能体能够完成任务——理解任务并采取行动。约束、验证和纠正确保它可靠且安全地完成任务——它们不是上下文和工具之外的附加物，而是让它们在生产环境中可靠运行的工程手段。在智能体产品的成熟度曲线上，这两组要素之间的重心会逐渐转移。

早期的智能体框架侧重于上下文和工具：给模型工具，给它上下文，让它完成任务。生产级系统已经将重心转移到约束、验证和纠正上：确保工具调用是安全的、上下文是被管理的、错误是可恢复的。

以 Claude Code 为例。其驾驭层代码的绝大多数属于约束、验证和纠正，而非上下文和工具——工具本身（文件读写、命令执行、搜索）只占很小一部分；围绕它们构建的保障机制才是真正的核心。这些机制包括：

- **进程状态管理**：跟踪智能体当前正在执行哪一步
- **多层上下文压缩**：信息过多时自动裁剪
- **权限分类**：控制哪些操作需要用户确认
- **熔断器**：重复出错后自动停止重试，防止单个失败的操作级联到整个系统
- **错误恢复机制**：捕获异常，回滚到最近的稳定状态，重试，或交由人工处理

**行业正从任务完成转向可靠的任务完成，这使得驾驭层工程成为智能体系统的核心竞争优势。**

### 从提示工程到循环工程：工程范式的演进

回顾 AI 应用工程的发展历程，一条清晰的演进脉络浮现出来：

**提示工程**是第一波创新——通过改进输入模型的自然语言指令来提升输出质量。

**上下文工程**是第二波——人们认识到仅优化提示词是不够的：模型能看到的所有信息（系统指令、工具定义、对话历史、外部知识）都需要系统化管理。

**驾驭层工程**是第三波——它将视野从"模型接收到什么信息"扩展到"模型运行在什么样的系统中"，纳入模型之外的所有基础设施：约束机制、验证方法、反馈循环、错误恢复。

**循环工程**接踵而至，将视野从单次运行扩展到跨运行的持续自主运行：谁来发现下一项工作、何时验证、以及任务何时才算真正完成（第 10 章与多智能体协作系统一起展开讨论）。

2026 年 7 月，业界开始使用**图工程（Graph Engineering）**这一更高层次的编排视角：将智能体循环、确定性程序和人工审批组织成显式执行图，其中节点提供能力，边定义路由和依赖，结构化状态沿这些边传递，并在关键边界处持久化[^ch1-graph-engineering]。

[^ch1-graph-engineering]: Josh C. Simmons 在其 2026 年 7 月 4 日的文章 *We Are Entering the Graph Engineering Phase* 中明确使用了这一名称，并以节点、带类型的边和检查点状态加以概括。7 月 18 日，Peter Steinberger 关于讨论是否已从循环转向图的提问进一步推动了该名称的传播。这些实践先于该标签出现：LangGraph、Microsoft Agent Framework 和 Google ADK 的官方文档都将它们描述为图编排或基于图的工作流。参见 https://www.drjoshcsimmons.com/writing/we-are-entering-the-graph-engineering-phase、https://x.com/steipete/status/2078277297791189132、https://docs.langchain.com/oss/python/langgraph/overview、https://learn.microsoft.com/en-us/agent-framework/workflows/ 和 https://adk.dev/workflows/。

这五个阶段并非相互替代，而是层层嵌套：提示工程是上下文工程的子集，上下文工程是驾驭层工程的子集，驾驭层工程是循环工程的子集。循环工程又是图工程的子集：单个智能体循环构成执行图中的一个节点。每一层都将工程师的关注范围和影响力扩展到上一层之外。**当模型能力趋于趋同、不再成为决定性的差异化因素时，竞争优势便转移到模型之外的工程上。**

近期的工程实践印证了这一观点。LangChain 在 Terminal Bench 2.0（一个评估智能体在终端环境中完成复杂任务能力的基准测试）上的工作就是一个引人注目的例子：他们的编码智能体从 52.8% 提升到 66.5%（从榜单 30 名开外跃升至前 5）。改变的不是模型，而是驾驭层——让智能体检查自身的执行结果、检测是否陷入重复循环，并优化推理策略。

### 构建高效智能体的核心原则

基于 Anthropic 的经验，成功的智能体系统遵循三个核心原则[^ch1-anthropic-building-effective-agents]。

**保持简洁。** 从最简单的方案开始，仅在真正必要时才增加复杂度。直接的 API 调用优于复杂的框架；清晰的代码优于精巧的抽象——每多一层抽象，调试时就多一个盲区。

**保持透明。** 清晰展示智能体的规划步骤、执行日志和决策轨迹。这不仅是调试的便利，更是用户信任的前提——黑盒中的错误很难从外部定位或修复。

**设计结构良好的工具接口（ACI，智能体-计算机接口）。** ACI 意味着从智能体的视角设计接口——让智能体易于理解和使用——而不是像传统 API 那样从程序员的视角出发。工具名称和参数应当直观，在容易误用的地方，设计应使错误从一开始就不可能发生：SIM 卡的缺角使其只能以一个方向插入卡托，微波炉门打开时拒绝加热。在制造业中，这种方法被称为 **poka-yoke（防呆法）** 或 **防错（mistake-proofing）**：通过设计产品和流程来防止错误，或使错误立即可见。丰田生产体系中就采用了这一方法[^ch1-poka-yoke]。设计不当的工具即使是能力最强的模型也会反复失败：接口是模型与工具之间唯一的通道，含糊的接口会被放大为系统性错误。

[^ch1-poka-yoke]: Toyota UK，["Poka-yoke – Toyota Production System guide"](https://mag.toyota.co.co.uk/poka-yoke/)；American Society for Quality (ASQ)，["What Is Mistake Proofing?"](https://asq.org/quality-resources/mistake-proofing)。两者都将防错描述为防止错误发生或在错误出现时立即检测到。

[^ch1-anthropic-building-effective-agents]: Anthropic. "Building effective agents", 2024 年 12 月。https://www.anthropic.com/engineering/building-effective-agents

接下来的三节讨论驾驭层工程中三个独立但重要的话题：模型选择、编排模式以及安全护栏与安全性。它们都不属于驾驭层的五个核心要素，但在工程实践中都是无法回避的。

### 如何选择模型

在讨论编排模式之前，我们首先需要回答一个实际问题：应该用什么样的模型来驱动你的智能体？

模型是智能体智力的基础，选对模型往往比任何提示词调优都更重要。模型迭代太快，具体版本推荐很快就会过时，因此本节只给出方向性建议。

**闭源模型。** 当前智能体开发中最常用的两个闭源模型提供商是 OpenAI（GPT/o 系列）和 Anthropic（Claude 系列）。闭源模型通常能力领先，但价格更高，且受供应商 API 政策约束。选择模型时，不要仅依赖排行榜；**在你自己的任务上进行评估**（参见第 7 章）。

**开源模型。** 在撰写本书时，开源模型与闭源模型的差距不超过六个月，而成本却低得多。如果你的业务场景不要求最高的模型能力，开源模型是务实之选。开源模型成本低、支持私有化部署、允许微调定制，适合成本敏感或有数据合规要求的场景。DeepSeek、Kimi 和 GLM 是智能体能力较强的国产模型。需要注意的是，各模型在工具调用能力上差异较大，务必在你的具体场景中先测试再做决定。

**除了能力，还要考虑模型的策略边界。** 模型可能在技术上具备执行某项任务的能力，但托管它的产品未必允许用户调用该能力。不同厂商在网络安全、模型蒸馏、模型提取、私有数据和高风险操作等方面划定了不同的策略边界；同一任务在聊天产品、编码智能体 [待审] 和 API 中也可能产生不同的结果。因此，模型选型不能只比较准确率、价格和速度。应在真实任务上测试：模型是否愿意执行、接口是否暴露了所需能力、服务条款是否允许预期的使用方式。对于业务关键任务，要准备好人工交接 [待审] 或另一个合规模型作为兜底。

**大多数智能体需要支持推理的模型。** 智能体需要做出复杂决策——多步推理、工具选择——没有推理能力的模型在这些任务上往往表现不佳。例外很少：单个简单步骤，或者 Computer Use 中等同于点击固定位置的 GUI 操作，非推理模型 [待审] 或许够用。一旦涉及多步推理或动态决策，推理模型就不可或缺。

**关注输出速度和多模态能力。** 除了成本，有两个维度容易被忽视。其一是**词元输出速度**：智能体通常需要运行多轮推理，每一轮必须完成才能开始下一轮，因此输出速度直接决定了端到端时延——一个 20 轮的智能体任务如果每轮慢 2 秒，就意味着多等 40 秒。其二是**多模态 [待审] 支持**：如果你的智能体需要理解图像、音频或视频，多模态能力就是硬性要求，而各模型在这方面差异很大。

### 编排模式 [待审]：工作流 vs. 自主智能体

编排模式描述了驾驭层如何组织其"上下文与工具"层——它们决定了上下文如何在 LLM 调用之间流动、工具如何被调度，以及智能体的执行路径是预先固定的还是动态生成的。智能体编排已经从简单发展到复杂，每种模式都有其适用场景和权衡。根据 Anthropic 与数十个构建 LLM 智能体的团队合作的经验[^ch1-anthropic-building-effective-agents]，最成功的实现很少使用复杂框架；它们使用的是简单、可组合的模式。

构建 LLM 应用时，遵循从简到繁的原则。首先考虑单次 LLM 调用。如果更好的提示词和上下文内示例 [待审] 就能解决问题，就不要引入智能体系统。当需要多步处理时，对于能够清晰分解为固定子任务的场景，考虑使用工作流。只有在需要动态决策和灵活执行路径时，才使用自主智能体。记住，智能体系统通常以时延和成本换取更好的任务表现，因此要仔细权衡这种交换是否值得。

一个常见的反面案例是：一上来就构建一个高度复杂的工作流或多智能体系统。例如，当被要求设计一个"从百万条聊天消息中提取个人记忆"的智能体时，某些 AI 模型会迅速画出一个看似严谨的流水线：先对对话进行分段，然后依次分配提取、证据验证、身份解析、记忆整理和合并审查等智能体，最后构建事实图谱、覆盖账本和不可变版本。每个组件单独看都有道理，但合在一起却形成了一个低效且不可靠的系统。因为复杂工作流的执行拓扑是固定的，每个新异常都容易催生一个新的节点：架构变得越来越复杂，通用性却越来越差。本可以由模型从上下文做出的语义判断，反而被硬编码到了工作流中。

因此，**驾驭层的重要性并不意味着驾驭层越复杂越好**。Manus 网站将这种权衡总结为"更少结构，更多智能"。[^ch1-manus-less-structure] 首先给一个有能力的智能体一个清晰的目标、必要的上下文和可组合的工具，用自然语言告诉它人会如何验证证据、做比较、解决冲突。程序只需硬编码必须始终成立的边界，例如权限、绝不覆盖源材料、原子化发布 [待审]。只有当业务约束本身就要求如此，或评估反复暴露稳定的失败模式时，才应将对应步骤提升为专门的验证器、独立的智能体或确定性流程。好的结构不会替智能体预演所有的思考；它守住了边界，并将边界内的决策空间交还给模型。

[^ch1-manus-less-structure]: Manus, "Less structure, more intelligence." https://manus.im/

#### 工作流模式：确定性编排

**工作流**是通过预定义的代码路径来编排 LLM 和工具的系统。其执行路径是确定性的，由开发者预先设计——每个步骤和转换的行为都在代码中定义；LLM 只负责每个节点内部的理解和生成。

例如，一个机票预订智能体可以使用包含四个固定节点的工作流：

1.  **验证用户身份**——调用身份验证 API，确认用户身份。
2.  **搜索可用航班**——根据用户需求查询航班数据库。
3.  **完成支付**——调用支付接口扣除金额。
4.  **确认预订**——调用预订 API 锁定座位，并向用户发送确认。

每个节点内部可以使用 LLM（例如用自然语言理解用户的出行需求），但节点之间的流程顺序由代码固定——系统不会在支付完成之前预订座位，也不会在身份验证之前开始搜索航班。

工作流模式有两个核心优势。第一，**严格的流程控制**：开发者可以保证关键步骤绝不会被跳过或乱序执行——"未支付不得预订"这样的业务规则由代码强制执行，而非依赖 LLM 的判断。第二，**安全性**：由于执行路径是确定性的，提示注入或模型错误最多只能影响当前节点内部的处理，无法让智能体跳转到不应到达的分支。攻击面被限制在单个节点内。

工作流的主要局限是**缺乏灵活性**。当出现预料之外的事件——例如用户在支付过程中更改预订，或航班取消需要推荐替代方案——固定路径无法自行适应，只能走预设的异常分支或将控制权交还给人工。

以最简单的工作流示例来看：**文本生成图像**。用户的需求通常是一句朴素的自然语言，比如"画一幅 AGI 实现后程序员工作的场景"；但像 Stable Diffusion 这样的文生图模型只接受特定风格的提示词——以逗号分隔的英文标签、质量词、负面提示词 [待审]。因此，工作流在用户和图像生成模型之间插入两个固定节点：

1.  **提示词改写**——用 LLM 将用户的自然语言请求改写为文生图模型期望的提示词格式。就上面的例子而言，"AGI 实现后程序员工作"是一个非常宽泛的需求，因此 LLM 还需要仔细推敲（例如"AGI 实现后，程序员不再需要写代码，所以画面应该是一个程序员在沙滩上晒太阳，通过脑机接口指挥 AI 员工"），然后产出具体的场景描述。
2.  **图像生成**——用改写后的提示词调用文生图模型，获取图像。

执行路径是硬编码的。这个工作流中的 LLM 节点执行的是**翻译**——将人类语言转换为工具可以理解的输入格式——它之所以存在，是因为文生图模型"听不懂大白话"。专门修补工具（或模型）能力短板的驾驭层代码，可以称为**适配层** [待审]。

但如果图像生成工具被替换为具备**原生图像生成**能力的多模态模型，例如 Nano Banana 2 或 GPT-Image 2，提示词改写就不再需要了。无论用户如何表达需求，模型都能自行理解并直接生成图像。

> **实验 1-4 ★：文生图工作流 vs. 原生图像生成**
>
> 通过两条路径发送同一句自然语言请求。**工作流路径**：先由 LLM 将请求改写为 Stable Diffusion 风格的提示词，再调用文生图模型生成图像；**原生路径**：将原句直接发送给支持原生图像生成的多模态模型（如 GPT-Image 2），一次调用即产出图像。
>
> 比较两件事：提示词改写节点将原始请求变成了什么，以及哪条路径的图像更接近原始请求。值得比较两类请求：一类是具体的（例如带有指定文案的海报），另一类是宽泛的（如上面的 AGI 工作场景）——对于后一类，工作流路径可能仍有其自身的优势。

这一实验表明，**驾驭层中修补模型能力短板的部分，会随着模型变强而被模型自身所内化**。仅在本章中，这种情况就已多次发生：少样本示例 [待审] 和"让我们一步步思考"之类的提示词技巧被指令微调 [待审] 和推理模型内化；输出格式修复和 JSON 解析容错被结构化输出和原生工具调用内化；文生图的提示词改写则被模型的原生多模态理解与生成能力所吸收。每一轮内化，都会淘汰一类"翻译"和"脚手架"式的适配层代码。

#### 自主智能体：运行时决策

当工作流的固定路径不够用时，我们需要**自主智能体**。自主智能体与工作流的核心区别在于：执行路径不是预先定义的，而是在运行时由智能体根据**环境反馈**动态决定的。

回到机票预订的例子，自主智能体不需要四个预定义节点。用户说"帮我订下周三去上海的机票"，智能体动态决定执行顺序：它先搜索航班，发现需要登录，于是先进行身份验证，然后继续搜索。如果最便宜的航班需要中转，它可以询问用户是否接受；如果用户说不行，它就调整搜索条件。

因此，自主智能体必须自行规划——选择自己的执行步骤——并在遇到失败时识别问题、改变策略，而非在出错时简单地停止。但自主性并非无边界：必须设计明确的**停止条件**（任务完成、达到最大迭代次数、遇到不可恢复的错误），否则智能体可能陷入无限循环，或在任务已完成之后仍在继续执行。

从实现角度看，自主智能体本质上是一个在循环中使用工具的 LLM，不断获取环境反馈以推进任务——这就是前面介绍的推理-行动循环。常见的退出条件包括：调用最终输出工具、模型返回不含任何工具调用的响应、遇到错误或达到最大轮数。

![图 1-6：自主智能体的执行循环](images/fig1-6.svg)

自主智能体非常适合开放式问题——即难以预测所需步骤数量的问题。典型用例包括：编码智能体解决 SWE-bench（软件工程基准，用于评估智能体自动修复真实 GitHub issue 能力的基准测试）任务、"Computer Use"智能体像人一样操作计算机界面，以及需要迭代搜索和分析的研究类任务。

自主性也意味着更高的成本，且错误容易累积。因此，部署自主智能体需要在沙盒中进行充分测试、设置适当的安全护栏和监控，并在关键决策点设置人在回路检查点。

#### 选择与混合两种模式

在实践中，工作流和自主智能体并非互斥——许多系统将两者混合使用：有严格合规要求的关键流程以工作流方式运行以保证可靠性，而需要灵活决策的部分则切换到自主模式。例如，n8n 是一个成熟的开源工作流自动化框架，开发者通过在可视化画布上排列功能组件来构建智能体——工作流节点和自主智能体节点可以在同一系统中共存。

![图 1-7：n8n 工作流编辑器界面](images/n8n-workflow.png)

另一种混合方式是**让自主智能体先编写工作流，再由工作流来执行**。智能体在读取任务后自行决定拓扑并生成一段编排代码；一旦代码生成，执行阶段就回归到工作流的确定性。这样既保留了自主智能体面对陌生任务时的灵活性，又避免了模型在每次派发时都要做决策。第 10 章将详细讨论这种形式。

### 安全护栏与安全

安全护栏实现了驾驭层的约束、验证和纠正机制，提供分层防御，确保智能体行为安全可控。设计良好的**安全护栏**有助于管理数据隐私风险（例如防止系统提示词泄露）和声誉风险（例如保持模型行为与品牌一致）。先针对已识别的风险部署安全护栏，再随着新漏洞的出现逐步补充。

将安全护栏视为纵深防御 [待审]。单一的安全护栏不太可能独自足够，但多个专门的安全护栏组合起来，能让智能体系统更具韧性。

安全护栏还有另一种失败模式：**误拒** [待审]。为了降低放行危险请求的概率，模型也可能拒绝合法但看似敏感的工作，例如授权安全测试或模型蒸馏研究。因此，安全护栏评估不仅要测试禁止性请求是否被拦截，还要测试明显允许的请求是否仍能完成。

#### 安全护栏的类型

安全护栏可以放置在三个层次：**上下文层、执行层和数据层**。这三个层次的排序不是按照它们在请求生命周期中的位置，而是按照**被绕过的难度**——层次越低，对模型自身判断的依赖越少，单次成功攻击就越难穿透。本书后续的安全讨论将围绕这个三层框架展开。

**上下文层**安全护栏管控**模型能看到什么内容**，在内容进入上下文之前进行拦截。它们通常包含四种机制。**相关性分类器**[待审]标记偏离主题的查询——比如向一个编程助手询问"帝国大厦有多高？"**安全分类器**[待审]检测越狱攻击[待审]（诱导模型绕过其安全限制）和提示注入（在输入中嵌入恶意指令）；关键区别在于，越狱是用户试图绕过模型自身的限制，而提示注入是攻击者通过网页或文档等外部数据间接操纵模型。**内容审核**[待审]标记有害或不当的输入，例如暴力或歧视性内容。**基于规则的防护**[待审]针对已知威胁（如 SQL 注入）应用确定性措施——黑名单、输入长度限制、正则表达式过滤器。来源标注以及"指令"与"数据"的分离也属于这一层；第2章将对此展开讨论。

Anthropic 的"宪法分类器"（Constitutional Classifiers）[待审]提供了基于分类器的安全护栏在实践中的一个范例[^ch1-3]。其设计包含三个关键要素。第一，**规则驱动训练**[待审]：使用指定允许和禁止内容的自然语言规则，为输入和输出分类器生成合成训练数据。第二，**联合上下文判断**[待审]：新一代分类器将用户的问题和模型的回答放在一起检查，因为有些回答单独看完全正常（例如"如何使用食品调味料"），但结合问题才能看出"食品调味料"其实是化学试剂的暗语。第三，**两阶段筛查**[待审]：一个极其轻量的探针[待审]——几乎零成本地读取模型的内部激活——首先检查每段对话，任何可疑内容都会升级到更强大的分类器进行审查，而非直接拒绝。这样第一阶段可以容忍更多的误报而不损害用户体验，同时大幅降低整体成本。

[^ch1-3]: Anthropic. "下一代宪法分类器：更高效地防御通用越狱攻击", 2026. https://www.anthropic.com/research/next-generation-constitutional-classifiers; 论文：Cunningham et al., "Constitutional Classifiers++: Efficient Production-Grade Defenses against Universal Jailbreaks", arXiv:2601.04603

但这一层存在结构性上限：**智能体无法可靠地判断提示注入是否已经污染了自己的上下文**。因此，上下文层可以降低攻击的成功率，但无法提供保证——这正是其下两层存在的必要性。

**执行层**安全护栏管控**模型能做什么**，在动作生效之前进行校验。其核心是**工具风险评级**[待审]：每个工具根据可逆性、权限级别和财务影响被标记为低、中、高风险，高风险操作需要额外审查或人工确认。关键在于，这项审查必须由**上下文之外**的机制执行——独立的审查流程、最小权限凭证、沙箱隔离、人在回路——否则同一次攻击可能同时破坏智能体及其防护措施。返回给用户的回复本身就是一个动作（第4章将其归类为用户通信工具），因此**输出检查**也属于这一层：**个人可识别信息（PII）过滤器**[待审]对输出进行筛查，过滤身份证号、电话号码等个人可识别信息以防止不必要的暴露；**输出校验**[待审]检查内容，确保回复符合品牌价值。

**数据层**安全护栏管控**系统被允许对数据做出哪些变更**。它们通过稳定且经人工审核的机制来强制执行谁可以对哪些记录执行哪些操作：数据库中的行级安全策略、约束和校验器、受控视图和存储过程，以及由可信运行时绑定的、不可伪造的访问上下文。这一层的价值恰恰在于它不依赖于上面两层的正确性——即使提示注入成功、生成的代码完全省略了权限检查，未授权操作仍然会在数据层被拒绝。第5章通过动态生成软件的例子展开这一层的内容。

#### 人工干预

**人在回路**[待审]干预是一项关键的保护措施：它让智能体在提升真实世界性能的同时不损害用户体验。它在早期部署阶段尤为重要，有助于识别失败模式、暴露边界情况，并建立稳健的评估循环。

有了人在回路机制，无法完成任务的智能体可以优雅地移交控制权。在客服场景中，这意味着升级转接人工坐席；对于编码智能体，这意味着将控制权交还给开发者。

通常有两类主要情况会触发人工干预：

**超出失败阈值**
为智能体的重试次数和操作次数设定上限。一旦智能体超过这些上限，就升级转交人工。

**高风险操作**
敏感的、不可逆的或高风险的操作应触发人工监督——至少在团队对智能体的可靠性建立足够信心之前。典型例子包括授权大额退款或处理付款。

回到驾驭层五要素的主线——来看看它们与本书结构的关系。

### 驾驭层五要素与"构建"部分

**两个公式在不同细节层次上描述了同一架构。****智能体 = 大语言模型 + 上下文 + 工具**为全书提供了组织框架：第2至6章涵盖构建，第7至9章涵盖评估与改进，第10章涵盖协作。**智能体 = 模型 + 驾驭层**将上下文和工具展开为生产系统的五项职责：上下文管理、工具接口、约束、验证与纠正。因此，它**解释的是构建章节所涵盖的架构**，而非为全部十章提供独立的大纲。

在这一范围内，驾驭层五要素与第2至5章的对应关系如下：

| 驾驭层关注点 | 对应章节 | 核心内容 | 安全问题 |
|---|---|---|---|
| 上下文管理 | 第2章（上下文工程） | 提示工程、智能体状态栏、上下文压缩、智能体技能 | 提示注入与上下文污染 |
| 跨会话上下文管理 | 第3章（用户记忆与知识库） | 用户记忆、RAG、结构化索引、智能体化 RAG | 敏感信息暴露、隐私保护 |
| 工具接口与约束 | 第4章（工具） | 工具分类、权限控制、MCP 标准、主动工具发现 | 误操作、未授权访问、不可逆操作 |
| 验证与纠正 | 第5章（编码智能体与通用智能体） | 编码智能体的驾驭层、测试驱动开发、编码化规则 | 身份冒充、责任归属 |

第6章（交互）不属于五要素中的任何一个；它展开的是观测空间和行动空间本身的形式与时机。第7至9章探讨**我们如何知道驾驭层构建得正确，以及如何持续改进它**。第10章将单一智能体的驾驭层替换为多个智能体之间的协作结构。强行将这些章节归入五类只会削弱这些类别的实用性。

安全同样不是按章节划分的：它是一个贯穿全书的横切关注点（影响系统多个部分的问题），由上一节所述的三层安全护栏组织——上下文层、执行层、数据层。上表中的"安全问题"列指出了各章所涉及的主要安全问题。

Anthropic 在构建长时间运行智能体方面的实践表明，驾驭层设计能够解决模型自身无法解决的问题。他们将复杂任务拆分给"初始化智能体"（设置环境、分解任务列表）和"执行智能体"（每次会话推进增量进度并留下清晰的交接工件），使用结构化的驾驭层来应对长任务的两种失败模式：上下文耗尽和过早宣布任务完成。后续章节将逐个组件地剖析驾驭层——第2章从最核心的上下文工程开始，第5章则展示编码智能体中驾驭层工程的完整实践。

## 贯穿全书的设计模式

后续章节反复使用同一组设计模式，因此在此集中给出规范的命名和定义。

**提案者-评审者**[待审]：创建者和评审者在不同的上下文中工作。评审者评估的是工件本身——渲染结果、测试输出或结构化的调用参数——而非创建者的推理过程。其前提是**自我评审不可靠**：模型可能难以识别自身的盲区，也无法察觉上下文是否已被提示注入污染。第3章用它来更新知识；第4章用它对工具调用进行事前审批和事后验证（Sidecar 是其只读变体）；第5章的 PPT、视频和日志实验都基于它构建；第7章用它评估用户界面；第9章用它审查更新提案；第10章讨论它在对等协作中的形态，以及为什么智能体不能自我评审。

**渐进式披露**[待审]：不将所有内容一次性放入上下文，而是先提供一个可搜索的目录，按需加载详细信息。它同时优化两件事——上下文预算和选择准确率。第2章的智能体技能是其原型（元数据常驻，正文按需加载）；第3章的分层检索、第4章的主动工具发现与分页截断、第10章的智能体发现都是其变体。

**仅追加**[待审]：状态通过追加来演进，已写入的内容绝不原地修改。这带来的是可缓存性、可回放性和可审计性。第2章展示了保持 KV缓存前缀稳定的性能收益：前缀中越早的改动会使越多缓存失效。第3章的事件式记忆和第4章将新发现的工具模式追加到轨迹而非插入前缀的做法，都遵循同一原则。

**边界集 + 保留集**[待审]：每次变更都必须在"它应该改变的样本"和"它不应影响的样本"上同时验证。只测试前者会将过拟合误判为进展；只测试后者会将无效的变更误判为安全的变更。第7章的回归任务、第8章的训练/评估隔离以及第9章的更新提案验证都建立在这对集合之上。

**最小差异、可逆**[待审]：保持每次变更尽可能小，携带其来源信息，并且可以独立回滚而非整体重写。这使得归因成为可能——当出现问题时，可以追溯到某一个具体的变更。第3章的知识更新、第5章的代码补丁和第9章的提示词与程序更新都遵循这一原则；本章开头给出的三条更新路径（上下文自适应、外部工件更新、参数更新）本身就是按可逆性从高到低排列的。

## 章节小结

本章构建了一个以实践为导向的理解和构建智能体的框架。

**智能体 = 推理引擎 + 工作上下文 + 行动接口**：大语言模型提供推理与决策，上下文提供决策时可用的信息工作集，工具提供行动接口。三者缺一不可。

**扩展上下文与工具是主要的能力杠杆**：一旦模型确定，重新定义或扩大观测空间和行动空间——即扩展上下文与工具——往往能直接将不可解的任务变为可解的任务。Manus 和 OpenClaw 的演进表明，智能体的多功能性很大程度上来自可用接口的扩展；这种扩展必须保持按需加载，并与权限和验证相配合。

**上下文是决定性因素**：上下文由静态前缀（系统提示词 + 工具定义）和动态轨迹（消息历史）组成。消融实验表明各组件并不等价：移除工具定义或工具结果会直接剥夺行动能力或闭环能力，而移除其余两者的代价则取决于这些信息能否从当前观测中重建。推理-行动循环的本质是不断向轨迹中追加，使模型持续推进任务。

**驾驭层是竞争优势**：模型能力正在趋于同质化；真正的差异化因素是驾驭层——围绕上下文和工具构建的约束、验证与纠正机制，它们使可靠的任务完成成为可能。在生产级智能体系统中，绝大部分驾驭层代码用于这些安全防护，而不仅仅是上下文和工具本身。

**从工作流到自主智能体**：先是提示词，然后是工作流，最后是自主智能体——这种顺序是减少意外行为的最实用方式。每种编排模式都有其适用的场景；没有一种模式在所有场景下都是最优的。

**五种设计模式贯穿全书**：提案者-评审者、渐进式披露、仅追加、边界集 + 保留集、最小差异 + 可逆。

**安全是架构问题**：安全必须从第一行代码开始考虑，而非在上线前打补丁。安全护栏按绕过难度分为上下文层、执行层和数据层；后续所有安全讨论都沿用这一结构。

下一章将深入探讨驾驭层最核心的组件：上下文工程。第8章涵盖智能体概念在强化学习中的学术根源，并比较传统强化学习与现代大语言模型智能体。

## 思考题

1. ★★ 如果你只能为智能体系统增强一项能力——更强的模型、更丰富的上下文，或更多工具——你会选择哪一个？在什么条件下你的选择会发生变化？

2. ★★★ 在推理-行动循环中，累积的缓存读取量近似随轮数呈二次增长。如何降低这种增长？

3. ★★ "模型即智能体"范式意味着模型在工具调用决策上正变得越来越自主。然而本章认为驾驭层工程的重要性实际上在上升。这两种趋势如何共存？智能体框架未来的核心价值在哪里？

4. ★★ 在消融实验中，"工具结果反馈"的缺失使智能体不断重试直至耗尽其迭代预算。在生产环境中，除工具结果缺失外，还有哪些情况可能使智能体陷入此类循环？你会设计什么样的检测和终止机制？

5. ★ 本章从工作上下文、行动接口和策略三个维度分析了五个智能体产品。选择一个你日常使用的 AI 产品，按同样三个维度进行分析，判断其架构是否合理。如果你来设计它，你会改进什么？

6. ★★ 如果你要设计一个专门用于预订机票的客服系统，你会选择工作流模式还是自主智能体模式？能否在同一系统中混合两种模式？

7. ★★★ 安全护栏一节提到了工具风险评级。如果一个工具通常为低风险，但在特定参数组合下变为高风险（例如 `delete_file` 删除普通文件与删除系统文件），你将如何设计动态风险评估？

8. ★★ 本章的智能体产品表格中，所有智能体的行动空间都是"开放式"的。在哪些场景下，受限的行动空间（例如只能从预定义选项中选择）会优于开放式行动空间？

9. ★★ 人在回路干预机制要求智能体"优雅地移交控制权"。然而在实践中，用户可能离线、响应缓慢或给出模糊的指令。在这种情况下智能体应该怎么做？

10. ★★★ 导言中指出"优秀的设计原则应当超越模型迭代周期"，但用于实现这些原则的具体工程方法可能会随着模型能力的提升而过时。请给出这样一个智能体工程方法的例子并解释原因。
