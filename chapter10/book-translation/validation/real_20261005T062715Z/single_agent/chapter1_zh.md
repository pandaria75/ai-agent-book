# AI 智能体入门

如果你曾用 Cursor 写代码，看着它搜索代码库、编辑多个文件、反复重跑测试直到全部通过，那么你已经在使用 AI 智能体了。同样，如果你用 Deep Research 反复搜索和阅读来调研一个话题，让 Manus 控制浏览器完成在线任务，让豆包手机助手订票或发消息，或者派 Pine AI 去跟电信运营商砍话费，你也在使用 AI 智能体。

这些产品形态各异，但有一个共同特征：它们不再是被动的"你问它答"式对话。它们会自行规划执行步骤，调用每个任务所需的工具，并随着结果反馈调整策略。AI 智能体正在成为一种与计算机交互的新方式。

本章从实际案例出发，回溯到 AI 智能体的核心组成部分：读者将亲身体验现代智能体的能力，理解其背后的架构，并学习构建智能体系统的设计模式和最佳实践。

> **阅读提示**：本章是全书的概念地图：对核心公式、运行循环、工程框架和智能体设计模式的一次精要导览。它建立了贯穿后续章节的共享词汇和参考坐标。首次阅读时不必试图记住每个概念，目标是把握全貌。后续每一章都会深入展开本章引入的某一主题，需要重新定位时可随时回到本章。

## 现代智能体 = LLM + 上下文 + 工具

最简而言，一个现代智能体由三个组件构成：**智能体 = LLM（大语言模型）+ 上下文 + 工具**。这里的加号表示工程组件的组合，而非强化学习的正式定义；更重要的是，这个公式只描述智能体边界内部的内容，**不包括智能体交互的环境**。每个术语都需要广义理解，但要有清晰的边界：

- **LLM 是智能体的推理引擎**：它不只是一组模型参数，而是智能体的决策核心，负责理解意图、推理、规划和判断。LLM 的能力来自**预训练**阶段习得的世界知识和语言能力，加上通过**后训练**编码的决策策略（监督微调、强化学习等技术在第 8 章介绍）。
- **上下文是智能体的信息工作集**：不只是喂给模型的文本，而是智能体在每个决策点可用的信息工作集——环境、用户记忆、领域知识、自身状态和任务进度。正如一个人做决策需要审时度势、回忆相关经验、查阅参考资料，智能体的上下文窗口包含了它在那一刻可以使用的信息。
- **工具是智能体的动作接口**：不只是几个可调用的 API 函数，而是智能体能够行动的全部途径——从预定义的工具调用到按需加载的 Skills，从动态生成代码来创造新能力到将工作委派给子智能体，从主动联系用户到响应外部事件。

更直观地说：**智能体 = 推理引擎 + 工作上下文 + 动作接口**。模型负责推理和决策，上下文为这些决策提供所依赖的信息工作集，工具则提供决策影响外部世界的接口。

从经典的强化学习和控制论视角来看，智能体与环境是闭环交互的两面，而非彼此的组成部分。环境返回一个观测，智能体利用其上下文选择下一个动作，该动作改变环境状态，产生下一个观测。

![图 1-1：智能体与环境的交互循环，以及智能体内部的模型-框架结构](images/fig1-1.svg)

图 1-1 展示了两个抽象层级。外层是**智能体与环境的交互**：环境包括文件系统、数据库、网页、用户、其他智能体以及物理或模拟世界。内层是**智能体内部的模型-框架（Model–Harness）结构**：Model 做策略决策；Harness 是智能体边界内的运行时和治理层，负责构建上下文、暴露工具接口、维护循环和状态、执行权限、验证和修正。Harness 可以创建、隔离或代理环境，但不包含环境的状态或转移规则。

因此，工程公式可以进一步展开为：LLM 即 Model，而 Context + Tools 构成最小的 Harness；生产系统在此边界内加入约束、验证和修正。本章其余部分将遵循这一边界。

这三个组件可以与强化学习（RL，见第 8 章）中的策略和交互接口相关联，但并非一一对应。上下文代表智能体内部的观测和历史，而非整个观测空间。工具定义了智能体可用的观测和动作接口，而它们作用的对象仍留在环境中。

| 直觉理解 | 智能体组件 | RL 概念 | 角色 |
|---------------|----------------|------------------|---------------------------------------------|
| **推理引擎** | LLM | **策略** | 决定"接下来做什么"的决策逻辑——根据当前信息，从所有可用选项中选择最合适的动作 |
| **工作上下文** | 上下文构建 | **观测与历史** | 将环境观测和已有历史组织成当前决策所需的信息 |
| **动作接口** | 工具接口 | **观测/动作接口** | 定义智能体可以读取哪些观测、发出哪些动作，以及这些接口的格式 |

### 观测空间与动作空间：模型与世界的接口

**观测空间和动作空间共同构成 LLM 与其外部环境之间的接口**。观测空间将环境中的信息转化为模型可以处理的上下文；动作空间将模型的决策转化为对外部世界的操作。观测空间之外的信息对模型而言实际上不存在。动作空间之外的操作，即便模型完全知道该做什么，也只能以文字形式提出建议。

因此，**在底层模型确定不变的情况下，提升智能体性能的首要系统工程手段往往是重新定义或扩展其观测空间和动作空间**。用本书的术语来说，就是扩展上下文和工具。许多看似需要"更聪明的模型"的问题，其实都是接口问题：把任务相关的数据带入上下文，或者把所需的操作暴露为一个工具，一个此前无法解决的任务就可能变得可解。

**Manus：合并原本分离的空间。** Manus 出现之前，生产级智能体基本沿着三条不同的赛道发展：Deep Research（深度研究）、Coding（编程）和 Computer Use（计算机操控）。Manus 是第一个将这三者融合进同一个系统的、具有广泛影响力的生产级智能体。它的虚拟浏览器扩大了观测空间，而文件系统、代码执行和命令执行扩大了动作空间。Manus 并非仅仅换了一个更强的模型就变成了通用智能体。它取了三类智能体观测空间和动作空间的并集，使一个智能体能够跨越此前的产品边界。

**OpenClaw：将接口延伸到用户的数字生活。** OpenClaw 再次将两个空间向外推进。它通过用户已有的消息渠道——WhatsApp、Telegram、Slack、Discord、iMessage 等——接收任务并返回结果，使智能体几乎可以从任何地方触达。它的本地网关（Gateway）既连接 Google Drive、Notion 等云端应用，也连接本地文件系统。散布在各个账户和设备上的文件，经用户明确授权后，即可进入一个智能体的观测空间，并被其工具操作。与以云端沙箱为中心的原始 Manus 形态（文件通常需要上传或单独配置连接器）相比，本地优先的 OpenClaw 覆盖了更宽的数据边界。Manus 后来也增加了自己的 Google Drive 连接器和本地文件的桌面访问，这恰恰印证了这一点：产品演进往往正是在扩展观测空间和动作空间[^ch1-agent-products]。

[^ch1-agent-products]: Manus 的官方材料将其最初的 Sandbox 描述为一台隔离的云端虚拟机。在介绍 Google Drive 连接器时，Manus 明确回顾了此前在 Drive、桌面和 Manus 之间手动下载和上传文件的碎片化工作流。2026 年 3 月推出 My Computer 时，它将"重要工作在本地而非云端"称为云沙箱的根本局限。OpenClaw 的官方 README 将其描述为运行在用户自己设备上的本地优先、始终在线的个人助手，并列出了二十多个消息渠道；其工具和插件系统可以添加云端集成和本地能力。参见 https://manus.im/blog/manus-sandbox、https://manus.im/blog/manus-google-drive-connector、https://manus.im/blog/manus-my-computer-desktop、https://github.com/openclaw/openclaw 和 https://docs.openclaw.ai/tools

理解每个组件的作用及其协作方式，是构建高效智能体系统的基础。我们将从三者中最具体的一环——工具，即动作接口——开始，逐步向内深入到 LLM 和上下文。先来看不同类型的智能体在这三个维度上的对比：

| 智能体产品 | 工作上下文 | 动作接口 | 策略 |
|-----------------|------------------------|--------------------------|-----------------------------|
| **编程智能体（如 Cursor）** | 需求文档、代码库、终端环境 | 开放式（内部推理、代码搜索、文件读写、命令执行等） | 增量开发：理解需求 → 搜索相关代码 → 编辑代码 → 测试验证 → 调试修复 |
| **搜索智能体（如 Deep Research）** | 网络资源、学术数据库、本地文件 | 开放式（内部推理、搜索查询、网页阅读、摘要生成） | 迭代深化：根据已有信息调整搜索方向，逐步综合出一份完整报告 |
| **计算机操控智能体（如 Browser Use）** | 电脑屏幕、浏览器页面、文件系统 | 开放式（内部推理、点击、输入、滚动、截图、代码执行等） | 视觉感知 + 操作：观察屏幕 → 识别目标元素 → 执行动作 → 验证结果 |
| **手机助手智能体（如豆包）** | 手机屏幕、已安装应用 | 开放式（内部推理、点击、滑动、输入、打开应用等） | 意图理解 + App 控制：理解用户需求 → 定位目标应用 → 执行动作 → 确认完成 |
| **个人任务智能体（如 Pine AI）** | 用户账户信息、历史账单、服务商知识库 | 开放式（内部推理、打电话、发邮件、填表单、与用户确认） | 多步任务执行：收集信息 → 制定谈判策略 → 联系服务商 → 谈判 → 汇报结果 |

这些系统共享三个特征：**开放式的动作空间**——不是从固定按钮集合中选择，而是生成任意自然语言和代码；**内部推理**——行动之前先做规划；**持续交互**——根据环境反馈调整策略。这些能力恰恰来自推理引擎、工作上下文和动作接口的交互——即 LLM、上下文和工具。

### 工具：智能体的动作接口

工具是智能体通向外部世界的桥梁。它们让智能体从被动的观察者变为能够搜索、写文件、运行代码、调用 API、发送消息或操作界面的主动系统。没有工具，智能体只能生成文本；有了工具，它就能对外部系统施加影响。

为了系统地讨论工具，我们可以按智能体与世界交互的方向将其分为五类。先给出各类的几个例子以建立整体认知；后续章节将深入探讨。

**感知工具**让智能体获取信息：搜索引擎提供实时网络数据，文件系统读取本地文档，API 和数据库连接外部服务和企业核心数据。

**执行工具**让智能体对外部系统施加作用：代码执行、文件操作、系统命令和外部 API 调用将决策转化为具体动作。

**协作工具**让智能体与其他智能体分担工作：将专业任务委派给子智能体，在关键决策点请求人类确认，或在多智能体系统中协调行动。

**事件触发工具**的调用方式与前三类根本不同：不是智能体调用它们，而是它们作为外部输入到来，触发智能体开始工作。一封新邮件到达、定时时间到了、另一个系统触发了 Webhook 回调；事件激活智能体并启动推理和行动。智能体从不主动调用它们，但它们仍然是智能体与外部世界交互的一条通道，因此我们将其纳入广义的工具体系。

**用户通信工具**是智能体与用户沟通的渠道。执行工具改变外部世界，通信工具则传递信息——通过短信、电话、邮件等送达智能体的进度报告或主动问询。

第 4 章将介绍这五类工具的完整分类和设计原则。工具设计的质量直接决定了智能体能可靠地完成什么：接口定义含糊，模型就会误用；错误处理不当，一次工具失败就可能让智能体卡住；权限范围过宽，一次智能体的错误就可能不可逆转。随着 MCP（Model Context Protocol，模型上下文协议）标准的普及，集成工具正变得越来越容易。

**工具调用**（也称为 Function Calling，函数调用）是现代 LLM 智能体的核心能力：它让模型以结构化的方式调用外部工具，将 LLM 从纯文本生成器转变为能通过外部接口行动的智能系统。本书统一使用"工具调用"这一术语。

工具调用分四个步骤：首先，上下文告知模型有哪些工具可用（名称、用途、参数）；然后，模型自行决定是否调用工具、调用哪个工具、传什么参数；接着，工具运行完毕后，其结果追加到上下文中；最后，模型根据结果决定下一步行动。这个循环是本章后文将介绍的 ReAct 的基础。

以天气查询为例，API 层面四步过程的简化表示如下：

```text
Step 1: Declare tools                  Step 2: Model decides to call
tools: [{                             assistant: {
  name: "get_weather",                  tool_calls: [{
  parameters: {                           function: "get_weather",
    city: "string"                        arguments: {city: "Beijing"}
  }                                      }]
}]                                    }

Step 3: Result appended to context    Step 4: Model responds based on result
tool: {                               assistant: {
  tool_call_id: "call_1",               content: "Today in Beijing: 28°C, sunny."
  content: '{"temp":28,"sky":"clear"}' }
}                                     }
```

开发者只需定义工具并执行调用；模型自身决定是否调用、调用哪个工具、传什么参数。第 2 章将详细分析这一 API 结构。

为智能体设计工具时，应从任务所需的最窄能力开始，随着任务变复杂再逐步扩展。如果任务只需要基本算术，一个参数定义清晰的计算器就足够了；当任务扩展到读取电子表格、清洗缺失值、计算统计量和绘制图表时，一个受限的 Python 代码解释器比不断膨胀的专用工具集合更容易组合和探索。但通用性也会增加错误风险并扩大攻击面：代码必须在隔离的沙箱中运行，默认禁用网络访问，禁止访问授权工作目录之外的文件，并对执行时间、CPU、内存和输出大小加以限制。

同样，单一的日志工具适合记录一次执行；对于需要数小时甚至数天的长时间运行任务，一个受控的虚拟工作目录可以保存计划、中间结果、执行日志和最终产物，使智能体可以在多次运行之间恢复。这个目录同样应限制可读写路径、存储容量和文件类型，并防止路径穿越，而非将整个主机文件系统暴露给智能体。

通用工具并不总是优于专用工具。高风险操作或受严格业务约束的操作——如支付、数据删除、发送邮件和生产部署——仍应暴露为专用工具，具有明确参数、受限权限和端到端可审计性，并在必要时增加预览和人工确认环节。因此，工具设计的核心原则是：**使用通用基础能力进行组合和探索；使用专用工具约束高风险操作并强制执行严格的业务规则**。

### LLM：智能体的推理引擎

大语言模型（LLM）是智能体的决策核心。面对用户请求，它首先要推断真实意图（用户说的往往不是他们真正想要的），然后将模糊或复杂的任务拆解为可执行的步骤。在整个执行过程中它持续做决策：下一步做什么、是否调用工具、调用哪个工具、传什么参数。这种理解—规划—执行的能力来自预训练阶段积累的知识，是工作流型和自主型智能体共同依赖的基础。

LLM 智能体的一个显著能力是**内部推理**——在行动之前，智能体可以对任务进行规划和推理。这不改变外部环境，却显著改善了后续行动。这种能力来自预训练（即在海量互联网文本上的初始训练，模型在此过程中学习语言模式和世界知识）：模型借鉴人类知识中编码的推理模式，包括数学定律、因果关系和问题分解策略。因此，与传统的强化学习智能体不同，当今基于 LLM 的智能体并非通过盲目试错来探索，而是在结构化的知识体系上进行推理。

#### 模型即智能体：当模型本身成为产品

# AI 智能体入门 [第 2/5 篇]

"模型即智能体"范式是 AI 智能体发展中最新的方向。先进模型通过后训练（尤其是强化学习）将工具调用内化为原生能力：何时调用工具、调用哪个工具、传什么参数——全部由模型自行决定，无需手动编排。这并不意味着框架层不再重要。恰恰相反：模型越强，周围的 Harness 就越关键。Harness 一词原指套在马身上的缰绳和马具——不是为了限制马奔跑的能力，而是为了恰当地引导那股力量。在智能体语境下，模型是一匹强大却难以预测的马，而 Harness 是将其能力导入可靠任务执行的工程基础设施。它包括上下文管理、工具接口、安全约束以及验证和修正机制（见本章最后一节）。

模型拥有的决策权越大，错误决策的影响就越大——这就需要更细粒度的约束、验证和修正来保持其可靠性。模型提供商的真正优势不在于"让框架更薄"，而在于能够对模型及其周围的 Harness 进行协同优化，持续迭代。

但随之而来一个更深层的问题：如果模型持续变强，今天的 Harness 最终会被模型吸收吗？在《苦涩的教训》（The Bitter Lesson）一文中，Rich Sutton 回顾了贯穿七十年 AI 研究的一个反复出现的模式[^ch1-1]：研究者不断将自己对某个领域的理解编码进系统，短期内获得收益，但最终输给了随算力和数据扩展的通用方法——搜索和学习。从这个视角审视，Harness 中的约束、验证和修正，有多少是注定会被模型内化的"人类先验"？**本书认为模型将越来越多地吸收这些能力，但对这一进程的速度应保持现实预期。** 方向上，我们不怀疑模型会继续吸收 Harness 的部分功能——工具调用和长周期规划曾依赖外部编排，如今已成为模型的原生能力。但实践中，这种吸收远比直觉所暗示的要慢：训练以月为时间尺度推进，没有任何模型能在一次训练中内化真实业务的全部约束和偏好。模型当前的能力边界，恰恰就是 Harness 创造价值的地方。因此，Harness 工程并非对苦涩教训的抵抗，而是在工程时间尺度上的实践：凡是模型尚无法可靠完成的，Harness 先行兜底；每当模型内化了某一层能力，Harness 就卸下这一层，转而支持下一个能力前沿。

[^ch1-1]: Sutton, Rich. "The Bitter Lesson", 2019. http://www.incompleteideas.net/IncIdeas/BitterLesson.html

#### 智能体的学习机制：从上下文适应到持久更新

前面的讨论提到，模型可以通过强化学习将工具使用策略内化为原生能力。但智能体行为的改变并非只发生在训练过程中。根据更新发生的位置和持续时间，这些变化可以被理解为三条互补的路径（图 1-2）：任务内的上下文适应、跨任务对外部工件的更新，以及训练周期中的参数更新。

![图 1-2：智能体能力更新的三个层次](images/fig1-2.svg)

**上下文适应**发生在当前任务中。一旦示例、状态和检索结果进入上下文，模型可以立即调整行为，但这不会改变下一个会话的持久状态。其优势是速度快、成本低；其局限在于上下文窗口的大小和信息组织方式。第 2 章将详细解释这种适应方式的工作原理。

要让更改跨任务持久，系统可以更新**外部工件**：事实和经验可以整理成知识文档，可用语言表达的策略可以写入 Prompt 或 Skill，确定性的流程和约束可以编码在程序和 Harness 中。这些工件可审计、可修订，但智能体在执行时仍需通过上下文或工具接口访问它们。第 3 至 5 章为知识和程序奠定基础，第 9 章讨论如何从经过评估的运行轨迹中生成此类更新。

当目标是一种高维能力——如医学影像理解、自然语言风格或隐式决策策略——外部规则无法完全表达时，就必须通过后训练更新**模型参数**。参数更新的部署成本更高，但能产生自然且广泛的泛化能力；第 8 章将系统介绍其方法。因此，这三条路径并非互斥的类别，而是在不同时间尺度上协同运作的机制：上下文支持即时适应，外部工件支持受控积累，参数则内化难以显式表达的能力。

### 上下文：智能体的工作集

上下文是智能体在每个决策点可用的信息工作集。正如一个人做决策需要桌上有合适的材料——任务指令、参考手册、往来的信件、最新的数据——智能体的上下文窗口就是它在当下可以使用的信息。从 API 视角来看（详见第 2 章），每次 LLM 调用的上下文由五个部分组成：

- **System Prompt（系统提示词）**：不同于用户在对话中输入的提示词，系统提示词由开发者编写，在整个对话中保持不变。它是智能体的"岗位说明书"——定义其身份、权限和行为规范。对系统提示词进行精心的提示词工程，是我们塑造智能体运行行为的方式。系统提示词还承载着跨会话持久的**用户记忆**（个性化的偏好、过往行为、背景设置等信息，见第 3 章），以及动态注入的环境状态。
- **Tool Definitions（工具定义）**：声明智能体可用工具的名称、功能描述和参数格式。没有工具定义，智能体就无法识别或调用任何工具——但它也不会就此沉默——一项消融实验（实验 1-1）将展示它会怎么做。工具定义与系统提示词一起构成在整个对话中保持不变的**静态前缀**。（这是基础模式；自 2026 年起，生产框架也可以在上下文末尾按需加载完整的工具 schema 而不破坏前缀——见第 2 章的工具定义一节和第 4 章。）
- **User Messages（用户消息）**：来自用户的输入。用户消息还可能包含通过 RAG（检索增强生成，详见第 3 章）动态检索的**外部知识**——涵盖训练数据截止之后的信息或私有领域知识。
- **Assistant Messages（助手消息）**：模型先前生成的响应，最多可包含三个部分——`reasoning`（内部思维链，保持连贯性和决策可解释性）、`content`（对用户的回答）和 `tool_calls`（智能体采取行动的方式）。在一次具体的响应中，这三部分不一定同时出现：例如，当智能体决定调用工具时，通常只有 `reasoning` + `tool_calls`；当给出最终答案时，通常只有 `reasoning` + `content`。
- **Tool Results（工具结果）**：智能体框架执行工具后返回的输出。这些结果是智能体下一步推理的直接依据——也是让它能从结果中学习而非重复犯错的原因。

前两项（系统提示词 + 工具定义）构成静态前缀；后三项（用户消息 + 助手消息 + 工具结果）构成随每次交互不断增长的动态消息历史。这五个部分共同组成每次 LLM 推理的上下文。

每个组成部分是否都不可或缺？最直接的验证方式是**消融研究**——逐一排除原因的诊断方法：移除组件 A，看系统是否还能工作，然后是组件 B，以此类推，直到每个组件的贡献都清晰可见。实验 1-1 正是将这一方法应用于上述五个组件。

> **实验 1-1 ★★：上下文的关键作用**
>
> 我们通过系统的**消融研究**探测了每个上下文组件如何塑造智能体行为。上述五个组件中，测试了四个——系统提示词作为智能体的基本身份定义被豁免：没有它，智能体完全没有角色意识，测试将毫无意义。如图 1-3 所示，实验设置了五个对照组：一个保留所有组件的完整基线组，加上各缺少一个组件的四组，以观察每个组件对智能体性能的影响。
>
> ![图 1-3：实验 1-1——上下文消融研究设计](images/fig1-3.svg)
>
> 实验结果揭示了每个上下文组件的作用——而且它们的重要程度并不相同。**工具定义**（静态前缀的一部分）是智能体行动能力的基础；没有它们，智能体无法调用任何工具。但丧失行动能力并不意味着沉默：模型仍然返回格式工整、措辞自信的回答，其中的数字来自参数化记忆而非观测结果，排版方式与真正从工具输出中得出的答案一模一样。它会直接拒绝还是当场编造，主要取决于模型自身的幻觉率和诚实度；提示词中的约束如"不要自行估算费率"可以降低编造概率但无法完全消除。**工具结果**是闭环控制的关键；没有它们，智能体就是"盲执行"，不断重试直到耗尽迭代预算。**推理过程**（助手消息中的 reasoning 部分）记录了一步*为什么*被采取，而工具结果记录了*发生了什么*；当前者可以从后者重建时，从历史中去掉它的代价几乎为零。**消息历史**（前几轮的用户消息、助手消息和工具结果）防止冗余操作，避免重蹈覆辙。
>
> 实验的核心洞见：**上下文决定了智能体能"看到"什么，而智能体只能基于它所看到的做出决策。** 但这些组件并非等价的；衡量标准是它携带的信息能否从别处重建——"每个组件都不可或缺"之类的论断必须经过测量而非假设，而且模型迭代如此之快，在更新的模型上进行同样的消融实验很可能得出不同的结论。还有一点在工程实践中更为重要：**"给出了一个答案"不等于"完成了任务"。** 当某个上下文组件缺失时，典型的失败不是报错退出，而是一个看起来无懈可击的答案。

### ReAct 循环

有了这三个组件，一个自然的问题是：它们如何协同工作？ReAct 循环就是将 LLM、上下文和工具连接成一个系统的核心机制。我们可以逐步剖析它。

智能体执行任务的核心模式被称为 **ReAct**（Reasoning + Acting，推理 + 行动）。名字只提到了推理和行动，但实际循环包含三个阶段：模型首先**推理**下一步该做什么，然后调用工具去**行动**，接着**观察**工具的结果并推理后续步骤。这个"推理 → 行动 → 观察 → 推理 → 行动 → 观察"的循环不断重复，直到任务完成。

考虑一个具体例子——跨多种货币汇总收入——来理解智能体的**轨迹（trajectory）**：智能体工作过程中积累的消息历史，由用户消息、助手消息（含推理和工具调用）以及工具结果组成。每次 LLM 调用时，模型接收到的完整上下文是**静态前缀**（系统提示词 + 工具定义）加上**轨迹**（动态消息历史）（图 1-4）。这揭示了一个关键事实：**智能体上下文 = 静态前缀 + 轨迹**。具体而言，静态前缀是上述五个组件的前两个（系统提示词 + 工具定义）；轨迹是后三个（用户消息 + 助手消息 + 工具结果，随每次交互增长）。LLM 基于这个完整上下文生成下一个响应，然后将该响应追加到轨迹中，供后续调用使用。

![图 1-4：智能体轨迹——多币种汇总任务的 ReAct 循环](images/fig1-4.svg)

先从该循环的最小实现开始。它展示了**各组件如何协同工作**：Model 只负责决定下一步，Harness 组装上下文并验证和执行工具，Environment 产生实际的状态变化和观测。本书其余部分也使用 Python 风格的伪代码；伪代码不可运行，也不对应任何特定 SDK。可直接运行的具体代码在本书的配套仓库中。

```python
trajectory = [user_request]

repeat:
    context = stable_prefix + trajectory
    decision = Model(context)
    trajectory.append(decision)

    if decision has no tool call:
        return decision.answer

    for call in decision.tool_calls:       # independent calls may run in parallel
        validated_call = Harness.validate(call)
        observation = Environment.execute(validated_call)
        trajectory.append(observation)
```

以下是轨迹结构的伪代码表示：

```text
trajectory = [
  {role: "user", content: "Based on the company's quarterly revenue: Q1 2.5M USD, Q2 2.1M EUR, Q3 1.8M GBP, Q4 380M JPY, calculate the company's total annual revenue and average quarterly revenue"},
  
  # First iteration - LLM receives the above trajectory and generates a response
  {role: "assistant",
   reasoning: "Need to convert all currencies to USD...",
   content: "",  # No direct reply to the user
   tool_calls: [
     {name: "convert_currency", args: {amount: 2100000, from: "EUR", to: "USD"}},
     {name: "convert_currency", args: {amount: 1800000, from: "GBP", to: "USD"}},
     {name: "convert_currency", args: {amount: 380000000, from: "JPY", to: "USD"}}
   ]},
  
  # Agent framework executes tools, adds results to trajectory
  {role: "tool", content: "EUR->USD: 2282608.7"},
  {role: "tool", content: "GBP->USD: 2278481.01"},
  {role: "tool", content: "JPY->USD: 2541806.02"},
  
  # Second iteration - LLM receives the complete trajectory, including tool results
  {role: "assistant",
   reasoning: "Conversion results obtained, now need to aggregate and calculate...",
   content: "",
   tool_calls: [
     {name: "code_interpreter", args: {code: "total = 2500000 + 2282608.7 + ..."}}
   ]},
  
  {role: "tool", content: "Total: $9,602,895.73, Average: $2,400,723.93..."},
  
  # Third iteration - LLM receives the complete trajectory and generates the final answer
  {role: "assistant",
   reasoning: "All calculations complete, summarizing results...",
   content: "FINAL ANSWER: Total revenue $9,602,895.73..."}
]
```

注意系统提示词和工具定义不出现在轨迹中——它们作为静态前缀，在每次 LLM 调用前自动附加到轨迹之前。

在我们的实验中，这个循环清晰可见。第一轮，智能体分析任务并并行调用了三个货币转换工具；第二轮，它将转换结果交给代码解释器进行计算量更大的运算；第三轮，确认所有计算完成后，给出了最终答案。一个复杂的多步任务在 3 次迭代和 4 次工具调用中完成。

在这个最基本的设计中，LLM 所见的上下文不断追加。每次 LLM 调用都会接收到完整的轨迹，因此模型知道自己处于任务的哪个阶段、之前尝试过什么、结果如何。正如人们在解决问题时不断回顾和总结，智能体通过轨迹保持对任务的全局视野。而且由于轨迹是结构化的——用户消息、助手消息（推理 + 工具调用）和工具结果都清晰分离——系统高度可解释、可调试。

理解了智能体的运行循环之后，我们来看两个实验，观察不同模型如何驱动它。

> **实验 1-2 ★：Kimi K3 的原生智能体能力**
>
> 本实验展示了 **Kimi K3** 的原生智能体能力，它是"模型即智能体"范式的一个实例。Kimi K3 是一个约 2.8 万亿参数的混合专家（MoE）模型。MoE 可以理解为一个专家团队：面对每类问题，系统只激活最擅长的少数专家，而非整个模型，在保留能力的同时不必付出全额效率代价。Kimi K3 拥有 100 万 token 的上下文窗口、原生视觉理解和始终在线的"思考模式"。通过强化学习，它已将工具调用的**决策策略**内化为原生能力：何时调用工具、调用哪个工具、传什么参数，全部由模型自主决定，使其能够自主执行网络搜索等任务。更精确地说，被内化的是*何时以及如何调用*的决策；工具本身，如 `web_search` 和 `code_runner`，仍以 API 级内置工具的形式在服务端执行。Kimi 通过一个名为 Formula 的服务端脚本引擎运行这些官方工具。
>
> 关键观察是：模型自行决定何时搜索、搜索什么，展现出真正的自主性；它随着搜索结果的返回调整策略，判断信息是否足够。有一个常见误解值得澄清：**强化学习赋予模型的是决策策略**，而非工具本身。它教会模型何时调用工具、选择哪个工具、传什么参数、收到结果后是否继续，以及如何将数十甚至上百次调用串联成连贯的推理；这些*是否以及如何使用*的判断才被写入模型的权重。**工具及其执行由智能体框架或 API 内置机制提供**：`web_search` 和 `code_runner` 的实现、代码沙箱，以及发起调用和返回结果的基础设施，全部位于模型之外。RL 优化的是决策策略；它并不会把搜索引擎或代码沙箱嵌入模型权重。因此，编排循环并未消失；它从客户端移到了服务端，而决策则进入了模型[^ch1-2]。
>
> [^ch1-2]: 感谢读者 asdlem 通过 GitHub Issue #30 指出并澄清：RL 内化的是工具调用的决策策略，而非工具执行机制。参见 https://github.com/bojieli/ai-agent-book/issues/30
>
> Kimi K3 在智能体任务中的显著优势是**长链工具调用的稳定性**——它能够维持 200–300 次连续工具调用且推理始终连贯，远超大多数模型开始退化的几十次调用水平。K3 针对长周期编程和智能体工作负载进行了优化，发布了两个变体：K3 Max（用于对话和智能体任务）和 K3 Swarm Max（用于大规模并行处理）。作为开源模型，它在软件工程和智能体基准测试上与顶级闭源系统比肩——这是强化学习能够赋予模型原生智能体能力的证据。
>
> **实验 1-3 ★：GPT-5.6 的原生深度研究能力**
>
> 第二个实验使用 **OpenAI GPT-5.6**，展示一个先进模型如何在 API 级内置工具的支撑下，在服务端为 Deep Research 闭合"搜索—阅读—分析"编排循环。GPT-5.6 有一个便利的特性：**自由格式工具调用（Freeform Tool Calling）**。传统上，模型调用工具必须将每个参数序列化为严格的 JSON（结构化数据格式），就像填写一份有严格格式要求的表格。自由格式工具调用（在 API 中通过 `type: "custom"` 的工具声明）让模型可以直接向工具发送原始文本（一段 Python 代码、一条 SQL 查询），完全避免 JSON 转义。需要强调的是，这是 API 参数格式的演进，而非模型架构的创新——客户端的工具调用循环（检测 `tool_calls` → 执行 → 返回结果）保持不变；只是参数从 JSON 字符串变为原始文本。
>
> GPT-5.6 与 Responses API 的**网络搜索和代码解释器**内置工具配合，实现了 Deep Research 的核心机制：模型可以自主搜索网络获取实时信息，并编写代码进行深入分析，实现"搜索 → 阅读 → 分析 → 再搜索"的迭代研究过程。例如，面对"东盟 10 国首都之间最短距离是多少？"这样的问题，GPT-5.6 会自动搜索各首都的地理坐标，然后编写 Python 代码计算所有首都对之间的大圆距离，最终找出最近的一对。类似地，在"搜索比特币过去一个月的走势并进行技术分析"这样的任务中，它可以从多个金融数据源获取实时价格数据，利用专业技术分析库计算移动平均线、RSI、MACD 等技术指标，生成可视化图表，并给出交易建议。
>
> 更重要的是，GPT-5.6 在模型层面内化了 **OpenAI Deep Research** 产品的设计哲学，引入了**意图澄清流程**。面对一个研究请求，GPT-5.6 不会立即开始执行；它首先通过一系列问题澄清用户的真实意图。对于"搜索比特币过去一个月的走势并进行技术分析"，它会先问："你偏好哪个数据源？你希望分析哪些技术指标？"这种交互式澄清使 GPT-5.6 能够产出更精准、更符合用户实际需求的研究报告。
>
> GPT-5.6 是"模型即智能体"的成熟案例——网络搜索、代码解释器等 Responses API 的内置工具在服务端闭环执行；编排循环从客户端移到了 API 服务器，简化了客户端实现。模型仍然发出标准工具调用；客户端只是不再需要自己搭建"搜索—阅读—分析"的编排框架。其最值得关注的是意图澄清机制：模型不立即执行任务，而是先确认用户真正需要什么，再制定研究策略。"用户说了什么"与"用户真正想要什么"之间的差距，在执行开始之前就被弥合了。
>
> 需要注意的是，本实验不绑定任何特定厂商。没有 OpenAI 额度的读者可以用提供同等托管工具的服务商复现。例如，阿里云百炼的 qwen3.7-plus Responses API 同样包含内置的 `web_search` 和 `code_interpreter`；Kimi K3 由 Formula 托管的搜索和 `code_runner` 提供同类能力。

## Harness 工程：围绕模型构建可靠系统

至此你已经理解了智能体的核心运作方式：LLM 运行 ReAct 循环，以上下文为引导，使用工具完成任务。上面的实验表明基本机制是可行的——同时也暴露了它有多脆弱。模型可能产生幻觉（编造不存在的工具或参数）、选错工具，或无法从错误中恢复。从一个能跑的演示到一个可靠的产品之间存在相当大的鸿沟，而这些脆弱性恰恰是 Harness 工程要解决的问题。本章前半部分回答了智能体是什么；后半部分回答智能体如何在生产环境中可靠运行。

前几节确立了核心公式：**智能体 = LLM + 上下文 + 工具**。它描述了智能体的**内部构成**：推理引擎、工作上下文和动作接口。Harness 工程在同一系统上增加了第二个、**实现层面**的视角：将 LLM 视为一个核心组件（Model），把围绕它构建的所有支撑代码称为 Harness。两种视角并非对立，而是在不同抽象层次描述同一个系统。我们切换到更通用的"Model"一词，是因为 Harness 工程的原则适用于任何能推理和调用工具的模型，而非某一特定类型。Harness 的核心是原公式中的"上下文 + 工具"，外加三层保障：**约束（Constrain）**（智能体可以和不可以做什么）、**验证（Verify）**（它是否正确地做了事）和**修正（Correct）**（做错了如何恢复）。

展开为方程，完整的生产级构成为：

> **Agent = Model + Harness**
>
> **Harness = Context management + Tool interfaces + Constraints + Verification + Correction**
>
> **Agent ↔ Environment**

一个最小演示只需要一个 Model 和一个能构建上下文、暴露工具的 Harness；生产系统必须在同一边界内添加约束、验证和修正。例如，一个退款智能体可以将策略放入上下文，用权限和金额规则约束调用，对照数据库状态验证结果，并在超时后重试或回退。Harness 工程研究的正是这种运行时和治理代码——位于 Model 之外、Agent 边界之内。

更精确地说，Harness 并非模型之外的一切：它是**位于 Agent 边界内、Model 之外**的运行时和治理层。它介导 Model 与 Environment 的交互，但不包含 Environment 本身。工具定义、调用适配器、沙箱权限和重置机制属于 Harness；沙箱内变化的文件和进程、外部数据库、网页、用户和物理世界属于 Environment。部署位置不会改变这一概念边界。Harness 的核心是上下文管理和工具接口，围绕它们构建三类工程保障：

| 组件 | 职责与设计原则 | 实际示例 | 参见章节 |
|---|---|---|---|
| **上下文管理** | 提供相关信息。**信息充分性：**在每一步都给予智能体足够的信息以做出知情决策。 | 系统提示词、知识库、智能体状态栏、Sidecar 旁路查询 | 第 2、3 章 |
| **工具接口** | 定义模型如何行动。**清晰的接口：**使用直观的工具名称、提供参数示例、说明每个工具的限制。 | MCP 工具、代码解释器、搜索工具 | 第 4 章 |
| **约束** | 定义智能体被允许做什么。**默认安全（Fail-safe）：**在明确启用之前保持能力关闭，类似手机应用权限。 | Claude Code 默认在工具执行前要求用户授权。 | 第 4 章 |
| **验证** | 检查工具执行是否产生了正确结果。**输入隔离：**基于结构化数据（如工具返回的字段）做安全检查，而非可能被攻击者通过提示注入影响的模型生成文本。 | 代码检查（Linting）、类型检查、工具结果校验 | 第 5、6 章 |
| **修正** | 从错误中恢复或回滚失败操作。在向用户呈现失败之前先尝试恢复——例如，重试失败的工具调用，而非展示不完整的结果。 | 自动重试、恢复生成、多次失败后升级给人类（熔断器） | 第 2、5 章 |

基本的模型控制循环如下方伪代码所示：

```python
observation = Environment.observe()
trajectory = [observation]
while true:
	actions = Model(Harness.build_context(trajectory))
	if len(actions) == 0:
		break
	allowed_actions = Harness.constrain(actions)
	observation = Environment.apply(allowed_actions)
	if not Harness.verify(Environment):
		observation = Harness.correct(Environment)
	trajectory.append(allowed_actions, observation)
```

这个骨架刻意省略了实现细节。完整的 API 消息循环见第 2 章；工具和自动验证分别在第 4、5 章介绍。

上下文和工具让智能体能够完成任务——理解任务并据此行动。约束、验证和修正则确保它可靠、安全地完成任务——它们不是上下文和工具之外的附加物，而是让上下文和工具在生产环境中可靠运转的工程实践。沿着智能体产品的成熟度曲线，这两组要素的侧重点会逐渐转移。

早期的智能体框架聚焦于上下文和工具：给模型工具，给它上下文，让它完成任务。生产级系统已将重心转向约束、验证和修正：确保工具调用安全、上下文得到管理、错误可以恢复。

以 Claude Code 为例。其 Harness 代码的绝大多数在做约束、验证和修正，而非上下文和工具——工具本身（文件读写、命令执行、搜索）只是很小一部分；围绕它们构建的保障机制才是真正的核心。这些机制包括：

- **过程状态管理**：跟踪智能体当前正在执行的步骤
- **多层上下文压缩**：信息过多时自动裁剪
- **权限分类**：控制哪些操作需要用户确认
- **熔断器（Circuit Breaker）**：多次错误后自动停止重试，防止一次失败操作级联影响整个系统
- **错误恢复机制**：捕获异常、回滚到最后一个稳定状态、重试，或交由人类处理

**行业正从"完成任务"转向"可靠地完成任务"，使 Harness 工程成为智能体系统的核心竞争力。**

### 从 Prompt 工程到 Loop 工程：工程范式的演进

回顾 AI 应用工程的发展，一条清晰的演进脉络浮现：

**Prompt Engineering（提示词工程）** 是第一波创新——通过打磨喂给模型的自然语言指令来提升输出质量。

**Context Engineering（上下文工程）** 是第二波——认识到仅优化提示词不够：模型能看到的一切信息（系统指令、工具定义、对话历史、外部知识）都必须被系统地管理。

**Harness Engineering（Harness 工程）** 是第三波——将视野从"模型接收什么信息"扩展到"模型运行在什么类型的系统中"，纳入模型之外的所有基础设施：约束机制、验证方法、反馈回路、错误恢复。

**Loop Engineering（循环工程）** 随之而来，将视野从单次运行扩展到跨运行的持续自主运行：谁来发现下一项工作、何时验证、任务何时才算真正完成（第 10 章将与多智能体协作系统一起展开这一主题）。

2026 年 7 月，业界开始使用 **Graph Engineering（图工程）** 来描述更高层次的编排视角：将智能体循环、确定性程序和人工审批组织成一张显式执行图，其中节点提供能力，边定义路由和依赖关系，结构化状态沿这些边流动并在关键边界处持久化[^ch1-graph-engineering]。

[^ch1-graph-engineering]: Josh C. Simmons 在 2026 年 7 月 4 日的文章 *We Are Entering the Graph Engineering Phase* 中明确使用了这个名称，从节点、带类型的边和带检查点的状态三个维度加以总结。7 月 18 日，Peter Steinberger 关于讨论是否已从循环转向图的提问，进一步推动了这一名称的传播。这些实践早于这一标签：LangGraph、Microsoft Agent Framework 和 Google ADK 的官方文档都将它们描述为图编排或基于图的工作流。参见 https://www.drjoshcsimmons.com/writing/we-are-entering-the-graph-engineering-phase、https://x.com/steipete/status/2078277297791189132、https://docs.langchain.com/oss/python/langgraph/overview、https://learn.microsoft.com/en-us/agent-framework/workflows/ 和 https://adk.dev/workflows/。

这五个阶段不是替代关系，而是嵌套的层次：Prompt Engineering 是 Context Engineering 的子集，Context Engineering 是 Harness Engineering 的子集，Harness Engineering 是 Loop Engineering 的子集。Loop Engineering 又是 Graph Engineering 的子集：单个智能体循环构成执行图中的一个节点。每一层都比上一层扩大了工程师的关注范围和影响力。**当模型能力趋于收敛、不再成为决定性的差异化因素时，竞争优势就转移到模型之外的工程上。**

近期的工程实践支持这一观点。LangChain 在 Terminal Bench 2.0（一个评估智能体在终端环境中完成复杂任务能力的基准测试）上的工作就是一个引人注目的例子：他们的编程智能体从 52.8% 提升到 66.5%（排名从前三十之外跃升至前五）。改变的不是模型，而是 Harness——让智能体检查自己的执行结果、检测自己何时陷入重复循环，并优化其推理策略。

### 构建高效智能体的核心原则

基于 Anthropic 的经验，成功的智能体系统遵循三条核心原则[^ch1-anthropic-building-effective-agents]。

**保持简单。** 从最简单的方案开始，仅在真正必要时才增加复杂度。直接调用 API 优于复杂的框架；清晰的代码优于巧妙的抽象——每多一层抽象，调试时就多一个盲区。

**保持透明。** 清晰展示智能体的规划步骤、执行日志和决策轨迹。这不只是调试的便利，更是用户信任的前提——黑盒内部的错误很难从外部定位或修复。

**设计良好的工具接口（ACI，智能体-计算机接口）。** ACI 意味着从智能体的视角设计接口——让智能体易于理解和使用——而非从程序员的视角，如传统 API 那样。工具名称和参数应当直观，在容易被误用的地方，设计应当从一开始让错误不可能发生：SIM 卡的缺口使其只能以一个方向插入卡托，微波炉门开着时拒绝加热。在制造业中，这种方法被称为 **poka-yoke（防错法）** 或 **mistake-proofing（防呆）**：通过设计产品和流程来防止错误或使错误立即显现。它被丰田生产体系所采用[^ch1-poka-yoke]。一个设计不良的工具可以让最强大的模型反复失败：接口是模型与工具之间唯一的通道，模糊的接口会被放大为系统性错误。

[^ch1-poka-yoke]: Toyota UK, ["Poka-yoke – Toyota Production System guide"](https://mag.toyota.co.uk/poka-yoke/)；American Society for Quality (ASQ), ["What Is Mistake Proofing?"](https://asq.org/quality-resources/mistake-proofing)。两者都将防错定义为防止错误或在其发生时立即检测。

[^ch1-anthropic-building-effective-agents]: Anthropic. "Building effective agents", December 2024. https://www.anthropic.com/engineering/building-effective-agents

接下来三节涉及 Harness 工程中三个独立但重要的主题：模型选择、编排模式、护栏与安全。它们都不属于 Harness 的五个要素本身，但在工程实践中不可避免。

### 如何选择模型

# AI 智能体入门 [第 4/5 篇]

在讨论编排模式之前，我们首先需要回答一个实际问题：什么样的模型应该驱动你的智能体？

模型是智能体智能的基础，选对模型往往比任何提示词调优都更重要。模型发布节奏太快，具体版本推荐很快就会过时，因此本节提供方向而非版本清单。

**闭源模型。** 当前智能体开发中最常用的两个闭源模型提供商是 OpenAI（GPT/o 系列）和 Anthropic（Claude 系列）。闭源模型通常能力领先，但价格更贵，且受制于厂商的 API 政策。选择模型时，不要只依赖排行榜；**在你自己的任务上评估它**（见第 7 章）。

**开源模型。** 截至本书写作时，开源模型落后闭源模型不超过六个月，而成本却低得多。如果业务场景不要求最高的模型能力，开源模型是务实之选。开源模型成本低、支持私有部署、可微调定制，适合成本敏感型场景或有数据合规要求的场景。DeepSeek、Kimi 和 GLM 是国内智能体能力较强的模型。注意不同模型的工具调用能力差异很大，务必在你的具体场景中测试后再做决定。

**除了能力，还要考虑模型的政策边界。** 一个模型可能具备执行某项任务的技术能力，但承载它的产品不一定允许用户调用这种能力。不同厂商在网络安全、模型蒸馏、模型提取、私有数据和高风险操作上划定的政策边界各不相同；同一任务在聊天产品、编程智能体和 API 中也可能产生不同结果。因此，模型选择不能只比较准确率、价格和速度。要在你的真实任务上测试：模型是否愿意继续执行、接口是否暴露了所需能力、服务条款是否允许预期用途。对业务关键任务，应准备人工接管或另一个合规模型作为回退。

**大多数智能体需要支持推理的模型。** 智能体要做复杂决策——多步推理、工具选择——而没有推理能力的模型在这些任务上往往表现不佳。例外很少：单一的简单步骤，或本质上就是点击固定位置的计算机操控 GUI 操作，非推理模型或许够用。一旦涉及多步推理或动态决策，推理模型就是必需的。

**考虑输出速度和多模态能力。** 除了成本，还有两个容易被忽视的维度。一个是**输出 token 速度**：智能体通常要运行多轮推理，每轮必须完成才能开始下一轮，因此输出速度直接决定端到端延迟——一个 20 轮的智能体任务每轮多花 2 秒就意味着多等 40 秒。另一个是**多模态支持**：如果你的智能体需要理解图像、音频或视频，多模态能力就是硬性要求，而模型在这方面差异很大。

### 编排模式：工作流 vs. 自主智能体

编排模式是 Harness 组织其"上下文与工具"层的方式——它决定上下文如何在 LLM 调用之间流动、工具如何被调度，以及智能体的执行路径是预先固定还是动态生成。智能体编排经历了从简单到复杂的演进，每种模式都有适合的场景和取舍。在 Anthropic 与数十个团队构建 LLM 智能体的经验中[^ch1-anthropic-building-effective-agents]，最成功的实现很少使用复杂框架；它们使用简单、可组合的模式。

构建 LLM 应用时，应遵循从简单到复杂的原则。先考虑单次 LLM 调用。如果更好的提示词和上下文示例就能解决问题，就不要引入智能体系统。当需要多步处理时，对于能清晰分解为固定子任务的场景，考虑使用工作流。只有在需要动态决策和灵活执行路径时，才使用自主智能体。记住，智能体系统通常以延迟和成本换取更好的任务表现，所以要仔细权衡这笔交易是否值得。

一个常见的反面教材是上来就构建一个高度复杂的工作流或多智能体系统。例如，当被要求设计一个"从百万条聊天消息中提取个人记忆"的智能体时，一些 AI 模型会迅速勾勒出一条看似严谨的流水线：先分段对话，然后依次分配提取、证据验证、身份消解、记忆策展和合并审查智能体，最后构建事实图谱、覆盖清单和不可变版本。每个组件单独看都有道理，但合在一起就构成了一个低效且不可靠的系统。因为复杂工作流的执行拓扑是固定的，每个新异常都容易导致增加一个节点：架构越来越复杂，通用性却越来越差。本可以由模型从上下文做出的语义判断，反而被硬编码进了工作流。

因此，**Harness 的重要性并不意味着越复杂的 Harness 越好**。Manus 网站将这一取舍总结为"Less structure, more intelligence"（更少的结构，更多的智能）[^ch1-manus-less-structure]。先给一个有能力的智能体一个清晰的目标、必要的上下文和可组合的工具，用自然语言告诉它一个人类会如何验证证据、做比较、解决冲突。程序只应硬编码必须始终成立的边界，如权限、绝不覆盖原始素材、原子化发布。只有当业务约束本质上要求，或评估反复暴露某种稳定的失败模式时，才应将相应步骤提升为专门的验证器、独立智能体或确定性流程。好的结构不是替智能体预演所有思考；它守住边界，把边界内的决策空间还给模型。

[^ch1-manus-less-structure]: Manus, "Less structure, more intelligence." https://manus.im/

#### 工作流模式：确定性编排

**工作流（Workflow）** 是通过预定义代码路径编排 LLM 和工具的系统。其执行路径是确定性的，由开发者预先设计——每一步的行为和状态转移在代码中定义；LLM 只负责每个节点内部的理解和生成。

例如，一个机票预订智能体可以使用一个包含四个固定节点的工作流：

1. **验证用户身份**——调用身份验证 API，确认用户是谁。
2. **搜索可用航班**——根据用户需求查询航班数据库。
3. **完成支付**——调用支付接口扣款。
4. **确认预订**——调用预订 API 锁定座位，并向用户发送确认信息。

每个节点内部可以使用 LLM（例如用自然语言理解用户的出行需求），但节点之间的流转顺序由代码固定——系统不会在支付完成前预订座位，也不会在身份验证前开始搜索航班。

工作流模式有两个核心优势。第一，**严格的流程控制**：开发者可以保证关键步骤绝不会被跳过或乱序执行——"未支付不预订"这样的业务规则由代码强制执行，而非交由 LLM 判断。第二，**安全性**：由于执行路径是确定性的，提示注入或模型错误最多只能影响当前节点内部的处理；它无法让智能体跳到不该到达的分支。攻击面被限制在单个节点内。

工作流的主要局限是**缺乏灵活性**。当发生预期之外的事件——例如用户在支付过程中更改预订，或航班取消后系统需要推荐替代方案——固定路径无法自行适应；它只能走预设的异常分支，或把控制权交还给人类。

来看最简单的工作流例子：**文生图生成**。用户的需求通常是一句朴素的自然语言，比如"给我画一幅 AGI 实现后程序员工作时的场景"；但 Stable Diffusion 这类文生图模型只接受特定风格的提示词——逗号分隔的英文标签、质量词、负向提示词。因此工作流在用户和图像生成模型之间放了两个固定节点：

1. **提示词改写**——用 LLM 将用户的自然语言请求改写为文生图模型期望的提示词格式。对于上面的例子，"AGI 实现后程序员工作时"是一个非常宽泛的需求，所以 LLM 还需要仔细思考（例如"AGI 实现后程序员不再需要写代码，所以画面应展示一个程序员在海滩上晒太阳，通过脑机接口指挥 AI 员工"），然后产出具体的场景描述。
2. **图像生成**——用改写后的提示词调用文生图模型，获得图像。

执行路径是硬编码的。这个工作流中的 LLM 节点执行的是**翻译**——把人类语言转换为工具能理解的输入格式——它之所以存在，是因为文生图模型"听不懂大白话"。专门修补工具（或模型）这类能力短板的 Harness 代码，可以称为**适配器层（adapter layer）**。

但如果把图像生成工具换成具有**原生图像生成**能力的多模态模型，如 Nano Banana 2 或 GPT-Image 2，提示词改写就不再需要了。无论用户怎么表述需求，模型都能自行理解并直接生成图像。

> **实验 1-4 ★：文生图工作流 vs. 原生图像生成**
>
> 通过两条路径发送相同的自然语言请求。**工作流路径**：LLM 先将请求改写为 Stable Diffusion 风格的提示词，然后调用文生图模型生成图像；**原生路径**：将原句直接发送给支持原生图像生成的多模态模型（如 GPT-Image 2），一次调用即生成图像。
>
> 对比两件事：提示词改写节点把原始请求变成了什么，以及哪条路径的图像更贴近原始请求。值得对比两类请求：一类是具体的（例如指定文案的海报），一类是宽泛的（如上面的 AGI 工作场景）——对于后者，工作流路径可能仍有自身的优势。

这个实验表明，**Harness 中修补模型能力短板的部分，会随着模型变强而被模型自身内化**。仅在本章中，这就已经发生过多次：少样本示例和"让我们一步步思考"之类的提示技巧被指令微调和推理模型内化；输出格式修复和 JSON 解析容错被结构化输出和原生工具调用内化；文生图提示词改写被模型的原生多模态理解与生成能力吸收。每一轮内化都消灭了一类"翻译"和"脚手架"式的适配器层代码。

#### 自主智能体：运行时决策

当工作流的固定路径不够用时，我们需要**自主智能体**。自主智能体与工作流的核心区别在于：执行路径不是预先定义的，而是在运行时由智能体根据**环境反馈**决定。

回到机票的例子，自主智能体不需要四个预定义节点。用户说"帮我订一张下周三去上海的机票"，智能体自行动态决定顺序：它搜索航班，发现需要登录，先验证身份，再恢复搜索。如果最便宜的航班有中转，它可以询问是否可以接受；如果用户说不行，它就调整搜索条件。

因此自主智能体必须自行规划——选择自己的执行步骤——并能识别失败、改变策略，而非一出错就直接停止。但自主性不是无边界的：必须设计显式的**停止条件**（任务完成、达到最大迭代次数、遇到不可恢复的错误），否则智能体可能陷入无限循环，或在任务完成后仍在继续执行。

从实现角度看，自主智能体本质上就是一个 LLM 在循环中使用工具，持续获取环境反馈以推进任务——这就是前文介绍的 ReAct 循环。常见的退出条件包括：调用了最终输出工具、模型返回不带任何工具调用的响应、遇到错误或达到最大轮数。

![图 1-6：自主智能体的执行循环](images/fig1-6.svg)

自主智能体特别适合开放式问题——那些难以预测需要多少步骤的问题。典型用例包括：编程智能体解决 SWE-bench（软件工程基准，评估智能体自动修复真实 GitHub issue 能力的基准测试）任务、"Computer Use"智能体像人类一样操作计算机界面、需要迭代搜索和分析的研究任务。

自主性也意味着更高的成本，且错误会累积。因此部署自主智能体需要在沙箱中进行充分测试、设置适当的护栏和监控，并在关键决策点设置人工介入检查点。

#### 选择与混合两种模式

在实践中，工作流和自主智能体并非互斥——许多系统将两者混合：合规要求严格的关键流程以工作流运行以保证可靠性，需要灵活决策的部分则切换到自主模式。例如，n8n 是一个成熟的开源工作流自动化框架，开发者通过在可视化画布上排列功能组件来构建智能体——工作流节点和自主智能体节点可以在同一系统中并存。

![图 1-7：n8n 工作流编辑器界面](images/n8n-workflow.png)

另一种混合方式是**先让自主智能体编写工作流，再由工作流来执行**。阅读任务后，智能体自行决定拓扑并生成一段编排代码；代码生成之后，执行阶段就回到工作流的确定性上。这样既保留了自主智能体面对陌生任务的灵活性，又不必让模型在每次调度时都做决策。第 10 章将详细讨论这种形式。

### 护栏与安全

护栏实现了 Harness 的约束、验证和修正机制，提供分层防御，使智能体行为保持安全可控。设计良好的**护栏**有助于管理数据隐私风险（例如防止系统提示词泄露）和声誉风险（例如保持模型行为与品牌一致）。从你已经识别的风险对应的护栏开始，然后随着新漏洞的出现逐步增加新的护栏。

把护栏视为纵深防御。单一护栏可能都不够，但几个专门的护栏组合起来能让智能体系统韧性大增。

护栏还有另一种失败模式：**误拒（false refusal）**。为降低放行危险请求的概率，模型也可能拒绝合理但看起来敏感的工作，例如授权的安全测试或模型蒸馏研究。因此，护栏评估不仅应测试禁止的请求是否被拦截，还应测试明显允许的请求是否仍能完成。

#### 护栏的类型

护栏可以放置在三个层次：**上下文层、执行层和数据层**。这三个层次的排序依据不是它们在请求生命周期中的位置，而是**被绕过的难度**——层次越低，越不依赖模型自身的判断，单次成功的攻击就越难穿透。本书以这个三层框架来组织后续的安全讨论。

**上下文层**护栏管控**模型能看到什么**，在内容进入上下文之前进行拦截。它通常包含四种机制。**相关性分类器**标记离题查询——比如向一个编程助手提问"帝国大厦有多高？"。**安全分类器**检测越狱（诱导模型绕过其安全限制）和提示注入（在输入中嵌入恶意指令）；两者的关键区别在于，越狱是用户试图绕过模型自身的限制，而提示注入是攻击者通过网页或文档等外部数据间接操纵模型。**内容审核**标记暴力或歧视等有害、不当的输入。**基于规则的防护**对已知威胁（如 SQL 注入）采取确定性措施——黑名单、输入长度限制、正则表达式过滤。来源标注和"指令"与"数据"的分离也属于这一层；第 2 章将展开讨论。

Anthropic 的宪法分类器（Constitutional Classifiers）是基于分类器的护栏在实践中的一个例子[^ch1-3]。其设计有三个关键要素。第一，**规则驱动训练**：用自然语言规则说明允许和禁止的内容，据此为输入和输出分类器生成合成训练数据。第二，**联合上下文判断**：新一代分类器将用户的提问和模型的回答放在一起检查，因为有些回答单独看完全正常（例如"如何使用食品调味料"），只有结合问题才清楚"食品调味料"是化学试剂的暗语。第三，**两阶段筛选**：一个极其轻量的探针——几乎零成本地读取模型的内部激活——先检查每段对话，任何可疑内容都升级给更强的分类器复审，而非直接拒绝。这样第一阶段可以容忍更多误报而不损害用户体验，总体成本也大大降低。

[^ch1-3]: Anthropic. "Next-generation Constitutional Classifiers: More efficient protection against universal jailbreaks", 2026. https://www.anthropic.com/research/next-generation-constitutional-classifiers；论文：Cunningham et al., "Constitutional Classifiers++: Efficient Production-Grade Defenses against Universal Jailbreaks", arXiv:2601.04603

但这一层存在结构性上限：**智能体无法可靠地判断提示注入是否已经攻破了自己的上下文**。因此，上下文层可以降低攻击的成功率，但无法提供保证——这恰恰是下面两层存在的必要性所在。

**执行层**护栏管控**模型能做什么**，在动作生效之前进行验证。其核心是**工具风险评级**：每个工具根据可逆性、权限级别和资金影响被标记为低、中、高风险，高风险操作需要额外审查或人工确认。关键在于，这项审查必须由**上下文之外**的机制执行——独立的审查流程、最小权限凭证、沙箱隔离、人在回路中——否则同一次攻击可能同时攻破智能体及其安全机制。返回给用户的回复本身就是一种动作（第 4 章将其归类为用户通信工具），因此**输出检查**也属于这一层：**PII 过滤器**筛选输出中的身份证号、电话号码等个人可识别信息，防止不必要的暴露；**输出验证**检查内容，确保回复符合品牌价值观。

**数据层**护栏管控**系统被允许对数据做出哪些更改**。它通过稳定、经人工审查的机制强制执行谁可以在哪些记录上执行哪些操作：数据库中的行级安全策略、约束和校验器、受控视图和存储过程，以及由可信运行时绑定的、不可伪造的访问上下文。这一层的价值恰恰在于它不依赖上面两层的正确性——即使提示注入成功、生成的代码完全省略了权限检查，未经授权的操作仍会在数据层被拒绝。第 5 章将通过动态生成软件的示例展开这一层。

#### 人工干预

**人在回路中（Human-in-the-loop）** 的干预是一项关键保障措施：它让智能体在不损害用户体验的前提下提升实际表现。它在部署早期最为重要，帮助识别失败模式、发现边缘情况，并建立稳健的评估循环。

有了人在回路的机制，无法完成任务的智能体可以优雅地移交控制权。在客服场景中，这意味着升级给人工坐席；对编程智能体而言，这意味着把控制权交还给开发者。

通常有两种主要情况会触发人工干预：

**超过失败阈值**
为智能体的重试次数和操作次数设定上限。超过上限时，升级给人工。

**高风险操作**
敏感、不可逆或高风险的操作应触发人工监督——至少在团队对智能体的可靠性建立足够信心之前。典型例子包括授权大额退款或处理付款。

回到五大 Harness 要素的主线——让我们看看它们与本书结构的关系。

### 五大 Harness 要素与"构建"部分

**两个公式在不同细节层次上描述同一套架构。** **Agent = LLM + Context + Tools** 提供了全书的组织框架：第 2–6 章覆盖构建，第 7–9 章覆盖评估与改进，第 10 章覆盖协作。**Agent = Model + Harness** 将上下文和工具展开为生产系统的五项职责：上下文管理、工具接口、约束、验证和修正。因此它**解释的是构建章节中涵盖的架构**，而非为全部十章提供单独的大纲。

在这一范围内，五大 Harness 要素清晰地映射到第 2 至 5 章：

| Harness 聚焦 | 对应章节 | 核心内容 | 安全关注点 |
|--------------------|--------------------|-------------------------------|------------------------|
| 上下文管理 | 第 2 章（上下文工程） | 提示词工程、智能体状态栏、上下文压缩、Agent Skills | 提示注入与上下文污染 |
| 跨会话的上下文管理 | 第 3 章（用户记忆与知识库） | 用户记忆、RAG、结构化索引、Agentic RAG | 敏感信息泄露、隐私保护 |
| 工具接口与约束 | 第 4 章（工具） | 工具分类、权限控制、MCP 标准、主动工具发现 | 误操作、未授权访问、不可逆操作 |
| 验证与修正 | 第 5 章（编程智能体与通用智能体） | 编程智能体的 Harness、测试驱动开发、规则编码化 | 身份冒用、责任归属 |

第 6 章（交互）不属于五大要素中的任何一项；它展开的是观测空间和动作空间本身的模态和时机。第 7 至 9 章追问的是**我们如何知道 Harness 被正确构建，以及如何持续改进它**。第 10 章用多个智能体之间的协作结构取代单个智能体的 Harness。强行将这些章节归入五类只会让这五类失去价值。

安全同样不按章节划分：它是一个贯穿全书的横切关注点（影响系统许多部分的问题），由上一节的三层护栏来组织——上下文、执行、数据。上表中的"安全关注点"列指出了各章涉及的主要安全问题。

Anthropic 在构建长时间运行的智能体方面的实践展示了 Harness 设计如何解决模型自身无法解决的问题。他们将复杂任务拆分给"初始化智能体"（搭建环境、分解任务列表）和"执行智能体"（每次会话推进增量进度、留下清晰的交接产物），用结构化 Harness 应对长任务的两种失败模式：上下文耗尽和过早宣告任务完成。后续章节将逐个组件地展开 Harness——第 2 章从最核心的上下文工程开始，第 5 章则呈现编程智能体中 Harness 工程的完整实践。

## 贯穿全书的设计模式

后续章节反复使用同一组设计模式，因此在此统一命名和定义。

**提案者-审查者（Proposer-Reviewer）**：创建者和审查者在各自的上下文中工作。审查者评估的是产出物本身——渲染结果、测试输出或结构化调用参数——而非创建者的推理过程。其前提是**自我审查不可靠**：模型可能难以识别自身的盲区，或检测其上下文是否已被提示注入攻破。第 3 章用它来更新知识；第 4 章用它做工具调用的预审批和后验证（Sidecar 是一个只读变体）；第 5 章的 PPT、视频和日志实验都建立在它之上；第 7 章用它评估 UI；第 9 章用它审查更新提案；第 10 章讨论它在对等协作中的形态，以及为什么智能体不能审查自己。

**渐进式披露（Progressive Disclosure）**：不要一次性把所有内容放进上下文，而是先提供一个可检索的目录，按需加载细节。它同时优化两件事——上下文预算和选择准确率。第 2 章的 Agent Skills 是原型（元数据常驻，正文按需加载）；第 3 章的分层检索、第 4 章的主动工具发现与分页截断、第 10 章的智能体发现都是它的变体。

**仅追加（Append-only）**：状态通过追加来演化，已写入的内容从不就地修改。它换来的是可缓存性、可重放性和可审计性。第 2 章展示了保持 KV-cache 前缀稳定的性能收益：前缀中越早的变动会使越多缓存失效。第 3 章基于事件的记忆和第 4 章将新发现的工具 schema 追加到轨迹而非插入前缀的做法，都遵循同一原则。

**边界集 + 保留集（Boundary Set + Retention Set）**：每一次变更都必须在"它应该改变的样本"和"它不应影响的样本"上同时验证。只测前者会把过拟合误认为进步；只测后者会把无效的变更误认为安全的变更。第 7 章的回归任务、第 8 章的训练/评估隔离和第 9 章的更新提案验证都建立在这对集合之上。

**最小差异，可逆（Minimal Diff, Reversible）**：让每次变更尽可能小，携带其来源信息，并可独立回滚而非整体重写。这使得归因成为可能——当某处出错时，可以追溯到某一次具体变更。第 3 章的知识更新、第 5 章的代码补丁和第 9 章的提示词与程序更新都遵循这一原则；而本章开头给出的三条更新路径（上下文内适应、外部工件更新、参数更新）本身就是按可逆性从高到低排列的。

## 本章小结

本章建立了一个以实践为先的 AI 智能体理解与构建框架。

**智能体 = 推理引擎 + 工作上下文 + 动作接口**：LLM 提供推理和决策，上下文提供决策时可用的信息工作集，工具提供动作接口。三者缺一不可。

**扩展上下文与工具是首要的能力杠杆**：一旦模型确定，重新定义或扩大观测空间和动作空间——即扩展上下文和工具——往往能直接将不可解的任务变为可解。Manus 和 OpenClaw 的演进都表明，智能体的多才多艺很大程度上来自扩展其可用接口；但这种扩展必须按需进行，并配套权限和验证。

**上下文是决定性因素**：上下文由静态前缀（系统提示词 + 工具定义）和动态轨迹（消息历史）组成。消融实验表明各组件并不等价：去掉工具定义或工具结果直接剥夺了行动能力或闭环能力，而去掉另外两个组件的代价取决于该信息能否从当前观测中重建。ReAct 循环的本质就是不断地向轨迹追加，让模型持续推进任务。

**Harness 是竞争优势**：模型能力正在商品化；真正的差异化因素是 Harness——围绕上下文和工具构建的约束、验证和修正机制，使任务能够可靠完成。在生产级智能体系统中，绝大多数 Harness 代码投入在这些保障机制上，而非仅仅上下文和工具。

**从工作流到自主智能体**：先提示词，再工作流，最后自主智能体——这个顺序是减少意外行为最实用的方法。每种编排模式都有适合的场景；没有哪种模式在所有地方都是最优的。

**五种设计模式贯穿全书**：提案者-审查者、渐进式披露、仅追加、边界集 + 保留集、最小差异 + 可逆。

**安全是架构问题**：安全必须从第一行代码就开始考虑，而非上线前才打补丁。护栏按被绕过的难度分为上下文、执行和数据三层；后续所有安全讨论都沿用这一结构。

下一章将深入探讨 Harness 最核心的组件：上下文工程。第 8 章介绍智能体概念在强化学习中的学术根源，并对比传统 RL 与现代 LLM 智能体。
