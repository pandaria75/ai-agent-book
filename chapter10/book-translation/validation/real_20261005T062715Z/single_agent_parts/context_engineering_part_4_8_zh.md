在继续之前，有必要区分两个容易混淆的概念。**KV Cache** 是模型内部的机制：在单次推理过程中，缓存已处理 token 的键值状态，避免冗余计算。**Prompt Cache** 是推理引擎层面的优化：跨多次 API 请求复用相同前缀的缓存计算。两者都依赖前缀稳定性，但作用于不同层次。KV Cache 加速请求内的 token 生成；Prompt Cache 减少跨请求的冗余前缀计算。实践中，API 提供商会匹配请求前缀。如果多个请求共享相同的前缀，提供商可以直接复用先前计算的 KV Cache，而无需为这些 token 重新计算键值状态。从缓存读取的成本远低于重新计算——例如在 Anthropic、DeepSeek 和 GPT-5 上大约是十分之一的价格。缓存的启用和计费方式因提供商而异：有的自动启用，有的需要手动配置，使用时请查阅最新文档。

### 将缓存视为架构约束

在生产级智能体系统中，缓存不仅仅是性能优化——它是一种**架构约束**，决定了系统中许多看似无关的设计决策。

Claude Code 展示了一个更广泛的模式：当 Prompt Cache 具有显著的经济价值时，缓存一致性可以塑造整个系统的架构选择。有几个设计决策反映了这一约束：

**提示词结构由缓存边界塑造。** 系统提示词被缓存边界标记切分：标记之前的内容可以跨用户、跨会话全局缓存，标记之后的内容包含用户和会话特定的信息。这意味着提示词的排列顺序主要由缓存经济学驱动，其次才是语义逻辑。每个放在缓存边界之前的运行时条件（操作系统类型、当前模式、用户偏好等）都会使缓存键变体数量翻倍。如果每个条件是二值的，N 个条件产生 2^N 种组合，因此所有动态元素都需要放在边界之后。例如，3 个二值条件（macOS/Linux、正常/调试模式、中文/英文）产生 2×2×2 = 8 个缓存键。

**子智能体必须与父智能体逐字节对齐。** 当主智能体派生子智能体或执行旁路查询时，如果子智能体继承父智能体的上下文，其提示词、工具定义、模型配置、消息前缀和推理配置必须与父智能体逐字节一致。这使其能命中 API 提供商的 Prompt Cache，降低成本和延迟。不过，有些智能体框架派生的子智能体使用不同的上下文或提示词；在这种情况下，不要求字节级对齐。

**工具结果的替换字符串在首次出现时被冻结。** 当大型工具输出被替换为摘要预览时，替换字符串会被持久化。即使会话重启，系统也会复用完全相同的替换字符串，使恢复的消息序列与缓存流保持字节一致。

核心洞见是：**缓存经济学不是事后的优化，而是前置的架构约束。** 越早将这一约束纳入架构，后续工程成本就越低。

### 重新思考 KV Cache：可编辑、可组合的"笔记"

（以下内容为来自当前研究的可选进阶材料。首次阅读时可以跳过，不影响本章其余内容；上面的三个实践结论才是基础。）

到目前为止，本节一直假设一条严格规则：前缀中改一个字节，后续缓存即失效。这条规则在当今的推理引擎中成立，但未必是不可避免的。最近的一项研究从一个反直觉的观察出发[^ch2-2]：在预填充阶段，模型的行为仿佛在"做笔记"。当它读取上下文中的一个字段（如"用户所在城市：北京"）时，并不是简单地将该字段逐字缓存。相反，它将该字段**结论**的下游表示——即这个字段的含义——写入后续的 KV 状态。测量表明，该字段**自身** token 的 KV 状态对最终决策的贡献往往不到 1%；对输出影响更大的是该字段留下的下游"笔记"。

这一发现暗示了两种此前被认为不切实际的操作。第一是**编辑（Editing）**：既然结论已写入下游笔记，当模型有显式思维链（CoT）时，修改后的字段可以通过缓存的推理链传播，产生接近完全重算的结果，计算量仅为约 1%。反之，没有 CoT 时，孤立的字段修改可能被忽略，因为结论已嵌入下游且没有推理路径来更新它。第二是**组合（Composition）**：预计算的"技能"缓存可以通过旋转位置编码（RoPE）重定位并拼接到另一个上下文中，无需重新计算注意力。在这个框架下，从模块化缓存块组装长上下文从 O(L²) 重算降为 O(L) 拼接，输出质量接近完全重算。

这里的页边批注类比很有用。阅读一份长文档时，当某个事实发生变化，你不会重新阅读整篇文档，而是更新记录该事实含义的批注。将 KV Cache 视为笔记的思路类似：如果缓存的状态已经编码了对某个事实的推理，那么修改这个事实可能只需修正下游的笔记，而非重算一切。由于笔记以可移植的形式表示，一个问题的笔记块也可以通过 RoPE 重定位并在另一个问题中复用。论文在 vLLM 上实现了这一想法，将 p90 首 token 时间加速了数十到数百倍，前缀缓存命中率约 98.5%，输出接近逐 token 重算（在 12 个模型上，logit 余弦相似度 0.90–0.999）。

对智能体而言，其启示是：当工具、记忆字段或运行时状态变化时，长上下文未必总是需要拆掉重建。原则上，这可以在保留部分缓存收益的同时使上下文可变，将上下文组装从 O(L²) 重算变为 O(L) 笔记拼接。这仍是研究阶段的工作；本节前面的三个实践结论仍是当前生产系统的默认原则。

[^ch2-2]: Li, Bojie. *Models Take Notes at Prefill: KV Cache Can Be Editable and Composable.* arXiv:2606.17107, 2026.

理解了上下文如何被处理和缓存之后，下一个问题是如何设计内容本身。以下几节围绕三条相关线索讨论上下文中应该放什么以及如何组织：

- **提示词工程、提示注入与动态提示词（Agent Skills）**：如何编写系统提示词以及该包含什么。这是上下文工程最直接的部分。工具定义作为与系统提示词并列的另一个静态组件，也直接影响智能体工具使用的准确性。本章提供核心原则，第 4 章将展开详述。接下来是安全问题：当外部内容试图劫持精心设计的上下文时，系统应如何在上下文层面进行防御？随着提示词越来越长、覆盖场景越来越多，把所有东西塞进一个系统提示词变得不切实际：既浪费 token 又稀释注意力。这就自然引出了 Agent Skills 的渐进式披露机制——知识按需加载，而非一次性全部包含。
- **Agent Status Bar**：一种独立机制，在上下文末尾注入动态元信息（任务进度、环境观测摘要、工具调用计数等），弥补模型无法主动归纳隐式状态的不足。类比手机屏幕顶部显示的时间、电量和信号，Agent Status Bar 让模型可以随时获取当前运行时状态。
- **上下文压缩策略**：应对上下文不断膨胀的问题——何时压缩、如何压缩、以及压缩如何与 KV Cache 共存。

## 提示词工程：优化系统提示词

提示词工程的主要关注点是 **System Prompt**——API 消息列表中 `role: "system"` 的消息。它是智能体的操作手册，定义智能体的身份、行为规则、约束和工作流程。精心设计的系统提示词使模型能够在特定任务中充分发挥其通用能力。

系统提示词设计有一个实用的试金石：LLM 就像一位能力很强但对你的具体工作流程和内部惯例完全陌生的新团队成员。如果这样一位新成员在读完你的系统提示词后仍然不知道该怎么做，智能体也不会知道。

以下几节讨论系统提示词设计的几个维度。

### 语气与风格：行为框架

语气和风格容易被忽视，但对用户体验有强烈影响。比如"You MUST answer concisely with fewer than 4 lines."这样的指令。当智能体无法完成任务时，"keep your response to 1–2 sentences"和"do not explain why you cannot do something"等约束可以防止冗长的自我辩解。大写词如"NEVER do X"比"Please avoid doing X"等更柔和的措辞更能提升指令的显著性，但过度使用会削弱效果；将它们留给真正关键的约束。

### 结构化提示词：系统提示词的"格式"

现代大语言模型对结构化输入表现出显著的敏感性，这源于训练数据中大量的结构化内容。XML 标签的使用遵循层级原则，标签名本身携带语义信息——`<working_directory>` 立刻告诉模型这是工作目录信息，而"当前目录：/Users/project/src"这样的纯文本格式则需要模型额外推理来推断冒号两侧的关系。

Markdown 在保持可读性的同时提供轻量级结构，特别适合组织层级化的指令和信息。XML 和 Markdown 构成了两层结构：XML 提供精确的、机器可解析的语义，Markdown 则为人类和机器读者组织内容。

下面是一个同时使用两者的系统提示词：

```text
# Tool Usage Guidelines

## File Operations
<file_operation>
- Check whether the path exists before reading a file
- Create a backup before writing a file
</file_operation>

## Network Requests
<network_request>
- Set the timeout to 30 seconds
- Retry at most 3 times after a failure
</network_request>
```

- **Markdown 的贡献**：`#` 和 `##` 等标题让人类一眼就能看清层级结构，保持提示词的可读性。
- **XML 的贡献**：`<file_operation>` 和 `<network_request>` 等标签告诉模型"这个块是关于文件操作的"、"这个块是关于网络请求的"——精确的语义使模型的处理更加准确。

两者结合使用，提示词对人来说读起来清晰，对模型来说解析得精确。

### 流程驱动 vs. 规则堆叠：系统提示词的"组织"

能为人类降低认知负荷的方法对大语言模型同样有效——因为模型在训练中学习了人类的语言和推理模式。想象给新团队成员一本几百条零散规则的手册，没有流程图，没有优先级说明——即使是很强的人也会困惑：当多条规则同时适用时该选哪条？规则未覆盖的情况怎么办？

相比之下，流程驱动的提示词就像一份有效的培训手册，提供清晰的标准操作流程（SOP）：

```text
File Processing Standard Operating Procedure:

Step 1: Validation
   Check if file exists and is accessible
   - If not found → log error and stop
   ↓
Step 2: Classification
   Determine file type based on extension and content
   ↓
Step 3: Preprocessing
   Config files → create backup
   Large files (>1MB) → stream processing
   ↓
Step 4: Execution
   Execute core processing logic based on file type
   ↓
Step 5: Verification
   Ensure integrity of the processed file
```

这种流程设计帮助模型跟踪自己处于哪个阶段、当前步骤的目标是什么、下一步应该做什么。发生异常时，模型可以根据当前阶段选择应对方式，而不是在长长的无关规则列表中搜索。

### 将业务规则转化为可执行指令

构建生产级智能体系统时，最关键也最容易被忽视的步骤之一是**将业务策略转化为精确的决策规则**。这不是技术问题，而是产品设计问题，需要产品经理深度参与。

考虑一个帮助用户打电话解决账单问题的智能体：用户告诉智能体想要降低订阅费或申请退款，智能体自动致电客服完成谈判。为这样一项服务设计计费系统就说明了为什么这些规则需要精确。产品经理的核心需求是"任务不成功则退还服务费"，既鼓励用户尝试又防止滥用。团队设计了三种计费模式：

- **节省分成**：智能体代表用户谈判，从中抽成，例如节省金额的 20%。
- **固定服务费**：对于不涉及省钱的任务（如订餐厅），根据复杂度收取固定费用。
- **困难任务预付金**：对于成功率极低的任务，收取不可退还的预付金以过滤不切实际的请求。

然而，模糊的规则（如"根据任务情况选择合适的计费类型"）导致智能体行为高度不稳定。"帮我退回上个月买的衣服"——这是"帮用户省钱"还是"拿回本来属于他们的钱"？"帮我取消 Netflix 订阅"——取消确实能避免未来付款，但这算"省钱"吗？同一任务在不同时间可能被完全不同的分类，业务逻辑变得不可预测。

产品经理必须将决策规则定义到可执行的程度。佣金制计费仅适用于通过谈判降低现有账单的场景（智能体需要运用谈判技巧说服商家）。退款和服务取消绝不能采用佣金制——提示词必须明确写道："NEVER use percentage_based_one_time for refunds and service cancellations. Use fixed_fee instead."

成功率估算和金额计算同样需要精确到可执行的程度。成功率应按固定流程逐步评估，估算的概率应直接映射到计费模型。例如，估算成功概率高于 60% 的任务可能使用可退款模式，低于 30% 的可能被拒绝。金额计算必须定义计费精度——例如，电话通话按每分钟 $0.05 计费，总额四舍五入到最接近的整数美元——并明确说明"节省"仅根据现有账单计算。否则，模型可能推理道："如果明年价格涨到 $180 而不谈判，而我帮忙维持在 $150，那就是省了 $30"，错误地将避免未来涨价计入节省。

这些规则看似琐碎，但正是这些细节决定了系统行为的一致性。在成熟的智能体团队中，提示词往往由**产品经理**设计，他们基于生产数据、用户反馈和运营经验迭代规则定义。工程师的角色是准确编码规则、确保格式正确和结构清晰、避免擅自做出业务逻辑决策。

核心设计理念是：大语言模型擅长遵循复杂指令和从长上下文中提取信息，但不应赋予它们过多制定业务规则的自由裁量权。通过提供清晰的操作框架，模型的认知资源被释放出来，专注于真正需要推理的部分。有效的培训不是让人自己去推断流程，而是提供详细的标准操作流程，让人在清晰的框架内操作。

### Few-Shot 示例：何时向模型展示示例

除了规则和流程，示例（few-shot 示例）是另一类重要的系统提示词内容。当期望输出难以用规则精确描述时——例如特定风格的文案、结构化报告的格式、或客服回复的语气和分寸——提供两三个高质量的输入-输出示例往往比写长段抽象描述更有效。模型可以在当前上下文中适配这些模式，效果通常优于遵循同等数量的抽象指令（其背后的内部机制在本章的上下文压缩一节讨论）。反之，对于模型已能很好处理且规则容易陈述的任务，示例只会浪费 token。

有两个工程决策点。第一，**示例放在哪里**：放在系统提示词中使其成为对所有请求都有效的静态前缀；或者，一组合成的 user/assistant 消息可以放在对话的第一轮，适用于不同对话类型需要不同示例集的场景。第二，**示例如何影响 KV Cache 前缀稳定性**：无论放在哪里，示例都出现在上下文的早期。一旦选定，就应逐字节保持稳定。每次请求都动态检索不同的"最相关"示例会反复使缓存失效。因此，生产系统通常为每种任务类型准备一组固定示例，而非按请求逐一选择。

示例并非越多越好：两三个精心挑选的涵盖边界情况的示例，通常比十个近乎重复的示例更有用。近乎重复的示例消耗上下文并稀释模型对规则本身的关注。

### 工具定义设计

除了系统提示词，API 请求中另一个重要的静态组件是**工具定义**（`tools` 字段）。工具定义的质量直接决定智能体工具使用的准确性。好的工具定义就像操作手册，让从未见过该工具的模型从一开始就正确使用它并避免常见错误。

Claude Code 的工具定义表明，每个工具描述都经过精心设计，包含使用边界（"NEVER invoke grep or rg as a Bash command"）、具体示例（`timezone: 'America/New_York'`）、性能提示（"Batch your tool calls together"）和工具之间的关系（"Use the Read tool at least once before editing"）。第 4 章将详细讨论工具定义的设计原则和最佳实践。
