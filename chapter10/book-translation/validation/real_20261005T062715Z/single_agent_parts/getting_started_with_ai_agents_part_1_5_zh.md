# AI 智能体入门

如果你曾用 Cursor 写代码，看着它搜索代码库、编辑多个文件、反复重跑测试直到全部通过，那么你已经在使用 AI 智能体了。同样，如果你用 Deep Research 反复搜索和阅读来调研一个话题，让 Manus 控制浏览器完成在线任务，让豆包手机助手订票或发消息，或者派 Pine AI 去跟电信运营商砍话费，你也在使用 AI 智能体。

这些产品形态各异，但有一个共同特征：它们不再是被动的"你问它答"式对话。它们会自行规划执行步骤，调用每个任务所需的工具，并随着结果反馈调整策略。AI 智能体正在成为一种与计算机交互的新方式。

本章从实际案例出发，回溯到 AI 智能体的核心组成部分：读者将亲身体验现代智能体的能力，理解其背后的架构，并学习构建智能体系统的设计模式和最佳实践。

> **阅读提示**：本章是全书的概念地图：对核心公式、运行循环、工程框架和智能体设计模式的一次精要导览。它建立了贯穿后续章节的共享词汇和参考坐标。首次阅读时不必试图记住每个概念，目标是把握全貌。后续每一章都会深入展开本章引入的某一主题，需要重新定位时可随时回到本章。

## 现代智能体 = LLM + 上下文 + 工具

最简而言，一个现代智能体由三个组件构成：**智能体 = LLM（大语言模型）+ 上下文 + 工具**。这里的加号表示工程组件的组合，而非强化学习的正式定义；更重要的是，这个公式只描述智能体边界内部的内容，**不包括智能体交互的环境**。每个术语都需要广义理解，但要有清晰的边界：

- **LLM 是智能体的推理引擎**：它不只是一组模型参数，而是智能体的决策核心，负责理解意图、推理、规划和判断。LLM 的能力来自**预训练**阶段习得的世界知识和语言能力，加上通过**后训练**编码的决策策略（监督微调、强化学习等技术在第 8 章介绍）。
- **上下文是智能体的信息工作集**：不只是喂给模型的文本，而是智能体在每个决策点可用的信息工作集——环境、用户记忆、领域知识、自身状态和任务进度。正如一个人做决策需要审时度势、回忆相关经验、查阅参考资料，智能体的上下文窗口包含了它在那一刻可以使用的信息。
- **工具是智能体的动作接口**：不只是几个可调用的 API 函数，而是智能体能够行动的全部途径——从预定义的工具调用到按需加载的 Skills，从动态生成代码来创造新能力到将工作委派给子智能体，从主动联系用户到响应外部事件。

更直观地说：**智能体 = 推理引擎 + 工作上下文 + 动作接口**。模型负责推理和决策，上下文为这些决策提供所依赖的信息工作集，工具则提供决策影响外部世界的接口。

从经典的强化学习和控制论视角来看，智能体与环境是闭环交互的两面，而非彼此的组成部分。环境返回一个观测，智能体利用其上下文选择下一个动作，该动作改变环境状态，产生下一个观测。

![图 1-1：智能体与环境的交互循环，以及智能体内部的模型-框架结构](images/fig1-1.svg)

图 1-1 展示了两个抽象层级。外层是**智能体与环境的交互**：环境包括文件系统、数据库、网页、用户、其他智能体以及物理或模拟世界。内层是**智能体内部的模型-框架（Model–Harness）结构**：Model 做策略决策；Harness 是智能体边界内的运行时和治理层，负责构建上下文、暴露工具接口、维护循环和状态、执行权限、验证和修正。Harness 可以创建、隔离或代理环境，但不包含环境的状态或转移规则。

因此，工程公式可以进一步展开为：LLM 即 Model，而 Context + Tools 构成最小的 Harness；生产系统在此边界内加入约束、验证和修正。本章其余部分将遵循这一边界。

这三个组件可以与强化学习（RL，见第 8 章）中的策略和交互接口相关联，但并非一一对应。上下文代表智能体内部的观测和历史，而非整个观测空间。工具定义了智能体可用的观测和动作接口，而它们作用的对象仍留在环境中。

| 直觉理解 | 智能体组件 | RL 概念 | 角色 |
|---------------|----------------|------------------|---------------------------------------------|
| **推理引擎** | LLM | **策略** | 决定"接下来做什么"的决策逻辑——根据当前信息，从所有可用选项中选择最合适的动作 |
| **工作上下文** | 上下文构建 | **观测与历史** | 将环境观测和已有历史组织成当前决策所需的信息 |
| **动作接口** | 工具接口 | **观测/动作接口** | 定义智能体可以读取哪些观测、发出哪些动作，以及这些接口的格式 |

### 观测空间与动作空间：模型与世界的接口

**观测空间和动作空间共同构成 LLM 与其外部环境之间的接口**。观测空间将环境中的信息转化为模型可以处理的上下文；动作空间将模型的决策转化为对外部世界的操作。观测空间之外的信息对模型而言实际上不存在。动作空间之外的操作，即便模型完全知道该做什么，也只能以文字形式提出建议。

因此，**在底层模型确定不变的情况下，提升智能体性能的首要系统工程手段往往是重新定义或扩展其观测空间和动作空间**。用本书的术语来说，就是扩展上下文和工具。许多看似需要"更聪明的模型"的问题，其实都是接口问题：把任务相关的数据带入上下文，或者把所需的操作暴露为一个工具，一个此前无法解决的任务就可能变得可解。

**Manus：合并原本分离的空间。** Manus 出现之前，生产级智能体基本沿着三条不同的赛道发展：Deep Research（深度研究）、Coding（编程）和 Computer Use（计算机操控）。Manus 是第一个将这三者融合进同一个系统的、具有广泛影响力的生产级智能体。它的虚拟浏览器扩大了观测空间，而文件系统、代码执行和命令执行扩大了动作空间。Manus 并非仅仅换了一个更强的模型就变成了通用智能体。它取了三类智能体观测空间和动作空间的并集，使一个智能体能够跨越此前的产品边界。

**OpenClaw：将接口延伸到用户的数字生活。** OpenClaw 再次将两个空间向外推进。它通过用户已有的消息渠道——WhatsApp、Telegram、Slack、Discord、iMessage 等——接收任务并返回结果，使智能体几乎可以从任何地方触达。它的本地网关（Gateway）既连接 Google Drive、Notion 等云端应用，也连接本地文件系统。散布在各个账户和设备上的文件，经用户明确授权后，即可进入一个智能体的观测空间，并被其工具操作。与以云端沙箱为中心的原始 Manus 形态（文件通常需要上传或单独配置连接器）相比，本地优先的 OpenClaw 覆盖了更宽的数据边界。Manus 后来也增加了自己的 Google Drive 连接器和本地文件的桌面访问，这恰恰印证了这一点：产品演进往往正是在扩展观测空间和动作空间[^ch1-agent-products]。

[^ch1-agent-products]: Manus 的官方材料将其最初的 Sandbox 描述为一台隔离的云端虚拟机。在介绍 Google Drive 连接器时，Manus 明确回顾了此前在 Drive、桌面和 Manus 之间手动下载和上传文件的碎片化工作流。2026 年 3 月推出 My Computer 时，它将"重要工作在本地而非云端"称为云沙箱的根本局限。OpenClaw 的官方 README 将其描述为运行在用户自己设备上的本地优先、始终在线的个人助手，并列出了二十多个消息渠道；其工具和插件系统可以添加云端集成和本地能力。参见 https://manus.im/blog/manus-sandbox、https://manus.im/blog/manus-google-drive-connector、https://manus.im/blog/manus-my-computer-desktop、https://github.com/openclaw/openclaw 和 https://docs.openclaw.ai/tools

理解每个组件的作用及其协作方式，是构建高效智能体系统的基础。我们将从三者中最具体的一环——工具，即动作接口——开始，逐步向内深入到 LLM 和上下文。先来看不同类型的智能体在这三个维度上的对比：

| 智能体产品 | 工作上下文 | 动作接口 | 策略 |
|-----------------|------------------------|--------------------------|-----------------------------|
| **编程智能体（如 Cursor）** | 需求文档、代码库、终端环境 | 开放式（内部推理、代码搜索、文件读写、命令执行等） | 增量开发：理解需求 → 搜索相关代码 → 编辑代码 → 测试验证 → 调试修复 |
| **搜索智能体（如 Deep Research）** | 网络资源、学术数据库、本地文件 | 开放式（内部推理、搜索查询、网页阅读、摘要生成） | 迭代深化：根据已有信息调整搜索方向，逐步综合出一份完整报告 |
| **计算机操控智能体（如 Browser Use）** | 电脑屏幕、浏览器页面、文件系统 | 开放式（内部推理、点击、输入、滚动、截图、代码执行等） | 视觉感知 + 操作：观察屏幕 → 识别目标元素 → 执行动作 → 验证结果 |
| **手机助手智能体（如豆包）** | 手机屏幕、已安装应用 | 开放式（内部推理、点击、滑动、输入、打开应用等） | 意图理解 + App 控制：理解用户需求 → 定位目标应用 → 执行动作 → 确认完成 |
| **个人任务智能体（如 Pine AI）** | 用户账户信息、历史账单、服务商知识库 | 开放式（内部推理、打电话、发邮件、填表单、与用户确认） | 多步任务执行：收集信息 → 制定谈判策略 → 联系服务商 → 谈判 → 汇报结果 |

这些系统共享三个特征：**开放式的动作空间**——不是从固定按钮集合中选择，而是生成任意自然语言和代码；**内部推理**——行动之前先做规划；**持续交互**——根据环境反馈调整策略。这些能力恰恰来自推理引擎、工作上下文和动作接口的交互——即 LLM、上下文和工具。

### 工具：智能体的动作接口

工具是智能体通向外部世界的桥梁。它们让智能体从被动的观察者变为能够搜索、写文件、运行代码、调用 API、发送消息或操作界面的主动系统。没有工具，智能体只能生成文本；有了工具，它就能对外部系统施加影响。

为了系统地讨论工具，我们可以按智能体与世界交互的方向将其分为五类。先给出各类的几个例子以建立整体认知；后续章节将深入探讨。

**感知工具**让智能体获取信息：搜索引擎提供实时网络数据，文件系统读取本地文档，API 和数据库连接外部服务和企业核心数据。

**执行工具**让智能体对外部系统施加作用：代码执行、文件操作、系统命令和外部 API 调用将决策转化为具体动作。

**协作工具**让智能体与其他智能体分担工作：将专业任务委派给子智能体，在关键决策点请求人类确认，或在多智能体系统中协调行动。

**事件触发工具**的调用方式与前三类根本不同：不是智能体调用它们，而是它们作为外部输入到来，触发智能体开始工作。一封新邮件到达、定时时间到了、另一个系统触发了 Webhook 回调；事件激活智能体并启动推理和行动。智能体从不主动调用它们，但它们仍然是智能体与外部世界交互的一条通道，因此我们将其纳入广义的工具体系。

**用户通信工具**是智能体与用户沟通的渠道。执行工具改变外部世界，通信工具则传递信息——通过短信、电话、邮件等送达智能体的进度报告或主动问询。

第 4 章将介绍这五类工具的完整分类和设计原则。工具设计的质量直接决定了智能体能可靠地完成什么：接口定义含糊，模型就会误用；错误处理不当，一次工具失败就可能让智能体卡住；权限范围过宽，一次智能体的错误就可能不可逆转。随着 MCP（Model Context Protocol，模型上下文协议）标准的普及，集成工具正变得越来越容易。

**工具调用**（也称为 Function Calling，函数调用）是现代 LLM 智能体的核心能力：它让模型以结构化的方式调用外部工具，将 LLM 从纯文本生成器转变为能通过外部接口行动的智能系统。本书统一使用"工具调用"这一术语。

工具调用分四个步骤：首先，上下文告知模型有哪些工具可用（名称、用途、参数）；然后，模型自行决定是否调用工具、调用哪个工具、传什么参数；接着，工具运行完毕后，其结果追加到上下文中；最后，模型根据结果决定下一步行动。这个循环是本章后文将介绍的 ReAct 的基础。

以天气查询为例，API 层面四步过程的简化表示如下：

```text
Step 1: Declare tools                  Step 2: Model decides to call
tools: [{                             assistant: {
  name: "get_weather",                  tool_calls: [{
  parameters: {                           function: "get_weather",
    city: "string"                        arguments: {city: "Beijing"}
  }                                      }]
}]                                    }

Step 3: Result appended to context    Step 4: Model responds based on result
tool: {                               assistant: {
  tool_call_id: "call_1",               content: "Today in Beijing: 28°C, sunny."
  content: '{"temp":28,"sky":"clear"}' }
}                                     }
```

开发者只需定义工具并执行调用；模型自身决定是否调用、调用哪个工具、传什么参数。第 2 章将详细分析这一 API 结构。

为智能体设计工具时，应从任务所需的最窄能力开始，随着任务变复杂再逐步扩展。如果任务只需要基本算术，一个参数定义清晰的计算器就足够了；当任务扩展到读取电子表格、清洗缺失值、计算统计量和绘制图表时，一个受限的 Python 代码解释器比不断膨胀的专用工具集合更容易组合和探索。但通用性也会增加错误风险并扩大攻击面：代码必须在隔离的沙箱中运行，默认禁用网络访问，禁止访问授权工作目录之外的文件，并对执行时间、CPU、内存和输出大小加以限制。

同样，单一的日志工具适合记录一次执行；对于需要数小时甚至数天的长时间运行任务，一个受控的虚拟工作目录可以保存计划、中间结果、执行日志和最终产物，使智能体可以在多次运行之间恢复。这个目录同样应限制可读写路径、存储容量和文件类型，并防止路径穿越，而非将整个主机文件系统暴露给智能体。

通用工具并不总是优于专用工具。高风险操作或受严格业务约束的操作——如支付、数据删除、发送邮件和生产部署——仍应暴露为专用工具，具有明确参数、受限权限和端到端可审计性，并在必要时增加预览和人工确认环节。因此，工具设计的核心原则是：**使用通用基础能力进行组合和探索；使用专用工具约束高风险操作并强制执行严格的业务规则**。

### LLM：智能体的推理引擎

大语言模型（LLM）是智能体的决策核心。面对用户请求，它首先要推断真实意图（用户说的往往不是他们真正想要的），然后将模糊或复杂的任务拆解为可执行的步骤。在整个执行过程中它持续做决策：下一步做什么、是否调用工具、调用哪个工具、传什么参数。这种理解—规划—执行的能力来自预训练阶段积累的知识，是工作流型和自主型智能体共同依赖的基础。

LLM 智能体的一个显著能力是**内部推理**——在行动之前，智能体可以对任务进行规划和推理。这不改变外部环境，却显著改善了后续行动。这种能力来自预训练（即在海量互联网文本上的初始训练，模型在此过程中学习语言模式和世界知识）：模型借鉴人类知识中编码的推理模式，包括数学定律、因果关系和问题分解策略。因此，与传统的强化学习智能体不同，当今基于 LLM 的智能体并非通过盲目试错来探索，而是在结构化的知识体系上进行推理。

#### 模型即智能体：当模型本身成为产品
