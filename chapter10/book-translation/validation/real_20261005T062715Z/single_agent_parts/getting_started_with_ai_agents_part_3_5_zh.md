> **实验 1-2 ★：Kimi K3 的原生智能体能力**
>
> 本实验展示了 **Kimi K3** 的原生智能体能力，它是"模型即智能体"范式的一个实例。Kimi K3 是一个约 2.8 万亿参数的混合专家（MoE）模型。MoE 可以理解为一个专家团队：面对每类问题，系统只激活最擅长的少数专家，而非整个模型，在保留能力的同时不必付出全额效率代价。Kimi K3 拥有 100 万 token 的上下文窗口、原生视觉理解和始终在线的"思考模式"。通过强化学习，它已将工具调用的**决策策略**内化为原生能力：何时调用工具、调用哪个工具、传什么参数，全部由模型自主决定，使其能够自主执行网络搜索等任务。更精确地说，被内化的是*何时以及如何调用*的决策；工具本身，如 `web_search` 和 `code_runner`，仍以 API 级内置工具的形式在服务端执行。Kimi 通过一个名为 Formula 的服务端脚本引擎运行这些官方工具。
>
> 关键观察是：模型自行决定何时搜索、搜索什么，展现出真正的自主性；它随着搜索结果的返回调整策略，判断信息是否足够。有一个常见误解值得澄清：**强化学习赋予模型的是决策策略**，而非工具本身。它教会模型何时调用工具、选择哪个工具、传什么参数、收到结果后是否继续，以及如何将数十甚至上百次调用串联成连贯的推理；这些*是否以及如何使用*的判断才被写入模型的权重。**工具及其执行由智能体框架或 API 内置机制提供**：`web_search` 和 `code_runner` 的实现、代码沙箱，以及发起调用和返回结果的基础设施，全部位于模型之外。RL 优化的是决策策略；它并不会把搜索引擎或代码沙箱嵌入模型权重。因此，编排循环并未消失；它从客户端移到了服务端，而决策则进入了模型[^ch1-2]。
>
> [^ch1-2]: 感谢读者 asdlem 通过 GitHub Issue #30 指出并澄清：RL 内化的是工具调用的决策策略，而非工具执行机制。参见 https://github.com/bojieli/ai-agent-book/issues/30
>
> Kimi K3 在智能体任务中的显著优势是**长链工具调用的稳定性**——它能够维持 200–300 次连续工具调用且推理始终连贯，远超大多数模型开始退化的几十次调用水平。K3 针对长周期编程和智能体工作负载进行了优化，发布了两个变体：K3 Max（用于对话和智能体任务）和 K3 Swarm Max（用于大规模并行处理）。作为开源模型，它在软件工程和智能体基准测试上与顶级闭源系统比肩——这是强化学习能够赋予模型原生智能体能力的证据。
>
> **实验 1-3 ★：GPT-5.6 的原生深度研究能力**
>
> 第二个实验使用 **OpenAI GPT-5.6**，展示一个先进模型如何在 API 级内置工具的支撑下，在服务端为 Deep Research 闭合"搜索—阅读—分析"编排循环。GPT-5.6 有一个便利的特性：**自由格式工具调用（Freeform Tool Calling）**。传统上，模型调用工具必须将每个参数序列化为严格的 JSON（结构化数据格式），就像填写一份有严格格式要求的表格。自由格式工具调用（在 API 中通过 `type: "custom"` 的工具声明）让模型可以直接向工具发送原始文本（一段 Python 代码、一条 SQL 查询），完全避免 JSON 转义。需要强调的是，这是 API 参数格式的演进，而非模型架构的创新——客户端的工具调用循环（检测 `tool_calls` → 执行 → 返回结果）保持不变；只是参数从 JSON 字符串变为原始文本。
>
> GPT-5.6 与 Responses API 的**网络搜索和代码解释器**内置工具配合，实现了 Deep Research 的核心机制：模型可以自主搜索网络获取实时信息，并编写代码进行深入分析，实现"搜索 → 阅读 → 分析 → 再搜索"的迭代研究过程。例如，面对"东盟 10 国首都之间最短距离是多少？"这样的问题，GPT-5.6 会自动搜索各首都的地理坐标，然后编写 Python 代码计算所有首都对之间的大圆距离，最终找出最近的一对。类似地，在"搜索比特币过去一个月的走势并进行技术分析"这样的任务中，它可以从多个金融数据源获取实时价格数据，利用专业技术分析库计算移动平均线、RSI、MACD 等技术指标，生成可视化图表，并给出交易建议。
>
> 更重要的是，GPT-5.6 在模型层面内化了 **OpenAI Deep Research** 产品的设计哲学，引入了**意图澄清流程**。面对一个研究请求，GPT-5.6 不会立即开始执行；它首先通过一系列问题澄清用户的真实意图。对于"搜索比特币过去一个月的走势并进行技术分析"，它会先问："你偏好哪个数据源？你希望分析哪些技术指标？"这种交互式澄清使 GPT-5.6 能够产出更精准、更符合用户实际需求的研究报告。
>
> GPT-5.6 是"模型即智能体"的成熟案例——网络搜索、代码解释器等 Responses API 的内置工具在服务端闭环执行；编排循环从客户端移到了 API 服务器，简化了客户端实现。模型仍然发出标准工具调用；客户端只是不再需要自己搭建"搜索—阅读—分析"的编排框架。其最值得关注的是意图澄清机制：模型不立即执行任务，而是先确认用户真正需要什么，再制定研究策略。"用户说了什么"与"用户真正想要什么"之间的差距，在执行开始之前就被弥合了。
>
> 需要注意的是，本实验不绑定任何特定厂商。没有 OpenAI 额度的读者可以用提供同等托管工具的服务商复现。例如，阿里云百炼的 qwen3.7-plus Responses API 同样包含内置的 `web_search` 和 `code_interpreter`；Kimi K3 由 Formula 托管的搜索和 `code_runner` 提供同类能力。

## Harness 工程：围绕模型构建可靠系统

至此你已经理解了智能体的核心运作方式：LLM 运行 ReAct 循环，以上下文为引导，使用工具完成任务。上面的实验表明基本机制是可行的——同时也暴露了它有多脆弱。模型可能产生幻觉（编造不存在的工具或参数）、选错工具，或无法从错误中恢复。从一个能跑的演示到一个可靠的产品之间存在相当大的鸿沟，而这些脆弱性恰恰是 Harness 工程要解决的问题。本章前半部分回答了智能体是什么；后半部分回答智能体如何在生产环境中可靠运行。

前几节确立了核心公式：**智能体 = LLM + 上下文 + 工具**。它描述了智能体的**内部构成**：推理引擎、工作上下文和动作接口。Harness 工程在同一系统上增加了第二个、**实现层面**的视角：将 LLM 视为一个核心组件（Model），把围绕它构建的所有支撑代码称为 Harness。两种视角并非对立，而是在不同抽象层次描述同一个系统。我们切换到更通用的"Model"一词，是因为 Harness 工程的原则适用于任何能推理和调用工具的模型，而非某一特定类型。Harness 的核心是原公式中的"上下文 + 工具"，外加三层保障：**约束（Constrain）**（智能体可以和不可以做什么）、**验证（Verify）**（它是否正确地做了事）和**修正（Correct）**（做错了如何恢复）。

展开为方程，完整的生产级构成为：

> **Agent = Model + Harness**
>
> **Harness = Context management + Tool interfaces + Constraints + Verification + Correction**
>
> **Agent ↔ Environment**

一个最小演示只需要一个 Model 和一个能构建上下文、暴露工具的 Harness；生产系统必须在同一边界内添加约束、验证和修正。例如，一个退款智能体可以将策略放入上下文，用权限和金额规则约束调用，对照数据库状态验证结果，并在超时后重试或回退。Harness 工程研究的正是这种运行时和治理代码——位于 Model 之外、Agent 边界之内。

更精确地说，Harness 并非模型之外的一切：它是**位于 Agent 边界内、Model 之外**的运行时和治理层。它介导 Model 与 Environment 的交互，但不包含 Environment 本身。工具定义、调用适配器、沙箱权限和重置机制属于 Harness；沙箱内变化的文件和进程、外部数据库、网页、用户和物理世界属于 Environment。部署位置不会改变这一概念边界。Harness 的核心是上下文管理和工具接口，围绕它们构建三类工程保障：

| 组件 | 职责与设计原则 | 实际示例 | 参见章节 |
|---|---|---|---|
| **上下文管理** | 提供相关信息。**信息充分性：**在每一步都给予智能体足够的信息以做出知情决策。 | 系统提示词、知识库、智能体状态栏、Sidecar 旁路查询 | 第 2、3 章 |
| **工具接口** | 定义模型如何行动。**清晰的接口：**使用直观的工具名称、提供参数示例、说明每个工具的限制。 | MCP 工具、代码解释器、搜索工具 | 第 4 章 |
| **约束** | 定义智能体被允许做什么。**默认安全（Fail-safe）：**在明确启用之前保持能力关闭，类似手机应用权限。 | Claude Code 默认在工具执行前要求用户授权。 | 第 4 章 |
| **验证** | 检查工具执行是否产生了正确结果。**输入隔离：**基于结构化数据（如工具返回的字段）做安全检查，而非可能被攻击者通过提示注入影响的模型生成文本。 | 代码检查（Linting）、类型检查、工具结果校验 | 第 5、6 章 |
| **修正** | 从错误中恢复或回滚失败操作。在向用户呈现失败之前先尝试恢复——例如，重试失败的工具调用，而非展示不完整的结果。 | 自动重试、恢复生成、多次失败后升级给人类（熔断器） | 第 2、5 章 |

基本的模型控制循环如下方伪代码所示：

```python
observation = Environment.observe()
trajectory = [observation]
while true:
	actions = Model(Harness.build_context(trajectory))
	if len(actions) == 0:
		break
	allowed_actions = Harness.constrain(actions)
	observation = Environment.apply(allowed_actions)
	if not Harness.verify(Environment):
		observation = Harness.correct(Environment)
	trajectory.append(allowed_actions, observation)
```

这个骨架刻意省略了实现细节。完整的 API 消息循环见第 2 章；工具和自动验证分别在第 4、5 章介绍。

上下文和工具让智能体能够完成任务——理解任务并据此行动。约束、验证和修正则确保它可靠、安全地完成任务——它们不是上下文和工具之外的附加物，而是让上下文和工具在生产环境中可靠运转的工程实践。沿着智能体产品的成熟度曲线，这两组要素的侧重点会逐渐转移。

早期的智能体框架聚焦于上下文和工具：给模型工具，给它上下文，让它完成任务。生产级系统已将重心转向约束、验证和修正：确保工具调用安全、上下文得到管理、错误可以恢复。

以 Claude Code 为例。其 Harness 代码的绝大多数在做约束、验证和修正，而非上下文和工具——工具本身（文件读写、命令执行、搜索）只是很小一部分；围绕它们构建的保障机制才是真正的核心。这些机制包括：

- **过程状态管理**：跟踪智能体当前正在执行的步骤
- **多层上下文压缩**：信息过多时自动裁剪
- **权限分类**：控制哪些操作需要用户确认
- **熔断器（Circuit Breaker）**：多次错误后自动停止重试，防止一次失败操作级联影响整个系统
- **错误恢复机制**：捕获异常、回滚到最后一个稳定状态、重试，或交由人类处理

**行业正从"完成任务"转向"可靠地完成任务"，使 Harness 工程成为智能体系统的核心竞争力。**

### 从 Prompt 工程到 Loop 工程：工程范式的演进

回顾 AI 应用工程的发展，一条清晰的演进脉络浮现：

**Prompt Engineering（提示词工程）** 是第一波创新——通过打磨喂给模型的自然语言指令来提升输出质量。

**Context Engineering（上下文工程）** 是第二波——认识到仅优化提示词不够：模型能看到的一切信息（系统指令、工具定义、对话历史、外部知识）都必须被系统地管理。

**Harness Engineering（Harness 工程）** 是第三波——将视野从"模型接收什么信息"扩展到"模型运行在什么类型的系统中"，纳入模型之外的所有基础设施：约束机制、验证方法、反馈回路、错误恢复。

**Loop Engineering（循环工程）** 随之而来，将视野从单次运行扩展到跨运行的持续自主运行：谁来发现下一项工作、何时验证、任务何时才算真正完成（第 10 章将与多智能体协作系统一起展开这一主题）。

2026 年 7 月，业界开始使用 **Graph Engineering（图工程）** 来描述更高层次的编排视角：将智能体循环、确定性程序和人工审批组织成一张显式执行图，其中节点提供能力，边定义路由和依赖关系，结构化状态沿这些边流动并在关键边界处持久化[^ch1-graph-engineering]。

[^ch1-graph-engineering]: Josh C. Simmons 在 2026 年 7 月 4 日的文章 *We Are Entering the Graph Engineering Phase* 中明确使用了这个名称，从节点、带类型的边和带检查点的状态三个维度加以总结。7 月 18 日，Peter Steinberger 关于讨论是否已从循环转向图的提问，进一步推动了这一名称的传播。这些实践早于这一标签：LangGraph、Microsoft Agent Framework 和 Google ADK 的官方文档都将它们描述为图编排或基于图的工作流。参见 https://www.drjoshcsimmons.com/writing/we-are-entering-the-graph-engineering-phase、https://x.com/steipete/status/2078277297791189132、https://docs.langchain.com/oss/python/langgraph/overview、https://learn.microsoft.com/en-us/agent-framework/workflows/ 和 https://adk.dev/workflows/。

这五个阶段不是替代关系，而是嵌套的层次：Prompt Engineering 是 Context Engineering 的子集，Context Engineering 是 Harness Engineering 的子集，Harness Engineering 是 Loop Engineering 的子集。Loop Engineering 又是 Graph Engineering 的子集：单个智能体循环构成执行图中的一个节点。每一层都比上一层扩大了工程师的关注范围和影响力。**当模型能力趋于收敛、不再成为决定性的差异化因素时，竞争优势就转移到模型之外的工程上。**

近期的工程实践支持这一观点。LangChain 在 Terminal Bench 2.0（一个评估智能体在终端环境中完成复杂任务能力的基准测试）上的工作就是一个引人注目的例子：他们的编程智能体从 52.8% 提升到 66.5%（排名从前三十之外跃升至前五）。改变的不是模型，而是 Harness——让智能体检查自己的执行结果、检测自己何时陷入重复循环，并优化其推理策略。

### 构建高效智能体的核心原则

基于 Anthropic 的经验，成功的智能体系统遵循三条核心原则[^ch1-anthropic-building-effective-agents]。

**保持简单。** 从最简单的方案开始，仅在真正必要时才增加复杂度。直接调用 API 优于复杂的框架；清晰的代码优于巧妙的抽象——每多一层抽象，调试时就多一个盲区。

**保持透明。** 清晰展示智能体的规划步骤、执行日志和决策轨迹。这不只是调试的便利，更是用户信任的前提——黑盒内部的错误很难从外部定位或修复。

**设计良好的工具接口（ACI，智能体-计算机接口）。** ACI 意味着从智能体的视角设计接口——让智能体易于理解和使用——而非从程序员的视角，如传统 API 那样。工具名称和参数应当直观，在容易被误用的地方，设计应当从一开始让错误不可能发生：SIM 卡的缺口使其只能以一个方向插入卡托，微波炉门开着时拒绝加热。在制造业中，这种方法被称为 **poka-yoke（防错法）** 或 **mistake-proofing（防呆）**：通过设计产品和流程来防止错误或使错误立即显现。它被丰田生产体系所采用[^ch1-poka-yoke]。一个设计不良的工具可以让最强大的模型反复失败：接口是模型与工具之间唯一的通道，模糊的接口会被放大为系统性错误。

[^ch1-poka-yoke]: Toyota UK, ["Poka-yoke – Toyota Production System guide"](https://mag.toyota.co.uk/poka-yoke/)；American Society for Quality (ASQ), ["What Is Mistake Proofing?"](https://asq.org/quality-resources/mistake-proofing)。两者都将防错定义为防止错误或在其发生时立即检测。

[^ch1-anthropic-building-effective-agents]: Anthropic. "Building effective agents", December 2024. https://www.anthropic.com/engineering/building-effective-agents

接下来三节涉及 Harness 工程中三个独立但重要的主题：模型选择、编排模式、护栏与安全。它们都不属于 Harness 的五个要素本身，但在工程实践中不可避免。

### 如何选择模型
