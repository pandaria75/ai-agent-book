# AI 智能体入门 [第 4/5 篇]

在讨论编排模式之前，我们首先需要回答一个实际问题：什么样的模型应该驱动你的智能体？

模型是智能体智能的基础，选对模型往往比任何提示词调优都更重要。模型发布节奏太快，具体版本推荐很快就会过时，因此本节提供方向而非版本清单。

**闭源模型。** 当前智能体开发中最常用的两个闭源模型提供商是 OpenAI（GPT/o 系列）和 Anthropic（Claude 系列）。闭源模型通常能力领先，但价格更贵，且受制于厂商的 API 政策。选择模型时，不要只依赖排行榜；**在你自己的任务上评估它**（见第 7 章）。

**开源模型。** 截至本书写作时，开源模型落后闭源模型不超过六个月，而成本却低得多。如果业务场景不要求最高的模型能力，开源模型是务实之选。开源模型成本低、支持私有部署、可微调定制，适合成本敏感型场景或有数据合规要求的场景。DeepSeek、Kimi 和 GLM 是国内智能体能力较强的模型。注意不同模型的工具调用能力差异很大，务必在你的具体场景中测试后再做决定。

**除了能力，还要考虑模型的政策边界。** 一个模型可能具备执行某项任务的技术能力，但承载它的产品不一定允许用户调用这种能力。不同厂商在网络安全、模型蒸馏、模型提取、私有数据和高风险操作上划定的政策边界各不相同；同一任务在聊天产品、编程智能体和 API 中也可能产生不同结果。因此，模型选择不能只比较准确率、价格和速度。要在你的真实任务上测试：模型是否愿意继续执行、接口是否暴露了所需能力、服务条款是否允许预期用途。对业务关键任务，应准备人工接管或另一个合规模型作为回退。

**大多数智能体需要支持推理的模型。** 智能体要做复杂决策——多步推理、工具选择——而没有推理能力的模型在这些任务上往往表现不佳。例外很少：单一的简单步骤，或本质上就是点击固定位置的计算机操控 GUI 操作，非推理模型或许够用。一旦涉及多步推理或动态决策，推理模型就是必需的。

**考虑输出速度和多模态能力。** 除了成本，还有两个容易被忽视的维度。一个是**输出 token 速度**：智能体通常要运行多轮推理，每轮必须完成才能开始下一轮，因此输出速度直接决定端到端延迟——一个 20 轮的智能体任务每轮多花 2 秒就意味着多等 40 秒。另一个是**多模态支持**：如果你的智能体需要理解图像、音频或视频，多模态能力就是硬性要求，而模型在这方面差异很大。

### 编排模式：工作流 vs. 自主智能体

编排模式是 Harness 组织其"上下文与工具"层的方式——它决定上下文如何在 LLM 调用之间流动、工具如何被调度，以及智能体的执行路径是预先固定还是动态生成。智能体编排经历了从简单到复杂的演进，每种模式都有适合的场景和取舍。在 Anthropic 与数十个团队构建 LLM 智能体的经验中[^ch1-anthropic-building-effective-agents]，最成功的实现很少使用复杂框架；它们使用简单、可组合的模式。

构建 LLM 应用时，应遵循从简单到复杂的原则。先考虑单次 LLM 调用。如果更好的提示词和上下文示例就能解决问题，就不要引入智能体系统。当需要多步处理时，对于能清晰分解为固定子任务的场景，考虑使用工作流。只有在需要动态决策和灵活执行路径时，才使用自主智能体。记住，智能体系统通常以延迟和成本换取更好的任务表现，所以要仔细权衡这笔交易是否值得。

一个常见的反面教材是上来就构建一个高度复杂的工作流或多智能体系统。例如，当被要求设计一个"从百万条聊天消息中提取个人记忆"的智能体时，一些 AI 模型会迅速勾勒出一条看似严谨的流水线：先分段对话，然后依次分配提取、证据验证、身份消解、记忆策展和合并审查智能体，最后构建事实图谱、覆盖清单和不可变版本。每个组件单独看都有道理，但合在一起就构成了一个低效且不可靠的系统。因为复杂工作流的执行拓扑是固定的，每个新异常都容易导致增加一个节点：架构越来越复杂，通用性却越来越差。本可以由模型从上下文做出的语义判断，反而被硬编码进了工作流。

因此，**Harness 的重要性并不意味着越复杂的 Harness 越好**。Manus 网站将这一取舍总结为"Less structure, more intelligence"（更少的结构，更多的智能）[^ch1-manus-less-structure]。先给一个有能力的智能体一个清晰的目标、必要的上下文和可组合的工具，用自然语言告诉它一个人类会如何验证证据、做比较、解决冲突。程序只应硬编码必须始终成立的边界，如权限、绝不覆盖原始素材、原子化发布。只有当业务约束本质上要求，或评估反复暴露某种稳定的失败模式时，才应将相应步骤提升为专门的验证器、独立智能体或确定性流程。好的结构不是替智能体预演所有思考；它守住边界，把边界内的决策空间还给模型。

[^ch1-manus-less-structure]: Manus, "Less structure, more intelligence." https://manus.im/

#### 工作流模式：确定性编排

**工作流（Workflow）** 是通过预定义代码路径编排 LLM 和工具的系统。其执行路径是确定性的，由开发者预先设计——每一步的行为和状态转移在代码中定义；LLM 只负责每个节点内部的理解和生成。

例如，一个机票预订智能体可以使用一个包含四个固定节点的工作流：

1. **验证用户身份**——调用身份验证 API，确认用户是谁。
2. **搜索可用航班**——根据用户需求查询航班数据库。
3. **完成支付**——调用支付接口扣款。
4. **确认预订**——调用预订 API 锁定座位，并向用户发送确认信息。

每个节点内部可以使用 LLM（例如用自然语言理解用户的出行需求），但节点之间的流转顺序由代码固定——系统不会在支付完成前预订座位，也不会在身份验证前开始搜索航班。

工作流模式有两个核心优势。第一，**严格的流程控制**：开发者可以保证关键步骤绝不会被跳过或乱序执行——"未支付不预订"这样的业务规则由代码强制执行，而非交由 LLM 判断。第二，**安全性**：由于执行路径是确定性的，提示注入或模型错误最多只能影响当前节点内部的处理；它无法让智能体跳到不该到达的分支。攻击面被限制在单个节点内。

工作流的主要局限是**缺乏灵活性**。当发生预期之外的事件——例如用户在支付过程中更改预订，或航班取消后系统需要推荐替代方案——固定路径无法自行适应；它只能走预设的异常分支，或把控制权交还给人类。

来看最简单的工作流例子：**文生图生成**。用户的需求通常是一句朴素的自然语言，比如"给我画一幅 AGI 实现后程序员工作时的场景"；但 Stable Diffusion 这类文生图模型只接受特定风格的提示词——逗号分隔的英文标签、质量词、负向提示词。因此工作流在用户和图像生成模型之间放了两个固定节点：

1. **提示词改写**——用 LLM 将用户的自然语言请求改写为文生图模型期望的提示词格式。对于上面的例子，"AGI 实现后程序员工作时"是一个非常宽泛的需求，所以 LLM 还需要仔细思考（例如"AGI 实现后程序员不再需要写代码，所以画面应展示一个程序员在海滩上晒太阳，通过脑机接口指挥 AI 员工"），然后产出具体的场景描述。
2. **图像生成**——用改写后的提示词调用文生图模型，获得图像。

执行路径是硬编码的。这个工作流中的 LLM 节点执行的是**翻译**——把人类语言转换为工具能理解的输入格式——它之所以存在，是因为文生图模型"听不懂大白话"。专门修补工具（或模型）这类能力短板的 Harness 代码，可以称为**适配器层（adapter layer）**。

但如果把图像生成工具换成具有**原生图像生成**能力的多模态模型，如 Nano Banana 2 或 GPT-Image 2，提示词改写就不再需要了。无论用户怎么表述需求，模型都能自行理解并直接生成图像。

> **实验 1-4 ★：文生图工作流 vs. 原生图像生成**
>
> 通过两条路径发送相同的自然语言请求。**工作流路径**：LLM 先将请求改写为 Stable Diffusion 风格的提示词，然后调用文生图模型生成图像；**原生路径**：将原句直接发送给支持原生图像生成的多模态模型（如 GPT-Image 2），一次调用即生成图像。
>
> 对比两件事：提示词改写节点把原始请求变成了什么，以及哪条路径的图像更贴近原始请求。值得对比两类请求：一类是具体的（例如指定文案的海报），一类是宽泛的（如上面的 AGI 工作场景）——对于后者，工作流路径可能仍有自身的优势。

这个实验表明，**Harness 中修补模型能力短板的部分，会随着模型变强而被模型自身内化**。仅在本章中，这就已经发生过多次：少样本示例和"让我们一步步思考"之类的提示技巧被指令微调和推理模型内化；输出格式修复和 JSON 解析容错被结构化输出和原生工具调用内化；文生图提示词改写被模型的原生多模态理解与生成能力吸收。每一轮内化都消灭了一类"翻译"和"脚手架"式的适配器层代码。

#### 自主智能体：运行时决策

当工作流的固定路径不够用时，我们需要**自主智能体**。自主智能体与工作流的核心区别在于：执行路径不是预先定义的，而是在运行时由智能体根据**环境反馈**决定。

回到机票的例子，自主智能体不需要四个预定义节点。用户说"帮我订一张下周三去上海的机票"，智能体自行动态决定顺序：它搜索航班，发现需要登录，先验证身份，再恢复搜索。如果最便宜的航班有中转，它可以询问是否可以接受；如果用户说不行，它就调整搜索条件。

因此自主智能体必须自行规划——选择自己的执行步骤——并能识别失败、改变策略，而非一出错就直接停止。但自主性不是无边界的：必须设计显式的**停止条件**（任务完成、达到最大迭代次数、遇到不可恢复的错误），否则智能体可能陷入无限循环，或在任务完成后仍在继续执行。

从实现角度看，自主智能体本质上就是一个 LLM 在循环中使用工具，持续获取环境反馈以推进任务——这就是前文介绍的 ReAct 循环。常见的退出条件包括：调用了最终输出工具、模型返回不带任何工具调用的响应、遇到错误或达到最大轮数。

![图 1-6：自主智能体的执行循环](images/fig1-6.svg)

自主智能体特别适合开放式问题——那些难以预测需要多少步骤的问题。典型用例包括：编程智能体解决 SWE-bench（软件工程基准，评估智能体自动修复真实 GitHub issue 能力的基准测试）任务、"Computer Use"智能体像人类一样操作计算机界面、需要迭代搜索和分析的研究任务。

自主性也意味着更高的成本，且错误会累积。因此部署自主智能体需要在沙箱中进行充分测试、设置适当的护栏和监控，并在关键决策点设置人工介入检查点。

#### 选择与混合两种模式

在实践中，工作流和自主智能体并非互斥——许多系统将两者混合：合规要求严格的关键流程以工作流运行以保证可靠性，需要灵活决策的部分则切换到自主模式。例如，n8n 是一个成熟的开源工作流自动化框架，开发者通过在可视化画布上排列功能组件来构建智能体——工作流节点和自主智能体节点可以在同一系统中并存。

![图 1-7：n8n 工作流编辑器界面](images/n8n-workflow.png)

另一种混合方式是**先让自主智能体编写工作流，再由工作流来执行**。阅读任务后，智能体自行决定拓扑并生成一段编排代码；代码生成之后，执行阶段就回到工作流的确定性上。这样既保留了自主智能体面对陌生任务的灵活性，又不必让模型在每次调度时都做决策。第 10 章将详细讨论这种形式。

#### 主流智能体框架简要对比

下表总结了广泛使用的智能体框架和平台，帮助读者为自己的场景识别合适的选择：

| 框架/平台 | 核心定位 | 编排模式 | 开发方式 | 适用场景 |
|---|---|---|---|---|
| **Codex Harness** | Codex 背后的开源智能体运行时 | 自主 | 代码优先，可嵌入自有应用 | 编程智能体、将智能体嵌入自己的产品 |
| **Claude Agent SDK** | 生产级智能体开发框架 | 自主 | 代码优先 | 复杂自主任务、编程智能体 |

| **DeepSeek Harness** | 智能体自进化框架 | 一切皆插件 | 代码优先，易于定制 | 智能体开发者、研究人员 |
| **Pi** | 极简编程智能体框架 | 自主 | 代码优先，易于定制 | 智能体开发者 |

前两行需要单独说明。Codex 是 OpenAI 的编程智能体产品（App、CLI、IDE 插件），Codex Harness 是驱动所有这些形态的运行时层[^ch1-codex-harness]。Codex Harness 提供三条集成路径：`codex exec` 适合脚本和 CI 中的一次性任务；Codex SDK 适合启动、恢复和流式传输任务的第三方应用代码；app-server 通过 JSON-RPC 协议提供持久会话、事件流和审批回调，适合将智能体直接构建到产品中。Claude Agent SDK 和 Claude Code 是类似的关系，只是 Claude 开放的是 SDK 接口——Harness 实现本身不开源。

[^ch1-codex-harness]: OpenAI. "Codex as a platform: build on the open agent harness", August 2026.

智能体框架演进很快。当你读到本书时，其中一些框架可能已经过时，新的框架可能正流行。因此，学习某个特定框架的 API 并不重要。选择框架时，关键问题不在于它有多精巧，而在于它的抽象是否足够薄，让你能专注于业务逻辑。

编排模式解决的是 Harness 内部上下文和工具的组织方式——LLM 调用、工具和数据流如何衔接。但完成任务还不够；任务还必须被正确且安全地完成。因此我们转向护栏（Guardrails），它将约束、验证和修正付诸实践。

### 护栏与安全

护栏实现了 Harness 的约束、验证和修正机制，提供分层防御，使智能体行为保持安全可控。设计良好的**护栏**有助于管理数据隐私风险（例如防止系统提示词泄露）和声誉风险（例如保持模型行为与品牌一致）。从你已经识别的风险对应的护栏开始，然后随着新漏洞的出现逐步增加新的护栏。

把护栏视为纵深防御。单一护栏可能都不够，但几个专门的护栏组合起来能让智能体系统韧性大增。

护栏还有另一种失败模式：**误拒（false refusal）**。为降低放行危险请求的概率，模型也可能拒绝合理但看起来敏感的工作，例如授权的安全测试或模型蒸馏研究。因此，护栏评估不仅应测试禁止的请求是否被拦截，还应测试明显允许的请求是否仍能完成。

#### 护栏的类型

护栏可以放置在三个层次：**上下文层、执行层和数据层**。这三个层次的排序依据不是它们在请求生命周期中的位置，而是**被绕过的难度**——层次越低，越不依赖模型自身的判断，单次成功的攻击就越难穿透。本书以这个三层框架来组织后续的安全讨论。
