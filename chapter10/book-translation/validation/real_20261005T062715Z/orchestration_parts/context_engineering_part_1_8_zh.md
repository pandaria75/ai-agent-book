# 上下文工程

如第 1 章所述，智能体只能基于其可获取的信息来行动。对这些信息进行设计和管理，被称为**上下文工程**。上下文是 AI 在你与其交互时实际"看到"的全部信息。它不仅包括对话历史，还包括开发者编写的行为规则（系统指令）、可供 AI 使用的外部能力描述（工具描述），以及其他信息。从第 1 章引入的驾驭层视角来看，上下文工程是驾驭层"上下文与工具"层的核心实现：它决定了智能体在每个决策点看到什么信息，以及这些信息如何被组织。设计良好的上下文能够提供智能体将推理能力应用于特定任务所需的信息。

## 上下文：决定智能体能力的关键

大语言模型在标准化基准测试中能取得优异表现，但在真实的业务场景中往往令人失望。这是因为具体任务需要背景信息——例如产品架构、业务规则和内部惯例——而通用模型根本不知道这些。

设想一位能力很强的工程师加入一个新团队。他可能拥有深厚的理论知识和出色的编程能力，但还不了解产品架构、业务逻辑、技术债务或团队规范。如果关键的架构决策散落在个人记忆中，代码库又缺乏文档，即使再出色的工程师也难以快速交付价值。今天的智能体面临同样的问题。

考虑一个编程智能体。在收到同样的指令"帮我修复这个 bug"时，智能体获得的上下文质量决定了它能否完成任务：

- **代码上下文**：代码库结构、模块职责、核心数据结构和编码规范。缺少这些信息，智能体可能会产出语法正确但与项目风格或架构不一致的代码。
- **流程要求**：Git 分支策略、提交规范、代码审查流程和 CI/CD 要求。缺少这些信息，智能体可能会将未经测试的代码直接提交到主分支。
- **环境配置**：开发环境设置、测试数据库连接串、测试环境部署流程以及 API 密钥管理实践。缺少这些信息，一个本地运行正常的修复可能在测试环境中立刻失败。

这三类信息——代码、流程和环境——构成了智能体高效工作所需的最小上下文。这里进入上下文的是对环境的观察、描述或配置，而非环境本身；环境仍然是智能体与之交互的外部对象。模型自身的能力只是基础；**上下文质量才是智能体能力的真正关键**。一个中等能力的模型配上组织良好的上下文，往往能胜过一个能力更强但上下文不足的模型。

因此，上下文工程是用当今模型构建高效智能体的核心所在。它不仅仅是在提示词中添加更多文本，而是需要系统性地设计、组织和提供模型完成任务所需的背景知识。

上下文工程不仅仅是一个**技术问题**，也是一个**组织问题**。在许多团队中，关键知识仍然是隐性的：架构决策存在于资深工程师的记忆中，业务规则通过非正式方式传递，重要上下文埋藏在私人聊天记录里。如果团队本身就是一个糟糕的信息环境，再强的智能体也会受到限制。

**在远程协作中高效运转的团队，往往也能为智能体提供高效的环境。** Linux 内核这样的开源项目就是很有启发性的例子：分布在全球各地的开发者已经维护这个项目超过三十年。这之所以可行，是因为项目拥有透明、以文档驱动的沟通文化。讨论是公开的，决策被记录在案，新人可以通过阅读历史来了解代码的演变。这种工作方式天然创造了对 AI 友好的环境：信息是公开的、可检索的、结构化的。

每当智能体开始执行任务时，都应把它当作一位新团队成员来对待。有了充足的背景信息，它能产出高质量的工作；没有这些背景，它的大部分智能就会被浪费。因此，建设一支 AI 原生团队首先是一项文档工作，而不仅仅是部署新工具的问题。

OpenAI 研究员翁佳怡（Jiayi Weng）对此有非常清晰的表述：**"无论对人还是对模型，最重要的都是上下文。"** 反思自己的工作时，他说道："我在 OpenAI 的工作并不难。如果别人拥有我所有的上下文，他也能做同样的事。"这一原则同样适用于智能体：一个智能体在业务中创造的价值，往往不取决于模型大小，而取决于每个决策点提供的上下文的完整性和精确度。翁佳怡还观察到，团队协作的核心问题是上下文的不一致，而 AI 短期内无法替代人类的一个原因是 AI 与人类并不共享同一个环境。上下文工程正是要解决这个问题：如何系统性地将智能体所需的结构化背景信息传递给模型。

推理-行动被广泛认为是基于大语言模型构建智能体的奠基性工作之一。该论文的开篇第一句话就点明了智能体、环境、上下文和行动之间的关系[^ch2-react]：

> Consider a general setup of an agent interacting with an environment for task solving. At time step $t$, an agent receives an observation $o_t \in \mathcal{O}$ from the environment and takes an action $a_t \in \mathcal{A}$ following some policy $\pi(a_t \mid c_t)$, where $c_t=(o_1,a_1,\ldots,o_{t-1},a_{t-1},o_t)$ is the context to the agent.

在这个定义中，最重要的不是那些符号本身，而是**智能体的下一步行动取决于截至当前累积的完整交互上下文，而不仅仅是紧邻其前的输入**。对于大语言模型智能体而言，用户消息和工具执行结果是环境返回的观察，而模型回复和工具调用请求是智能体采取的行动；这些观察与行动交替出现，累积形成交互历史。在实际的 API 请求中，系统提示词和工具定义会被放在这段历史之前，共同构成模型在当前轮次接收到的上下文。由于模型 API 是无状态的，智能体框架必须为每次调用重建足够的上下文。最直接的无损方式是包含迄今为止的完整消息历史；生产系统可能会对其摘要压缩，但绝不能静默丢弃用于决定下一步行动所需的信息。本章后面介绍的所有上下文布局、状态栏和压缩技术，都可以视为对同一个问题的回答：如何以更低的成本为模型提供信息量足够充分的 $c_t$？

[^ch2-react]: Yao, Shunyu, et al. "ReAct: Synergizing Reasoning and Acting in Language Models." *ICLR*, 2023. https://arxiv.org/abs/2210.03629

接下来的问题是，这些上下文信息在技术层面如何提供给大语言模型。

## 智能体如何调用大语言模型：API 层面的上下文结构

本节以 OpenAI 的 Chat Completions API 作为具体示例。Anthropic、Google 及其他提供商在细节上有所不同，但它们面向智能体的 API 遵循相似的模式：每次模型调用都由结构化对话历史加上一组可用的工具定义构成。理解这一结构是掌握本章后续讨论的上下文工程技术的基础。

### 四种消息角色

在 Chat Completions 风格的 API 中，核心输入是一个**消息列表**，通常命名为 `messages`。每条消息都有一个 `role` 字段，用来告诉模型如何解读这条消息及其来源：

- **system**：开发者编写的指令，定义智能体的身份、行为、约束和工作流程。模型将其视为高优先级指令。在大多数对话中，system 消息只在消息列表开头出现一次。
- **user**：来自最终用户的输入，代表智能体需要处理的请求。
- **assistant**：模型之前的输出，包括自然语言回复和工具调用请求。在多轮交互中，这些消息会被包含在后续请求中，以便下一次无状态的模型调用能够访问之前的轨迹。
- **tool**：智能体框架执行工具后返回的结果。每个工具结果通过 `tool_call_id` 与相应的工具调用关联，使模型能够将每个结果与产生它的请求对应起来。

工具定义不是消息。它们通过单独的 `tools` 字段提供，该字段声明模型可用的工具并指定每个工具接受的参数。

这与第 1 章介绍的"上下文的五个组成部分"是同一套 API 请求结构，只是从不同的角度进行了归类：`system`、`user`、`assistant`、`tool` 四种消息角色分别对应系统提示词、用户消息、助手消息和工具结果。剩下的一个组成部分——工具定义——是通过顶层的 `tools` 字段传递的，而非消息角色。因此，"四种消息角色 + `tools` 字段"恰好涵盖了第 1 章的五个上下文组成部分。

### 单轮请求：最简单的 API 调用

![图 2-2：单轮 API 调用的请求与响应结构](images/fig2-2.svg)

先看最简单的情况，不涉及工具调用：用户问"你好，你是谁？"本示例使用本地部署的 Qwen3-0.6B 模型：

```javascript
// ══ Request constructed by the Agent framework ══
{
  "model": "Qwen3-0.6B",
  "messages": [
    {
      "role": "system",                           // ← Written by developer
      "content": "You are a helpful coding assistant. Follow user instructions."
    },
    {
      "role": "user",                              // ← User input
      "content": "Hello, who are you?"
    }
  ]
}
```

```javascript
// ══ Response returned by the API ══
{
  "choices": [{
    "message": {
      "role": "assistant",                         // ← Generated by model
      "content": "Hi! I'm a coding assistant. I can help you write code, debug issues, and explain technical concepts. How can I help?"
    }
  }]
}
```

这个请求只包含两条消息：一条包含开发者编写的规则的 system 消息，和一条包含用户输入的 user 消息。模型返回一条 assistant 消息作为回复。这是最基本的大语言模型 API 交互模式：**每次调用都是无状态的，因此请求中的消息列表必须包含模型所需的全部信息**。

### 携带工具调用的多轮交互：智能体的核心循环

真实的智能体工作流通常比单轮问答复杂。当用户问"温哥华现在几点，天气怎么样？"时，模型无法仅凭自身知识回答（它不知道"现在"是几点，更不知道天气），因此必须调用外部工具。以下示例将逐步展示智能体框架与模型之间的每一步交互。

![图 2-3：两次模型 API 调用的完整交互序列](images/fig2-3.svg)

图中的两次调用指的是**对模型 API 的调用**，而非先后调用了两个工具。在本示例中，`get_current_time` 的时区参数和 `get_weather` 的城市、单位参数都可以提前确定；天气服务本身就返回该城市的最新天气，不依赖时间工具的输出，因此智能体框架可以并行执行它们。如果后续工具的参数必须来自先前工具的结果，模型就需要在后续轮次中请求该工具，两个工具必须串行执行。

**第一次 API 调用——智能体框架发送初始请求：**

```javascript
// ══ Request constructed by the Agent framework (1st call) ══
{
  "model": "Qwen3-0.6B",
  "messages": [
    {
      "role": "system",                           // ← Written by developer
      "content": "You are a helpful assistant. Use the provided tools to get real-time information when needed."
    },
    {
      "role": "user",                              // ← User input
      "content": "What's the current time and weather in Vancouver?"
    }
  ],
  "tools": [                                       // ← Tools defined by developer
    {
      "type": "function",
      "function": {
        "name": "get_current_time",
        "description": "Get the current date and time in a specific timezone",
        "parameters": {
          "type": "object",
          "properties": {
            "timezone": { "type": "string", "description": "Timezone name, e.g. America/Vancouver" }
          }
        }
      }
    },
    {
      "type": "function",
      "function": {
        "name": "get_weather",
        "description": "Get the current weather for a specific city",
        "parameters": {
          "type": "object",
          "properties": {
            "city": { "type": "string", "description": "City name" },
            "unit": { "type": "string", "enum": ["celsius", "fahrenheit"] }
          }
        }
      }
    }
  ]
}
```

这个 `tools` 列表是开发者事先注册的静态工具元数据：工具名称、描述和参数模式是写在代码中的，与用户这次恰好问什么无关。无论用户询问温哥华的天气，还是让智能体预订机票，发出的都是同一个列表；示例中只列出了两个相关工具以保持请求简短，而真实的智能体通常会一次性声明几十个工具。**智能体并没有先把用户输入拆解为"查询时间"子任务和"查询天气"子任务，再编写相应的工具描述**——这个拆解发生在模型侧，正是下文响应中的 `tool_calls`。

**模型返回工具调用请求（而非最终回复）：**

```javascript
// ══ Response returned by the API (model decides to call tools) ══
{
  "choices": [{
    "message": {
      "role": "assistant",                         // ← Generated by model
      "content": null,                             // No text response
      "tool_calls": [                              // Model requests two tool calls
        {
          "id": "call_abc123",
          "type": "function",
          "function": {
            "name": "get_current_time",
            "arguments": "{\"timezone\": \"America/Vancouver\"}"
          }
        },
        {
          "id": "call_def456",
          "type": "function",
          "function": {
            "name": "get_weather",
            "arguments": "{\"city\": \"Vancouver\", \"unit\": \"celsius\"}"
          }
        }
      ]
    }
  }]
}
```

模型此时并没有回答用户的问题，而是返回了两个**工具调用请求**：一个查询当前时间，一个查询天气。由于这些请求相互独立，智能体框架可以并行执行它们。**模型发出调用请求，智能体框架执行实际调用。**这种职责分工是智能体架构的核心：模型决定调用哪个工具、传递什么参数，而框架负责调用 API、运行代码并返回结果。

**智能体框架执行工具后发起第二次 API 调用：**

收到模型的工具调用请求后，智能体框架执行这两个工具（例如调用一个时间 API 和一个天气 API），然后将**完整的对话历史连同工具执行结果**一起发送回模型：

```javascript
// ══ Request constructed by the Agent framework (2nd call) ══
{
  "model": "Qwen3-0.6B",
  "messages": [
    {
      "role": "system",                           // ← Same as 1st call
      "content": "You are a helpful assistant. Use the provided tools to get real-time information when needed."
    },
    {
      "role": "user",                              // ← Same as 1st call
      "content": "What's the current time and weather in Vancouver?"
    },
    {
      "role": "assistant",                         // ← Model output from 1st call, included verbatim
      "content": null,
      "tool_calls": [
        { "id": "call_abc123", "function": { "name": "get_current_time", "arguments": "{\"timezone\": \"America/Vancouver\"}" } },
        { "id": "call_def456", "function": { "name": "get_weather", "arguments": "{\"city\": \"Vancouver\", \"unit\": \"celsius\"}" } }
      ]
    },
    {
      "role": "tool",                              // ← Generated by Agent framework (tool execution result)
      "tool_call_id": "call_abc123",
      "content": "{\"timezone\": \"America/Vancouver\", \"datetime\": \"2025-09-13T05:18:47\", \"day_of_week\": \"Saturday\"}"
    },
    {
      "role": "tool",                              // ← Generated by Agent framework (tool execution result)
      "tool_call_id": "call_def456",
      "content": "{\"city\": \"Vancouver\", \"temperature\": 13.2, \"unit\": \"celsius\", \"conditions\": \"clear\", \"humidity\": 93}"
    }
  ],
  "tools": [ ... ]                                 // ← Same tool definitions as above, omitted
}
```

这里有三个关键细节：

1. **第二次请求包含第一次请求的完整对话历史**——系统消息、用户消息、包含工具调用的助手消息，以及新添加的工具结果。这体现了 API 的无状态特性：智能体框架必须在每次请求中包含相关历史。
2. **第一次的 assistant 消息被原样插回消息列表**——这使下一次模型调用能够访问上一次调用中做出的工具调用决策。
3. **工具消息通过 `tool_call_id` 与相应的工具调用关联**——这告诉模型哪个结果对应哪个请求的调用。

**模型基于工具结果生成最终回复：**

```javascript
// ══ Response returned by the API (final reply) ══
{
  "choices": [{
    "message": {
      "role": "assistant",                         // ← Generated by model
      "content": "It's currently 5:18 AM on Saturday, September 13, 2025 in Vancouver.\n\nWeather: 13.2°C with clear skies and 93% humidity. It's quite cool this morning - you might want to grab a jacket."
    }
  }]
}
```

这一次，模型没有返回 `tool_calls`；它返回了文本回复，因为它判断已经掌握了足够的信息来回答用户的问题，智能体随即停止。**这个"请求 → 工具调用 → 执行 → 返回结果 → 下一次请求"的循环，就是第 1 章引入的推理-行动循环在 API 层面的实现。**

如果用户想要更多信息（例如追问"东京呢？"），智能体框架会将追问追加到对话历史末尾，再次发起模型 API 调用。模型开始再次返回 `tool_calls`，智能体框架执行它们、送回结果，如此循环往复。

### 用代码实现智能体的核心循环

既然 JSON 结构已经清楚，我们可以在 Python 中将这些步骤串联起来。以下是一个最小化的智能体实现，使用一个单一循环。
