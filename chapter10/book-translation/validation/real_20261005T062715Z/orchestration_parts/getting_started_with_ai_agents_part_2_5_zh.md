# 智能体入门 [第 2/5 部分]

"模型即智能体"范式是智能体开发的最新方向。先进模型通过后训练（尤其是强化学习）将工具调用内化为原生能力：何时调用工具、调用哪个工具、使用什么参数——全部由模型自行决定，无需人工编排。这并不意味着框架层不再重要。恰恰相反：模型越强大，周围的驾驭层就越关键。Harness 一词最初指的是套在马身上的缰绳和挽具——不是为了限制马奔跑的能力，而是为了恰当地引导这股力量。在智能体语境中，模型是强大但难以预测的马，而驾驭层则是将其能力引导为可靠任务执行的工程基础设施。它包括上下文管理、工具接口、安全约束以及验证与纠正机制（见本章最后一节）。

模型拥有的决策权越大，错误决策的影响就越大——这就要求更细粒度的约束、验证和纠正来保证其可靠性。模型提供商的真正优势不在于"让框架更薄"，而在于能够协同优化模型及其周围的驾驭层，并持续迭代。

但随之而来一个更深层的问题：如果模型不断变强，今天的驾驭层最终是否会被模型吸收？在《苦涩的教训》中，Rich Sutton 回顾了贯穿七十年 AI 研究的一种反复出现的模式[^ch1-1]：研究者一再将自己对某个领域的理解编码进系统，获得短期收益，但最终败给了能随算力和数据规模扩展的通用方法——搜索和学习。从这个视角来看，驾驭层中的约束、验证和纠正，有多少是模型注定要内化的"人类先验"？**本书认为模型将越来越多地吸收这些能力，但我们也应务实看待这一过程发生的速度。** 在方向上，我们毫不怀疑模型会持续吸收驾驭层的一部分——工具调用和长程规划曾经依赖外部编排，如今已是模型的原生能力。然而在实践中，这种吸收远比直觉所预期的缓慢：训练以月为单位推进，没有哪个模型能在单次训练中内化真实企业的所有约束和偏好。模型当前的能力边界，正是驾驭层创造价值的地方。因此，驾驭层工程不是对苦涩教训的抵抗，而是将其落实在工程时间尺度上：凡是模型尚不能可靠完成的事情，驾驭层先行覆盖；每当模型内化了又一层能力，驾驭层便卸下那一层，转而支撑下一个能力前沿。

[^ch1-1]: Sutton, Rich. "The Bitter Lesson", 2019. http://www.incompleteideas.net/IncIdeas/BitterLesson.html

#### 智能体学习机制：从上下文自适应到持久化更新

前面的讨论指出，模型可以通过强化学习将工具使用策略内化为原生能力。但智能体的行为变化并不只发生在训练期间。根据更新发生的位置以及持续时间，这些变化可以理解为三条互补的路径（图 1-2）：任务内的上下文自适应、跨任务的外部工件更新、以及训练循环中的参数更新。

![图 1-2：智能体能力更新的三个层次](images/fig1-2.svg)

**上下文自适应**发生在当前任务内。一旦示例、状态和检索结果进入上下文，模型可以立即调整其行为，但这不会改变下一个会话的持久状态。其优势是速度快、成本低；其局限则来自上下文窗口和信息组织方式。第 2 章将详细阐述这种自适应形式的工作原理。

为了使变化跨任务持久化，系统可以更新**外部工件**：事实和经验可以组织成知识文档，可用语言表达的策略可以写入提示词或 Skill，确定性流程和约束可以编码在程序和驾驭层中。这些工件可审计、可修订，但智能体在执行时仍必须通过上下文或工具接口来访问它们。第 3 至 5 章为知识和程序奠定基础，第 9 章则讨论如何从经过评估的运行轨迹中生成此类更新。

当目标是一种高维能力——例如医学影像理解、自然语言风格，或隐式决策策略——外部规则无法完全表达时，就必须通过后训练更新**模型参数**。参数更新的部署成本更高，但可以产生自然且广泛泛化的效果；第 8 章将系统介绍其方法。因此，这三条路径并非互斥的类别，而是运行在不同时间尺度上的协同机制：上下文支持即时自适应，外部工件支持受控积累，参数则内化难以显式表达的能力。

### 上下文：智能体的工作集

上下文是智能体在每个决策点可用的信息工作集。正如一个人做决策时需要桌上有合适的材料——任务指令、参考手册、之前的往来邮件、最新数据——智能体的上下文窗口就是它可以使用的信息。从 API 的角度来看（详见第 2 章），每次 LLM 调用的上下文由五个部分组成：

- **系统提示词**：与用户在对话中输入的提示词不同，系统提示词由开发者编写，在整个对话过程中保持固定。它是智能体的"职位描述"——定义其身份、权限和行为准则。对系统提示词进行精心的提示工程，正是我们塑造智能体运行行为的方式。系统提示词还承载着跨会话持久化的**用户记忆**（个性化信息，如偏好、过往行为和背景设置；见第 3 章），以及动态注入的环境状态。
- **工具定义**：声明智能体可用工具的名称、功能描述和参数格式。没有工具定义，智能体无法识别或调用任何工具——不过它也不会一言不发——一项消融实验（实验 1-1）将展示它会转而做什么。工具定义与系统提示词共同构成在整个对话中保持不变的**静态前缀**。（这是基础模式；自 2026 年起，生产框架也可以在上下文末尾按需加载完整的工具 schema 而不破坏前缀——见第 2 章的工具定义一节和第 4 章。）
- **用户消息**：来自用户的输入。用户消息还可以包含通过 RAG（检索增强生成，详见第 3 章）动态检索的**外部知识**——涵盖超出训练数据截止日期的信息或私有领域知识。
- **助手消息**：模型之前生成的响应，最多可包含三个部分——`reasoning`（内部思维链，保持连贯性和决策可解释性）、`content`（对用户的回答）和 `tool_calls`（智能体采取行动的方式）。在一次具体的响应中，这三个部分不一定同时出现：例如，当智能体决定调用工具时，通常只有 `reasoning` + `tool_calls`；当给出最终答案时，通常只有 `reasoning` + `content`。
- **工具结果**：智能体框架执行工具后返回的输出。这些结果是智能体下一步推理的直接依据——也是让它能从结果中学习而非重复犯错的原因。

前两项（系统提示词 + 工具定义）构成静态前缀；后三项（用户消息 + 助手消息 + 工具结果）构成随每次交互不断增长的动态消息历史。这五个部分共同组成每次 LLM 推理的上下文。

每个组件都真的不可或缺吗？最直接的检验方式是**消融实验**——逐一排除原因的诊断方法：去掉组件 A，看看系统是否还能工作，然后去掉组件 B，依此类推，直到每个组件的贡献都清晰明了。实验 1-1 正是将这种方法应用于上述五个组件。

> **实验 1-1 ★★：上下文的关键作用**
>
> 我们通过系统的**消融实验**探究了每个上下文组件如何塑造智能体行为。上述五个组件中，测试了四个——系统提示词作为智能体的基础身份定义，被豁免：没有它，智能体完全没有角色意识，测试将毫无意义。如图 1-3 所示，实验设置了五个对照组：一个保留所有组件的完整基线组，以及四个各缺少一个组件的组，以观察每个组件对智能体性能的影响。
>
> ![图 1-3：实验 1-1——上下文消融实验设计](images/fig1-3.svg)
>
> 实验结果揭示了每个上下文组件的作用——以及它们的重要性并不相同。**工具定义**（静态前缀的一部分）是智能体行动能力的基础；没有它们，智能体无法调用任何工具。但失去行动能力并不意味着沉默：模型仍然会返回格式整洁、措辞自信的回答，其中的数字来自参数化记忆而非观察所得，排版方式与真正从工具输出推导出的答案如出一辙。它是直接拒绝还是当场编造，主要取决于模型自身的幻觉率和诚实程度；提示词中诸如"不要自行估算比率"这样的约束可以降低编造概率，但无法杜绝。**工具结果**是闭环控制的关键；没有它们，智能体就是在"盲跑"，不断重试直至耗尽迭代预算。**推理过程**（助手消息中的推理部分）记录了*为什么*要执行某个步骤，而工具结果记录了*发生了什么*；当后者可以重构出前者时，将其从历史中移除几乎不产生任何损失。**消息历史**（之前轮次的用户消息、助手消息和工具结果）防止冗余操作，避免重复同样的错误。
>
> 实验的核心洞见：**上下文决定了智能体能"看到"什么，而智能体只能基于它看到的东西做决策。** 但各个组件并非等价；衡量标准是其承载的信息能否从别处重构——"每个组件都不可或缺"这类说法必须经过测量而非假设，而且模型迭代速度很快，同样的消融在更新的模型上很可能得出不同结论。还有一点在工程实践中更为重要：**"产出了答案"不等于"完成了任务"。** 当缺失某个上下文组件时，典型的失败不是错误退出，而是一个看起来无懈可击的答案。

### 推理-行动循环

掌握了这三个组件，一个自然的问题随之而来：它们如何协同工作？推理-行动循环是将 LLM、上下文和工具连接成一个系统的核心机制。我们来逐步剖析它。

智能体执行任务的核心模式称为**推理-行动**（Reasoning + Acting）。这个名字只提到了推理和行动，但实际的循环有三个阶段：模型首先**推理**接下来该做什么，然后调用工具进行**行动**，接着**观察**工具结果并推理下一步。这个"推理 → 行动 → 观察 → 推理 → 行动 → 观察"的循环不断重复，直到任务完成。

考虑一个具体例子——跨多种货币汇总收入——来理解智能体的**轨迹**：智能体工作过程中累积的消息历史，由用户消息、助手消息（含其推理和工具调用）以及工具结果组成。在每次 LLM 调用中，模型接收到的完整上下文是**静态前缀**（系统提示词 + 工具定义）加上**轨迹**（动态消息历史）（图 1-4）。这揭示了一个关键事实：**智能体上下文 = 静态前缀 + 轨迹**。具体而言，静态前缀是上述五个组件中的前两个（系统提示词 + 工具定义）；轨迹是后三个（用户消息 + 助手消息 + 工具结果，随每次交互增长）。LLM 从这个完整上下文中生成下一个响应，然后将其追加到轨迹中以供后续调用使用。

![图 1-4：智能体轨迹——多币种汇总任务的推理-行动循环](images/fig1-4.svg)

先看一个最小化的循环实现。它展示了**各组件如何协同工作**：模型只负责决定下一步，驾驭层负责组装上下文并验证和执行工具，环境负责产生实际的状态变更和观察结果。本书其余部分同样使用 Python 风格的伪代码；伪代码不可运行，也不对应任何特定的 SDK。可执行的具体代码在本书的配套仓库中。

```python
trajectory = [user_request]

repeat:
    context = stable_prefix + trajectory
    decision = Model(context)
    trajectory.append(decision)

    if decision has no tool call:
        return decision.answer

    for call in decision.tool_calls:       # independent calls may run in parallel
        validated_call = Harness.validate(call)
        observation = Environment.execute(validated_call)
        trajectory.append(observation)
```

以下是轨迹的结构，以伪代码表示：

```text
trajectory = [
  {role: "user", content: "Based on the company's quarterly revenue: Q1 2.5M USD, Q2 2.1M EUR, Q3 1.8M GBP, Q4 380M JPY, calculate the company's total annual revenue and average quarterly revenue"},
  
  # First iteration - LLM receives the above trajectory and generates a response
  {role: "assistant",
   reasoning: "Need to convert all currencies to USD...",
   content: "",  # No direct reply to the user
   tool_calls: [
     {name: "convert_currency", args: {amount: 2100000, from: "EUR", to: "USD"}},
     {name: "convert_currency", args: {amount: 1800000, from: "GBP", to: "USD"}},
     {name: "convert_currency", args: {amount: 380000000, from: "JPY", to: "USD"}}
   ]},
  
  # Agent framework executes tools, adds results to trajectory
  {role: "tool", content: "EUR->USD: 2282608.7"},
  {role: "tool", content: "GBP->USD: 2278481.01"},
  {role: "tool", content: "JPY->USD: 2541806.02"},
  
  # Second iteration - LLM receives the complete trajectory, including tool results
  {role: "assistant",
   reasoning: "Conversion results obtained, now need to aggregate and calculate...",
   content: "",
   tool_calls: [
     {name: "code_interpreter", args: {code: "total = 2500000 + 2282608.7 + ..."}}
   ]},
  
  {role: "tool", content: "Total: $9,602,895.73, Average: $2,400,723.93..."},
  
  # Third iteration - LLM receives the complete trajectory and generates the final answer
  {role: "assistant",
   reasoning: "All calculations complete, summarizing results...",
   content: "FINAL ANSWER: Total revenue $9,602,895.73..."}
]
```

请注意，系统提示词和工具定义并未出现在轨迹中——它们作为静态前缀，在每次 LLM 调用前自动拼接在轨迹之前。

在我们的实验中，这个循环清晰可见。第一轮，智能体分析任务并并行调用了三个货币转换工具；第二轮，它将转换结果交给代码解释器进行计算量更大的运算；第三轮，在确认所有计算完成后，它产出了最终答案。一个复杂的多步任务在 3 次迭代和 4 次工具调用中完成。

在这种最基础的设计中，LLM 看到的上下文是不断追加的。每次 LLM 调用都收到完整的轨迹，因此模型知道自己处于任务的哪个阶段、之前尝试过什么、结果如何。正如人们在解决问题时不断回顾和总结，智能体通过轨迹保持对任务的全局视野。而且由于轨迹是结构化的——用户消息、助手消息（推理 + 工具调用）和工具结果被清晰地分离——系统具有高度的可解释性和可调试性。

了解了智能体的运行循环后，我们接下来看两个实验，观察不同模型如何驱动这个循环。
