在讨论编排模式之前，我们首先需要回答一个实际问题：应该用什么样的模型来驱动你的智能体？

模型是智能体智力的基础，选对模型往往比任何提示词调优都更重要。模型迭代太快，具体版本推荐很快就会过时，因此本节只给出方向性建议。

**闭源模型。** 当前智能体开发中最常用的两个闭源模型提供商是 OpenAI（GPT/o 系列）和 Anthropic（Claude 系列）。闭源模型通常能力领先，但价格更高，且受供应商 API 政策约束。选择模型时，不要仅依赖排行榜；**在你自己的任务上进行评估**（参见第 7 章）。

**开源模型。** 在撰写本书时，开源模型与闭源模型的差距不超过六个月，而成本却低得多。如果你的业务场景不要求最高的模型能力，开源模型是务实之选。开源模型成本低、支持私有化部署、允许微调定制，适合成本敏感或有数据合规要求的场景。DeepSeek、Kimi 和 GLM 是智能体能力较强的国产模型。需要注意的是，各模型在工具调用能力上差异较大，务必在你的具体场景中先测试再做决定。

**除了能力，还要考虑模型的策略边界。** 模型可能在技术上具备执行某项任务的能力，但托管它的产品未必允许用户调用该能力。不同厂商在网络安全、模型蒸馏、模型提取、私有数据和高风险操作等方面划定了不同的策略边界；同一任务在聊天产品、编码智能体 [待审] 和 API 中也可能产生不同的结果。因此，模型选型不能只比较准确率、价格和速度。应在真实任务上测试：模型是否愿意执行、接口是否暴露了所需能力、服务条款是否允许预期的使用方式。对于业务关键任务，要准备好人工交接 [待审] 或另一个合规模型作为兜底。

**大多数智能体需要支持推理的模型。** 智能体需要做出复杂决策——多步推理、工具选择——没有推理能力的模型在这些任务上往往表现不佳。例外很少：单个简单步骤，或者 Computer Use 中等同于点击固定位置的 GUI 操作，非推理模型 [待审] 或许够用。一旦涉及多步推理或动态决策，推理模型就不可或缺。

**关注输出速度和多模态能力。** 除了成本，有两个维度容易被忽视。其一是**词元输出速度**：智能体通常需要运行多轮推理，每一轮必须完成才能开始下一轮，因此输出速度直接决定了端到端时延——一个 20 轮的智能体任务如果每轮慢 2 秒，就意味着多等 40 秒。其二是**多模态 [待审] 支持**：如果你的智能体需要理解图像、音频或视频，多模态能力就是硬性要求，而各模型在这方面差异很大。

### 编排模式 [待审]：工作流 vs. 自主智能体

编排模式描述了驾驭层如何组织其"上下文与工具"层——它们决定了上下文如何在 LLM 调用之间流动、工具如何被调度，以及智能体的执行路径是预先固定的还是动态生成的。智能体编排已经从简单发展到复杂，每种模式都有其适用场景和权衡。根据 Anthropic 与数十个构建 LLM 智能体的团队合作的经验[^ch1-anthropic-building-effective-agents]，最成功的实现很少使用复杂框架；它们使用的是简单、可组合的模式。

构建 LLM 应用时，遵循从简到繁的原则。首先考虑单次 LLM 调用。如果更好的提示词和上下文内示例 [待审] 就能解决问题，就不要引入智能体系统。当需要多步处理时，对于能够清晰分解为固定子任务的场景，考虑使用工作流。只有在需要动态决策和灵活执行路径时，才使用自主智能体。记住，智能体系统通常以时延和成本换取更好的任务表现，因此要仔细权衡这种交换是否值得。

一个常见的反面案例是：一上来就构建一个高度复杂的工作流或多智能体系统。例如，当被要求设计一个"从百万条聊天消息中提取个人记忆"的智能体时，某些 AI 模型会迅速画出一个看似严谨的流水线：先对对话进行分段，然后依次分配提取、证据验证、身份解析、记忆整理和合并审查等智能体，最后构建事实图谱、覆盖账本和不可变版本。每个组件单独看都有道理，但合在一起却形成了一个低效且不可靠的系统。因为复杂工作流的执行拓扑是固定的，每个新异常都容易催生一个新的节点：架构变得越来越复杂，通用性却越来越差。本可以由模型从上下文做出的语义判断，反而被硬编码到了工作流中。

因此，**驾驭层的重要性并不意味着驾驭层越复杂越好**。Manus 网站将这种权衡总结为"更少结构，更多智能"。[^ch1-manus-less-structure] 首先给一个有能力的智能体一个清晰的目标、必要的上下文和可组合的工具，用自然语言告诉它人会如何验证证据、做比较、解决冲突。程序只需硬编码必须始终成立的边界，例如权限、绝不覆盖源材料、原子化发布 [待审]。只有当业务约束本身就要求如此，或评估反复暴露稳定的失败模式时，才应将对应步骤提升为专门的验证器、独立的智能体或确定性流程。好的结构不会替智能体预演所有的思考；它守住了边界，并将边界内的决策空间交还给模型。

[^ch1-manus-less-structure]: Manus, "Less structure, more intelligence." https://manus.im/

#### 工作流模式：确定性编排

**工作流**是通过预定义的代码路径来编排 LLM 和工具的系统。其执行路径是确定性的，由开发者预先设计——每个步骤和转换的行为都在代码中定义；LLM 只负责每个节点内部的理解和生成。

例如，一个机票预订智能体可以使用包含四个固定节点的工作流：

1.  **验证用户身份**——调用身份验证 API，确认用户身份。
2.  **搜索可用航班**——根据用户需求查询航班数据库。
3.  **完成支付**——调用支付接口扣除金额。
4.  **确认预订**——调用预订 API 锁定座位，并向用户发送确认。

每个节点内部可以使用 LLM（例如用自然语言理解用户的出行需求），但节点之间的流程顺序由代码固定——系统不会在支付完成之前预订座位，也不会在身份验证之前开始搜索航班。

工作流模式有两个核心优势。第一，**严格的流程控制**：开发者可以保证关键步骤绝不会被跳过或乱序执行——"未支付不得预订"这样的业务规则由代码强制执行，而非依赖 LLM 的判断。第二，**安全性**：由于执行路径是确定性的，提示注入或模型错误最多只能影响当前节点内部的处理，无法让智能体跳转到不应到达的分支。攻击面被限制在单个节点内。

工作流的主要局限是**缺乏灵活性**。当出现预料之外的事件——例如用户在支付过程中更改预订，或航班取消需要推荐替代方案——固定路径无法自行适应，只能走预设的异常分支或将控制权交还给人工。

以最简单的工作流示例来看：**文本生成图像**。用户的需求通常是一句朴素的自然语言，比如"画一幅 AGI 实现后程序员工作的场景"；但像 Stable Diffusion 这样的文生图模型只接受特定风格的提示词——以逗号分隔的英文标签、质量词、负面提示词 [待审]。因此，工作流在用户和图像生成模型之间插入两个固定节点：

1.  **提示词改写**——用 LLM 将用户的自然语言请求改写为文生图模型期望的提示词格式。就上面的例子而言，"AGI 实现后程序员工作"是一个非常宽泛的需求，因此 LLM 还需要仔细推敲（例如"AGI 实现后，程序员不再需要写代码，所以画面应该是一个程序员在沙滩上晒太阳，通过脑机接口指挥 AI 员工"），然后产出具体的场景描述。
2.  **图像生成**——用改写后的提示词调用文生图模型，获取图像。

执行路径是硬编码的。这个工作流中的 LLM 节点执行的是**翻译**——将人类语言转换为工具可以理解的输入格式——它之所以存在，是因为文生图模型"听不懂大白话"。专门修补工具（或模型）能力短板的驾驭层代码，可以称为**适配层** [待审]。

但如果图像生成工具被替换为具备**原生图像生成**能力的多模态模型，例如 Nano Banana 2 或 GPT-Image 2，提示词改写就不再需要了。无论用户如何表达需求，模型都能自行理解并直接生成图像。

> **实验 1-4 ★：文生图工作流 vs. 原生图像生成**
>
> 通过两条路径发送同一句自然语言请求。**工作流路径**：先由 LLM 将请求改写为 Stable Diffusion 风格的提示词，再调用文生图模型生成图像；**原生路径**：将原句直接发送给支持原生图像生成的多模态模型（如 GPT-Image 2），一次调用即产出图像。
>
> 比较两件事：提示词改写节点将原始请求变成了什么，以及哪条路径的图像更接近原始请求。值得比较两类请求：一类是具体的（例如带有指定文案的海报），另一类是宽泛的（如上面的 AGI 工作场景）——对于后一类，工作流路径可能仍有其自身的优势。

这一实验表明，**驾驭层中修补模型能力短板的部分，会随着模型变强而被模型自身所内化**。仅在本章中，这种情况就已多次发生：少样本示例 [待审] 和"让我们一步步思考"之类的提示词技巧被指令微调 [待审] 和推理模型内化；输出格式修复和 JSON 解析容错被结构化输出和原生工具调用内化；文生图的提示词改写则被模型的原生多模态理解与生成能力所吸收。每一轮内化，都会淘汰一类"翻译"和"脚手架"式的适配层代码。

#### 自主智能体：运行时决策

当工作流的固定路径不够用时，我们需要**自主智能体**。自主智能体与工作流的核心区别在于：执行路径不是预先定义的，而是在运行时由智能体根据**环境反馈**动态决定的。

回到机票预订的例子，自主智能体不需要四个预定义节点。用户说"帮我订下周三去上海的机票"，智能体动态决定执行顺序：它先搜索航班，发现需要登录，于是先进行身份验证，然后继续搜索。如果最便宜的航班需要中转，它可以询问用户是否接受；如果用户说不行，它就调整搜索条件。

因此，自主智能体必须自行规划——选择自己的执行步骤——并在遇到失败时识别问题、改变策略，而非在出错时简单地停止。但自主性并非无边界：必须设计明确的**停止条件**（任务完成、达到最大迭代次数、遇到不可恢复的错误），否则智能体可能陷入无限循环，或在任务已完成之后仍在继续执行。

从实现角度看，自主智能体本质上是一个在循环中使用工具的 LLM，不断获取环境反馈以推进任务——这就是前面介绍的推理-行动循环。常见的退出条件包括：调用最终输出工具、模型返回不含任何工具调用的响应、遇到错误或达到最大轮数。

![图 1-6：自主智能体的执行循环](images/fig1-6.svg)

自主智能体非常适合开放式问题——即难以预测所需步骤数量的问题。典型用例包括：编码智能体解决 SWE-bench（软件工程基准，用于评估智能体自动修复真实 GitHub issue 能力的基准测试）任务、"Computer Use"智能体像人一样操作计算机界面，以及需要迭代搜索和分析的研究类任务。

自主性也意味着更高的成本，且错误容易累积。因此，部署自主智能体需要在沙盒中进行充分测试、设置适当的安全护栏和监控，并在关键决策点设置人在回路检查点。

#### 选择与混合两种模式

在实践中，工作流和自主智能体并非互斥——许多系统将两者混合使用：有严格合规要求的关键流程以工作流方式运行以保证可靠性，而需要灵活决策的部分则切换到自主模式。例如，n8n 是一个成熟的开源工作流自动化框架，开发者通过在可视化画布上排列功能组件来构建智能体——工作流节点和自主智能体节点可以在同一系统中共存。

![图 1-7：n8n 工作流编辑器界面](images/n8n-workflow.png)

另一种混合方式是**让自主智能体先编写工作流，再由工作流来执行**。智能体在读取任务后自行决定拓扑并生成一段编排代码；一旦代码生成，执行阶段就回归到工作流的确定性。这样既保留了自主智能体面对陌生任务时的灵活性，又避免了模型在每次派发时都要做决策。第 10 章将详细讨论这种形式。

智能体框架迭代迅速。当你读到本书时，其中一些框架可能已经过时，而新的框架可能已经流行。因此，学习某个特定框架的 API 并不重要。选择框架时，关键问题不在于它有多复杂，而在于其抽象层是否足够薄，能让你专注于业务逻辑。

编排模式解决的是驾驭层内上下文和工具的组织问题——LLM 调用、工具和数据流如何连接。但仅仅完成任务还不够；任务还必须正确、安全地完成。因此我们转向安全护栏，它将约束、验证和纠正付诸实践。

### 安全护栏与安全

安全护栏实现了驾驭层的约束、验证和纠正机制，提供分层防御，确保智能体行为安全可控。设计良好的**安全护栏**有助于管理数据隐私风险（例如防止系统提示词泄露）和声誉风险（例如保持模型行为与品牌一致）。先针对已识别的风险部署安全护栏，再随着新漏洞的出现逐步补充。

将安全护栏视为纵深防御 [待审]。单一的安全护栏不太可能独自足够，但多个专门的安全护栏组合起来，能让智能体系统更具韧性。

安全护栏还有另一种失败模式：**误拒** [待审]。为了降低放行危险请求的概率，模型也可能拒绝合法但看似敏感的工作，例如授权安全测试或模型蒸馏研究。因此，安全护栏评估不仅要测试禁止性请求是否被拦截，还要测试明显允许的请求是否仍能完成。

#### 安全护栏的类型

安全护栏可以放置在三个层次：**上下文层、执行层和数据层**。这三个层次的排序不是按照它们在请求生命周期中的位置，而是按照**被绕过的难度**——层次越低，对模型自身判断的依赖越少，单次成功攻击就越难穿透。本书后续的安全讨论将围绕这个三层框架展开。
