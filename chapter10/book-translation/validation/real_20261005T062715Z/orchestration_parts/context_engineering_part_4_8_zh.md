在继续之前，有必要区分两个容易混淆的概念。**KV缓存**是模型内部的一种机制：在单次推理过程中，它会缓存已处理词元的键值状态，以避免重复计算。**Prompt Cache（提示缓存）**是推理引擎层面的优化：它在多个 API 请求之间复用相同前缀的缓存计算结果。两者都依赖前缀的稳定性，但作用层级不同。KV缓存加速的是单个请求内部的词元生成；Prompt Cache 减少的是跨请求的冗余前缀计算。在实践中，API 提供商会匹配请求的前缀。如果多个请求共享相同的前缀，提供商可以直接复用之前计算好的 KV缓存，而不必重新计算这些词元的键值状态。从缓存中读取的开销远低于重新计算——例如在 Anthropic、DeepSeek 和 GPT-5 上，价格约为十分之一。缓存的启用方式和计费方式因提供商而异：有些自动启用，有些则需要手动配置，因此使用时请查阅最新文档。

### 缓存作为架构约束

在生产级智能体系统中，缓存不仅仅是性能优化——它是一个**架构约束**，决定了系统中许多看似无关的设计决策。

Claude Code 展示了一个更广泛的模式：当 Prompt Cache 具有显著的经济价值时，缓存一致性会影响整个系统的架构选择。以下若干设计决策反映了这一约束：

**提示词结构由缓存边界决定。** 系统提示词被缓存边界标记分割：标记之前的内容可以在所有用户和会话之间进行全局缓存，而标记之后的内容则包含用户和会话特定的信息。这意味着提示词的排序主要由缓存经济学驱动，其次才由语义逻辑驱动。放置在缓存边界之前的每一个运行时条件（操作系统类型、当前模式、用户偏好等）都会使缓存键的变体数量翻倍。如果每个条件都是二元的，N 个条件将产生 2^N 种组合，因此所有动态元素都需要放在边界之后。例如，3 个二元条件（macOS/Linux、正常/调试模式、中文/英文）会产生 2×2×2 = 8 个缓存键。

**子智能体必须与父智能体实现字节级对齐。** 当主智能体派生子智能体或执行旁路查询时，如果子智能体继承父智能体的上下文，那么子智能体的提示词、工具定义、模型配置、消息前缀和推理配置必须与父智能体逐字节匹配。这使得请求能够命中 API 提供商的 Prompt Cache，从而降低成本和时延。然而，一些智能体框架在派生子智能体时会使用不同的上下文或提示词；在这种情况下，则不需要字节级对齐。

**工具结果的替换字符串在首次出现时即被固定。** 当大型工具输出被替换为摘要预览时，替换字符串会被持久化保存。即使会话重启后，系统也会复用完全相同的替换字符串，以确保恢复后的消息序列与缓存流逐字节一致。

核心洞察在于：**缓存经济学不是事后优化，而是前置的架构约束。** 越早将这一约束纳入架构设计，后续的工程成本就越低。

### 重新审视 KV缓存：可编辑、可组合的"笔记"

（以下是来自当前研究的可选进阶内容，初次阅读时可以跳过，不影响本章其余内容；上述三条实用结论才是基础。）

到目前为止，本节假设了一条严格规则：修改前缀中的一个字节，后续缓存即失效。这条规则在当今的推理引擎中成立，但未必是不可避免的。近期一项研究从一个反直觉的观察出发[^ch2-2]：在预填充（prefill）阶段 [待审]，模型的表现仿佛在"做笔记"。当模型读取上下文中的某个字段（例如"用户所在城市：北京"）时，它并不是简单地逐字缓存该字段。相反，它将该字段**结论**的下游表征——即该字段的含义——写入后续的 KV 状态。测量表明，该字段**自身**词元的 KV 状态对最终决策的贡献往往不到 1%；对输出影响更大的，是该字段留下的下游"笔记"。

这一发现揭示了两种此前被认为不可行的操作。第一种是**编辑（Editing）[待审]**：由于结论已经写入下游笔记，当模型具有显式的思维链（Chain of Thought，CoT）[待审]时，修改后的字段可以通过缓存的推理过程进行传播，产生的结果接近完全重算，但计算量仅为约 1%。反过来，如果没有思维链，孤立的字段修改可能会被忽略，因为结论已经嵌入到下游，没有推理路径来更新它。第二种是**组合（Composition）[待审]**：预计算的"技能"缓存可以通过旋转位置编码（Rotary Position Embedding，RoPE）[待审]进行重新定位，并拼接到另一个上下文中，而无需重新计算注意力。在这种框架下，从模块化缓存块组装长上下文，从 O(L²) 的重计算降为 O(L) 的拼接，输出质量接近完全重算。

旁注类比在这里很有帮助。阅读长文档时，某个事实发生变化时，人们不会重新阅读整篇文档；而是更新记录该事实含义的旁注。将 KV缓存视为笔记的思路类似：如果缓存的状态已经编码了对某个事实的推理，那么修改该事实可能只需修正下游笔记，而不必重新计算一切。由于笔记以可移植的形式表示，来自一个问题的笔记块也可以（通过 RoPE 重新定位）移至并复用于另一个问题。该论文在 vLLM 上实现了这一想法，将 p90 首词时延（time to first token）[待审]加速了数十到数百倍，前缀缓存命中率约为 98.5%，输出接近逐词元重算的效果（在 12 个模型上，logit 余弦相似度为 0.90–0.999）。

对于智能体而言，这意味着当工具、记忆字段或运行时状态发生变化时，长上下文未必总是需要拆除重建。原则上，这可以使上下文具有可变性，同时保留部分缓存收益，将上下文组装从 O(L²) 的重计算转变为 O(L) 的笔记拼接。这仍处于研究阶段；本节前面的三条实用结论仍是当前生产系统的默认原则。

[^ch2-2]: Li, Bojie. *Models Take Notes at Prefill: KV Cache Can Be Editable and Composable.* arXiv:2606.17107, 2026.

既然我们已经了解了上下文如何被处理和缓存，下一个问题就是如何设计内容本身。以下各节围绕三条相关线索，讨论上下文中应该包含什么以及如何组织：

- **提示工程、提示注入与动态提示词（智能体技能）**：如何编写系统提示词以及包含哪些内容。这是上下文工程中最直接的部分。工具定义是与系统提示词并列的另一个静态组件，也直接影响智能体的工具调用准确性。本章提供核心原则，第 4 章将详细展开。接下来的问题是安全：当外部内容试图劫持精心设计的上下文时，系统应如何在上下文层面进行防御？随着提示词越来越长、覆盖场景越来越多，将所有内容塞入单个系统提示词已不切实际：它浪费词元并稀释注意力。这自然引出智能体技能（Agent Skills）的渐进式披露机制，知识按需加载而非一次性全部包含。
- **智能体状态栏（Agent Status Bar）[待审]**：一个独立机制，在上下文末尾注入动态元信息（任务进度、环境观察摘要、工具调用次数等），弥补模型无法主动总结隐式状态的不足。类比手机屏幕顶部显示的时间、电量和网络信号，智能体状态栏让模型可以随时访问当前运行时状态。
- **上下文压缩策略**：应对上下文不断膨胀的问题——何时压缩、如何压缩，以及压缩如何与 KV缓存共存。

## 提示工程：优化系统提示词

提示工程的主要关注对象是**系统提示词（System Prompt）**——即 API 消息列表中的 `role: "system"` 消息。它是智能体的操作手册，定义了智能体的身份、行为规则、约束和工作流程。良好的系统提示词设计能让模型在特定任务中充分发挥其通用能力。

关于系统提示词设计，有一个实用的检验标准：大语言模型就像一位能力很强但完全不了解你特定工作流程和内部惯例的新成员。如果这样一位新成员在阅读了你的系统提示词后仍然不知道该做什么，智能体也不会知道。

以下几节从多个维度讨论系统提示词设计。

### 语气与风格：行为框架

语气和风格容易被忽视，但它们深刻影响用户体验。试看这样的指令："You MUST answer concisely with fewer than 4 lines." 当智能体无法完成任务时，"keep your response to 1–2 sentences"（将回复控制在 1–2 句话内）和 "do not explain why you cannot do something"（不要解释为什么你不能做某事）等约束可以防止冗长的自我辩解。"NEVER do X"（绝不做 X）这样的全大写词汇比 "Please avoid doing X"（请避免做 X）等更温和的措辞更能提升指令的显著性，但过度使用会削弱效果；应将其保留给真正关键的约束。

### 结构化提示词：系统提示词的"格式"

现代大语言模型对结构化输入表现出显著的敏感性，这源于其训练数据中包含的大量结构化内容。使用 XML 标签遵循层次化原则，标签名称本身携带语义信息——`<working_directory>` 立即告知模型这是工作目录信息，而像"Current directory: /Users/project/src"这样的纯文本格式则需要模型做额外推理来推断冒号两侧的关系。

Markdown 在保持可读性的同时提供轻量级结构，特别适合组织层次化的指令和信息。XML 与 Markdown 形成两层结构：XML 提供精确的、机器可解析的语义，而 Markdown 则为人类和机器读者组织内容。

以下是一个同时使用两者的系统提示词示例：

```text
# Tool Usage Guidelines

## File Operations
<file_operation>
- Check whether the path exists before reading a file
- Create a backup before writing a file
</file_operation>

## Network Requests
<network_request>
- Set the timeout to 30 seconds
- Retry at most 3 times after a failure
</network_request>
```

- **Markdown 的贡献**：`#` 和 `##` 等标题让人一眼就能看清层级结构，保持提示词的可读性。
- **XML 的贡献**：`<file_operation>` 和 `<network_request>` 等标签告知模型"这个块是关于文件操作的"和"这个块是关于网络请求的"——精确的语义使模型的处理更加准确。

两者结合使用时，提示词对人类阅读清晰，对模型解析精准。

### 流程驱动 vs. 规则堆叠：系统提示词的"组织方式"

能降低人类认知负荷的方法对大语言模型同样有效——因为模型在训练过程中已经学习了人类的语言和推理模式。想象给新成员一本包含数百条散乱规则的手册，没有流程图，没有优先级说明——即使是能力很强的人也会困惑：多条规则同时适用时，该选哪条？规则未覆盖的情况又该怎么办？

相比之下，流程驱动的提示词就像一份有效的培训手册，提供清晰的标准操作规程（Standard Operating Procedure，SOP）[待审]：

```text
File Processing Standard Operating Procedure:

Step 1: Validation
   Check if file exists and is accessible
   - If not found → log error and stop
   ↓
Step 2: Classification
   Determine file type based on extension and content
   ↓
Step 3: Preprocessing
   Config files → create backup
   Large files (>1MB) → stream processing
   ↓
Step 4: Execution
   Execute core processing logic based on file type
   ↓
Step 5: Verification
   Ensure integrity of the processed file
```

这种流程设计帮助模型跟踪自己处于哪个阶段、当前步骤的目标是什么、接下来应该做什么。当异常发生时，模型可以根据当前阶段选择响应方式，而不是在冗长的无关规则列表中搜寻。

### 将业务规则转化为可执行指令

在构建生产级智能体系统时，最关键且最容易被忽视的步骤之一是**将业务策略转化为精确的决策规则**。这不是一个技术问题，而是一个产品设计问题，需要产品经理的深度参与。

考虑一个帮助用户打电话解决账单问题的智能体：用户告诉智能体想要降低订阅费用或申请退款，智能体自动致电客服完成协商。为这类服务设计计费系统可以说明为什么这些规则需要精确。产品经理的核心要求是"任务未成功则退还服务费"，以鼓励用户尝试同时防止滥用。团队设计了三种计费模式：

- **节省佣金制**：智能体代表用户进行谈判并收取佣金，例如节省金额的 20%。
- **固定服务费**：对于不涉及省钱的任务（如预订餐厅），根据复杂度收取固定费用。
- **困难任务预付费**：对于成功率极低的任务，收取不可退还的预付款以过滤不切实际的请求。

然而，模糊的规则（如"根据任务情况选择合适的计费类型"）会导致智能体行为高度不稳定。"帮我退回上个月买的衣物"——这算是"帮用户省钱"还是"取回本应属于他们的钱"？"帮我取消 Netflix 订阅"——取消确实可以防止未来的付款，但这算"省钱"吗？同一任务在不同时间可能被完全不同的归类，使业务逻辑不可预测。

产品经理必须将决策规则定义到可执行的程度。佣金制仅适用于通过谈判降低现有账单的场景（智能体需要运用谈判技巧说服商家）。退款和服务取消绝不能采用佣金制——提示词必须明确声明："NEVER use percentage_based_one_time for refunds and service cancellations. Use fixed_fee instead."

成功率估算和金额计算也需要精确到可执行的程度。成功率应按固定流程逐步评估，估算概率应直接映射到计费模式。例如，估算成功概率高于 60% 的任务可采用可退款模式，低于 30% 的可能直接拒绝。金额计算必须定义计费粒度——例如电话按每分钟 0.05 美元计费，总额取整到最接近的整美元——并明确声明"节省金额"仅从现有账单中计算。否则，模型可能会推理："如果明年没有协商，价格上涨到 180 美元，我帮助维持在 150 美元，这就节省了 30 美元"，错误地将避免未来涨价计入节省。

这些规则看似琐碎，但正是这些细节决定了系统行为的一致性。在成熟的智能体团队中，提示词往往由**产品经理**设计，他们根据生产数据、用户反馈和运营经验迭代规则定义。工程师的角色是准确编码规则、确保格式正确和结构清晰，避免擅自做业务逻辑决策。

核心设计哲学是：大语言模型擅长遵循复杂指令和从长上下文中提取信息，但不应让它们在制定业务规则时拥有过大的自由裁量权。通过提供清晰的操作框架，可以释放模型的认知资源，使其专注于真正需要推理的部分。有效的培训不会让人自己去推断流程，而是提供详细的标准操作规程，让人在清晰的框架内操作。

### 少样本示例：何时向模型展示示例

除了规则和流程之外，示例（少样本示例）是系统提示词内容的另一重要类型。当期望的输出难以用规则精确描述时——例如特定风格的文案、结构化报告的格式、客服回复的语气和细微差别——提供两三个高质量的输入-输出示例往往比撰写冗长的抽象描述更有效。模型可以在当前上下文中适应这些模式，其效果往往优于遵循同等量的抽象指令（这背后的内在机制将在本章的上下文压缩一节中讨论）。相反，对于模型已经处理得很好且规则容易陈述的任务，示例只会浪费词元。

有两个工程决策点。第一，**示例放置在哪里**：放在系统提示词中使其成为对所有请求都有效的静态前缀；或者，也可以在第一轮对话中放置一组合成的用户/助手消息，适用于不同对话类型需要不同示例集的场景。第二，**示例如何影响 KV缓存的前缀稳定性**：无论放在哪里，示例都出现在上下文的前部。一旦选定，就应保持逐字节稳定。为每个请求动态检索不同的"最相关"示例会反复使缓存失效。因此，生产系统通常为每种任务类型准备一组固定的示例，而不是按请求逐个选择。

示例并非越多越好：两三个精心选择的覆盖边界情况的示例，通常比十个近乎重复的示例更有用。近乎重复的示例消耗上下文，并稀释模型对规则本身的关注。

### 工具定义设计

除了系统提示词之外，API 请求中另一个重要的静态组件是**工具定义**（`tools` 字段）。工具定义的质量直接决定了智能体工具调用的准确性。一个好的工具定义就像一本操作手册，让从未见过该工具的模型从一开始就能正确使用并避免常见错误。

Claude Code 的工具定义显示，每个工具描述都经过精心设计，包含使用边界（"NEVER invoke grep or rg as a Bash command"）、具体示例（`timezone: 'America/New_York'`）、性能提示（"Batch your tool calls together"）以及工具之间的关系（"Use the Read tool at least once before editing"）。第 4 章将详细讨论工具定义的设计原则和最佳实践。
