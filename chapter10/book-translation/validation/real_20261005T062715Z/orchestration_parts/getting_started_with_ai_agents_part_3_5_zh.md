> **实验 1-2 ★：Kimi K3 的原生智能体能力**
>
> 本实验展示了 **Kimi K3** 的原生智能体能力，它是"模型即智能体"范式的一个范例。Kimi K3 是一个混合专家（MoE）模型，参数量约为 2.8 万亿。MoE 可以看作一个专家团队：对于每类问题，系统只激活最适合的少数专家，而非整个模型，从而在保留能力的同时不承担完整的效率开销。Kimi K3 拥有 100 万词元的上下文窗口、原生视觉理解能力以及始终开启的"思考模式"。通过强化学习，它将工具调用的**决策策略**内化为原生能力：何时调用工具、调用哪个工具、传入什么参数，全部由模型自身决定，使其能够自主执行诸如网络搜索等任务。严格来说，被内化的是*何时以及如何调用*的决策；工具本身（如 `web_search` 和 `code_runner`）仍然作为 API 级别的内置工具在服务端执行。Kimi 通过一个名为 Formula 的服务端脚本引擎来运行这些官方工具。
>
> 关键观察在于：模型自主决定何时搜索、搜索什么，展现出真正的自主性；随着搜索结果返回，它会调整策略并判断信息是否充分。有一个常见的误解需要澄清：**强化学习赋予模型的是决策策略**，而非工具本身。它教会模型何时调用工具、选择哪个工具、传入什么参数、收到结果后是否继续，以及如何将数十甚至数百次调用串联成连贯的推理；这些*是否使用以及如何使用*的判断才被写入模型的权重。**工具及其执行由智能体框架或 API 内置提供**：`web_search` 和 `code_runner` 的实现、代码沙箱、以及发出调用和返回结果的基础设施全部位于模型之外。强化学习优化的是决策策略；它不会把搜索引擎或代码沙箱嵌入模型的权重中。因此，编排循环并未消失；它从客户端移到了服务端，而决策权则移入了模型内部[^ch1-2]。
>
> [^ch1-2]: 感谢读者 asdlem 通过 GitHub Issue #30 指出并澄清了这一区别：强化学习内化的是工具调用的决策策略，而非工具执行机制。参见 https://github.com/bojieli/ai-agent-book/issues/30
>
> Kimi K3 在智能体任务中的显著优势在于**长链工具调用的稳定性**——它能够维持 200 至 300 次连续工具调用，并始终保持连贯的推理，远超大多数模型在几十次调用后就开始退化的水平。K3 针对长周期编程和智能体工作负载进行了优化，发布了两个变体：K3 Max（用于对话和智能体任务）和 K3 Swarm Max（用于大规模并行处理）。作为一个开源模型，它在软件工程和智能体基准测试中与顶级闭源系统相匹衡——这证明了强化学习能够赋予模型原生的智能体能力。
>
> **实验 1-3 ★：GPT-5.6 的原生深度研究能力**
>
> 第二个实验使用 **OpenAI GPT-5.6** 来展示一个先进的模型如何借助 API 级别内置工具，在服务端为深度研究（Deep Research）闭合"搜索—阅读—分析"编排循环。GPT-5.6 有一个便利的特性是**自由格式工具调用（Freeform Tool Calling）**。传统上，模型调用工具时必须将每个参数序列化为严格的 JSON（一种结构化数据格式），就像按照僵硬的格式规则填写表格。自由格式工具调用（在 API 中通过 `type: "custom"` 的工具声明）允许模型直接向工具发送原始文本（如一段 Python 代码、一条 SQL 查询），完全避免了 JSON 转义。需要强调的是，这是 API 参数格式的演进，而非模型架构上的创新——客户端的工具调用循环（检测 `tool_calls` → 执行 → 返回结果）保持不变；只有参数从 JSON 字符串变为原始文本。
>
> GPT-5.6 配合 Responses API 的**网页搜索和代码解释器**内置工具，实现了深度研究的核心机制：模型可以自主搜索网络获取实时信息，并编写代码进行深入分析，实现"搜索 → 阅读 → 分析 → 再次搜索"的迭代研究过程。例如，面对"东盟十国首都之间的最短距离是多少？"这样的问题，GPT-5.6 会自动搜索每个首都的地理坐标，然后编写 Python 代码计算所有首都两两之间的大圆距离，最终找出距离最近的一对。类似地，在"搜索比特币过去一个月的走势并进行技术分析"这样的任务中，它可以从多个金融数据源获取实时价格数据，利用专业技术分析库计算移动平均线、RSI、MACD 等技术指标，生成可视化图表，并给出交易建议。
>
> 更重要的是，GPT-5.6 在模型层面内化了 **OpenAI Deep Research** 产品的设计理念，引入了**意图澄清流程**。面对研究请求，GPT-5.6 不会立即开始执行；它会先通过一系列问题澄清用户的真实意图。对于"搜索比特币过去一个月的走势并进行技术分析"，它会先问："您偏好哪个数据源？您希望分析哪些技术指标？"这种交互式澄清使 GPT-5.6 能够产出更精准、更符合用户实际需求的研究报告。
>
> GPT-5.6 是"模型即智能体"的成熟范例——网页搜索、代码解释器等 Responses API 内置工具在服务端闭环执行；编排循环从客户端移至 API 服务器，简化了客户端实现。模型仍然输出标准的工具调用；只是客户端不再需要自行构建"搜索—阅读—分析"编排框架。最值得注意的是其意图澄清机制：模型不是立即执行任务，而是先确认用户真正需要什么，再制定研究策略。"用户说了什么"与"用户实际想要什么"之间的鸿沟在执行开始之前就被弥合了。
>
> 需要说明的是，本实验不绑定于任何特定厂商。没有 OpenAI 额度的读者可以用提供等效托管工具的服务商复现。例如，阿里云百炼的 qwen3.7-plus Responses API 同样包含内置的 `web_search` 和 `code_interpreter`；Kimi K3 由 Formula 管理的搜索和 `code_runner` 提供同类能力。

## 驾驭层工程：围绕模型构建可靠系统

至此，你已经理解了智能体的核心工作方式：大语言模型运行推理-行动循环，由上下文引导，使用工具完成任务。上面的实验表明基本机制是可行的——同时也暴露了它有多么脆弱。模型可能产生幻觉（捏造不存在的工具或参数）、选错工具，或无法从错误中恢复。一个可运行的演示与一个可靠的产品之间存在相当大的差距，而这些脆弱性正是驾驭层工程所要解决的问题。本章前半部分回答了智能体是什么；后半部分回答的是智能体如何在生产环境中可靠运行。

前文确立了核心公式：**智能体 = 大语言模型 + 上下文 + 工具**。它描述了智能体的**内部构成**：推理引擎、工作上下文和动作接口。驾驭层工程为同一系统提供了第二个、**实现层面**的视角：将大语言模型视为一个核心组件（模型），将围绕它构建的所有支撑代码统称为驾驭层。两个视角并非对立，而是从不同抽象层次描述同一个系统。我们改用更通用的"模型"一词，是因为驾驭层工程的原理适用于任何能够推理和调用工具的模型，而非某一特定类型。驾驭层的核心是原公式中的"上下文 + 工具"，再加上三层保障：**约束**（智能体可以和不可以做什么）、**验证**（它是否正确完成了任务）、**纠正**（当它做错时如何恢复）。

展开为等式，完整的生产级构成为：

> **智能体 = 模型 + 驾驭层**
>
> **驾驭层 = 上下文管理 + 工具接口 + 约束 + 验证 + 纠正**
>
> **智能体 ↔ 环境**

最小的演示只需要一个模型和一个能够构建上下文、暴露工具的驾驭层；生产系统则必须在同一边界内增加约束、验证和纠正。例如，一个退款智能体可以将政策放入上下文，用权限和金额规则约束调用，对照数据库状态验证结果，并在超时后重试或回退。驾驭层工程研究的正是这些运行时和治理代码——位于模型之外，但在智能体边界之内。

更精确地说，驾驭层并非模型之外的所有东西：它是**位于智能体边界内、模型之外**的运行时和治理层。它介导模型与环境的交互，但不包括环境本身。工具定义、调用适配器、沙箱权限和重置机制属于驾驭层；沙箱内发生变化的文件和进程、外部数据库、网页、用户以及物理世界属于环境。部署位置不改变这一概念边界。驾驭层的核心是上下文管理和工具接口，围绕它们构建了三类工程保障：

| 组件 | 职责与设计原则 | 实际示例 | 参见章节 |
|---|---|---|---|
| **上下文管理** | 提供相关信息。**信息充分性：**在每一步给智能体足够的信息以做出明智决策。 | 系统提示词、知识库、智能体状态栏、Sidecar 旁路查询 | 第 2、3 章 |
| **工具接口** | 定义模型如何行动。**清晰的接口：**使用直观的工具名称，提供参数示例，说明每个工具的限制。 | MCP 工具、代码解释器、搜索工具 | 第 4 章 |
| **约束** | 定义智能体被允许做什么。**安全默认值：**能力默认关闭，直到显式启用，类似于移动应用权限。 | Claude Code 默认要求用户授权后才执行工具。 | 第 4 章 |
| **验证** | 检查工具执行是否产生了正确结果。**输入隔离：**基于结构化数据进行安全检查，例如工具返回的字段，而非模型生成的文本——后者可能被攻击者通过提示注入影响。 | Lint 检查、类型检查、工具结果校验 | 第 5、6 章 |
| **纠正** | 从错误中恢复或回滚失败的操作。在向用户呈现失败之前先尝试恢复——例如，重试失败的工具调用，而不是展示不完整的结果。 | 自动重试、恢复生成、多次失败后升级给人工处理（熔断机制） | 第 2、5 章 |

基本的模型控制循环如下方伪代码所示：

```python
observation = Environment.observe()
trajectory = [observation]
while true:
	actions = Model(Harness.build_context(trajectory))
	if len(actions) == 0:
		break
	allowed_actions = Harness.constrain(actions)
	observation = Environment.apply(allowed_actions)
	if not Harness.verify(Environment):
		observation = Harness.correct(Environment)
	trajectory.append(allowed_actions, observation)
```

该框架刻意省略了实现细节。完整的 API 消息循环见第 2 章；工具和自动验证分别在第 4 章和第 5 章中介绍。

上下文和工具让智能体能够完成任务——理解任务并采取行动。约束、验证和纠正确保它可靠且安全地完成任务——它们不是上下文和工具之外的附加物，而是让它们在生产环境中可靠运行的工程手段。在智能体产品的成熟度曲线上，这两组要素之间的重心会逐渐转移。

早期的智能体框架侧重于上下文和工具：给模型工具，给它上下文，让它完成任务。生产级系统已经将重心转移到约束、验证和纠正上：确保工具调用是安全的、上下文是被管理的、错误是可恢复的。

以 Claude Code 为例。其驾驭层代码的绝大多数属于约束、验证和纠正，而非上下文和工具——工具本身（文件读写、命令执行、搜索）只占很小一部分；围绕它们构建的保障机制才是真正的核心。这些机制包括：

- **进程状态管理**：跟踪智能体当前正在执行哪一步
- **多层上下文压缩**：信息过多时自动裁剪
- **权限分类**：控制哪些操作需要用户确认
- **熔断器**：重复出错后自动停止重试，防止单个失败的操作级联到整个系统
- **错误恢复机制**：捕获异常，回滚到最近的稳定状态，重试，或交由人工处理

**行业正从任务完成转向可靠的任务完成，这使得驾驭层工程成为智能体系统的核心竞争优势。**

### 从提示工程到循环工程：工程范式的演进

回顾 AI 应用工程的发展历程，一条清晰的演进脉络浮现出来：

**提示工程**是第一波创新——通过改进输入模型的自然语言指令来提升输出质量。

**上下文工程**是第二波——人们认识到仅优化提示词是不够的：模型能看到的所有信息（系统指令、工具定义、对话历史、外部知识）都需要系统化管理。

**驾驭层工程**是第三波——它将视野从"模型接收到什么信息"扩展到"模型运行在什么样的系统中"，纳入模型之外的所有基础设施：约束机制、验证方法、反馈循环、错误恢复。

**循环工程**接踵而至，将视野从单次运行扩展到跨运行的持续自主运行：谁来发现下一项工作、何时验证、以及任务何时才算真正完成（第 10 章与多智能体协作系统一起展开讨论）。

2026 年 7 月，业界开始使用**图工程（Graph Engineering）**这一更高层次的编排视角：将智能体循环、确定性程序和人工审批组织成显式执行图，其中节点提供能力，边定义路由和依赖，结构化状态沿这些边传递，并在关键边界处持久化[^ch1-graph-engineering]。

[^ch1-graph-engineering]: Josh C. Simmons 在其 2026 年 7 月 4 日的文章 *We Are Entering the Graph Engineering Phase* 中明确使用了这一名称，并以节点、带类型的边和检查点状态加以概括。7 月 18 日，Peter Steinberger 关于讨论是否已从循环转向图的提问进一步推动了该名称的传播。这些实践先于该标签出现：LangGraph、Microsoft Agent Framework 和 Google ADK 的官方文档都将它们描述为图编排或基于图的工作流。参见 https://www.drjoshcsimmons.com/writing/we-are-entering-the-graph-engineering-phase、https://x.com/steipete/status/2078277297791189132、https://docs.langchain.com/oss/python/langgraph/overview、https://learn.microsoft.com/en-us/agent-framework/workflows/ 和 https://adk.dev/workflows/。

这五个阶段并非相互替代，而是层层嵌套：提示工程是上下文工程的子集，上下文工程是驾驭层工程的子集，驾驭层工程是循环工程的子集。循环工程又是图工程的子集：单个智能体循环构成执行图中的一个节点。每一层都将工程师的关注范围和影响力扩展到上一层之外。**当模型能力趋于趋同、不再成为决定性的差异化因素时，竞争优势便转移到模型之外的工程上。**

近期的工程实践印证了这一观点。LangChain 在 Terminal Bench 2.0（一个评估智能体在终端环境中完成复杂任务能力的基准测试）上的工作就是一个引人注目的例子：他们的编码智能体从 52.8% 提升到 66.5%（从榜单 30 名开外跃升至前 5）。改变的不是模型，而是驾驭层——让智能体检查自身的执行结果、检测是否陷入重复循环，并优化推理策略。

### 构建高效智能体的核心原则

基于 Anthropic 的经验，成功的智能体系统遵循三个核心原则[^ch1-anthropic-building-effective-agents]。

**保持简洁。** 从最简单的方案开始，仅在真正必要时才增加复杂度。直接的 API 调用优于复杂的框架；清晰的代码优于精巧的抽象——每多一层抽象，调试时就多一个盲区。

**保持透明。** 清晰展示智能体的规划步骤、执行日志和决策轨迹。这不仅是调试的便利，更是用户信任的前提——黑盒中的错误很难从外部定位或修复。

**设计结构良好的工具接口（ACI，智能体-计算机接口）。** ACI 意味着从智能体的视角设计接口——让智能体易于理解和使用——而不是像传统 API 那样从程序员的视角出发。工具名称和参数应当直观，在容易误用的地方，设计应使错误从一开始就不可能发生：SIM 卡的缺角使其只能以一个方向插入卡托，微波炉门打开时拒绝加热。在制造业中，这种方法被称为 **poka-yoke（防呆法）** 或 **防错（mistake-proofing）**：通过设计产品和流程来防止错误，或使错误立即可见。丰田生产体系中就采用了这一方法[^ch1-poka-yoke]。设计不当的工具即使是能力最强的模型也会反复失败：接口是模型与工具之间唯一的通道，含糊的接口会被放大为系统性错误。

[^ch1-poka-yoke]: Toyota UK，["Poka-yoke – Toyota Production System guide"](https://mag.toyota.co.co.uk/poka-yoke/)；American Society for Quality (ASQ)，["What Is Mistake Proofing?"](https://asq.org/quality-resources/mistake-proofing)。两者都将防错描述为防止错误发生或在错误出现时立即检测到。

[^ch1-anthropic-building-effective-agents]: Anthropic. "Building effective agents", 2024 年 12 月。https://www.anthropic.com/engineering/building-effective-agents

接下来的三节讨论驾驭层工程中三个独立但重要的话题：模型选择、编排模式以及安全护栏与安全性。它们都不属于驾驭层的五个核心要素，但在工程实践中都是无法回避的。

### 如何选择模型
