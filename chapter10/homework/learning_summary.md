# 《AI Agent》第一至十章学习总结

一个 Agent 的基本结构可以概括为 LLM、上下文和工具：LLM 负责理解与决策，上下文决定它能看到哪些信息，工具决定它能对外部世界做什么。真正影响系统稳定性的，不只是模型能力，还包括围绕模型建立的 Harness，例如权限控制、结果验证、错误恢复、终止条件和人工接管机制。模型会犯错并不可怕，关键是系统能否及时发现错误，并通过重试、修正或回滚降低影响。

上下文工程是 Agent 开发中的核心工作。上下文并不是把信息越多越好地塞给模型，而是要让当前任务真正需要的规则、状态、历史和工具说明清晰可见。稳定的提示词前缀有利于缓存，Skills 可以按需加载领域知识，状态栏可以记录目标、进度和约束。当对话越来越长时，应保留关键决策、失败原因和信息来源，对重复或过时内容进行压缩。对于复杂任务，使用子 Agent 隔离上下文，有时比不断压缩同一个上下文更加有效。

用户记忆和知识库解决的是跨任务的信息保存问题。用户记忆应只保存有依据、与后续任务有关的信息，并注意来源、时效、冲突和隐私。知识库则通常经过文档分块、稠密与稀疏检索、结果融合、重排序和生成等步骤。RAG 的重点不只是“搜到内容”，还要保证召回结果与当前问题有关，并能追溯原始材料。知识写入也不应直接覆盖旧内容，而应经过审核、增量更新和定期整理。

工具扩展了 Agent 的能力边界，但工具数量越多，选择和安全问题也越突出。工具描述、参数定义和返回结果需要准确，模型看到的参数必须与实际执行一致。只读的感知工具适合并行和缓存，带有外部影响的执行工具则需要分层权限、事前审批和事后检查。代码是其中很重要的一类通用能力，它不仅可以完成编程任务，还能用于计算、约束业务规则、处理数据、生成界面和适配不同系统。软件工程中的测试、类型检查和版本控制，也为 Agent 提供了天然的验证与恢复手段。

随着交互范围扩大，Agent 不再局限于文字对话。异步事件让系统能够在用户不在线时继续处理任务，语音、屏幕操作和机器人则把观察与动作扩展到更多模态。无论界面如何变化，基本闭环仍然是感知状态、选择动作、执行、观察反馈，再决定继续、修正或停止。尤其在 GUI 和物理环境中，动作完成并不等于任务完成，必须再次观察实际结果。

评估决定了系统改进是否可信。除了关注单次最好成绩，还要关注连续成功率、成本、速度和安全性。评估任务应来自公开基准、真实业务和生产失败案例，并结合确定性验证器、规则清单、模型评审及人工检查。只有把失败定位到具体步骤，才能提出有效修改。后训练也应按问题选择方法：基础知识或能力不足可考虑 Mid-training，输出协议不稳定可用 SFT，已有可评分轨迹且需要优化策略时再使用强化学习。数据质量、环境真实性和奖励设计往往比算法名称更重要。

Agent 的持续进化不等于让模型在线随意修改自己。更稳妥的方式是在线记录轨迹和反馈，离线形成知识、提示词、Skill、程序或参数的修改方案，再通过回归测试、小范围发布和回滚机制验证效果。每次改动都应尽量小、可解释、可追踪，避免一次修改引入新的问题。

多 Agent 协作也不是 Agent 数量越多越好。只有当不同 Agent 能提供新的信息、独立验证或明确分工时，协作才有意义。共享上下文便于保留细节，却容易膨胀并产生角色惯性；隔离上下文便于并行和权限控制，但必须设计清晰的移交内容、共享文件和验收标准。多 Agent 还可能出现文件冲突、错误级联、观点趋同和循环失控，因此需要工作副本、版本检查、预算、取消机制和交叉验证。

总体来看，构建可靠 Agent 的重点不是追求表面上的自主性，而是设计好信息、工具、反馈和责任边界。先把任务拆清楚，再提供必要上下文和工具；执行后用可验证的标准检查结果；发现问题后进行可回滚的局部改进。多 Agent、RAG、后训练等方法都只是解决特定问题的手段，是否采用应由实际收益和成本决定。人仍需理解系统的关键判断，并对最终结果负责。
